## 3.5 标准执行流程（0~8，逐项勾选，不漏项）

> 目标：从“读文档”→“开发”→“推 Git”→“开周会”→“下一轮迭代”完整跑一圈。  
> 背景：仓库主分支是 `dev`，任务按 Issue 编号推进（如 `#16/#17/#18/#29/#31`）。

### Step 0 开始前（5 分钟）

- [x] 今天只做 1~2 个最小可交付项（本轮先做 `#31` 最小主路径：回放列表 + 锚点回跳）
- [x] 已打开：架构文档 + 周计划模板 + 对应 issue 描述
- [x] 已写“今日完成定义”：`#31 最小链路可演示 + compile 通过 + issue/run 同步`

建议命令：
- `git -c gc.auto=0 status -sb`
- `git -c gc.auto=0 log --oneline -3`

输出物：
- 一句话“今日完成定义”
- 本轮仅 1~2 个交付项清单
  - 交付项 1：`回放列表最小展示与状态提示`
  - 交付项 2：`锚点回跳入口与动作回显`

### Step 1 读文档并拆成可执行任务（20~40 分钟）

先读三类内容并回填到 2.1/2.2：
- [x] 业务目标：这个功能解决什么问题（为什么做）
- [x] 技术边界：输入/输出、依赖谁、不能改什么（做什么/不做什么）
- [x] 验收标准：完成后别人怎么判断“合格”

按单个 issue 拆成 3~6 个小步骤（示例）：
- [x] Step1：定义 #31 回放条目最小字段（id/timestamp/source/eventId/status）
- [x] Step2：定义回跳协议（record -> session/trace/event）
- [x] Step3：实现回放列表最小 UI 容器与空态约束
- [x] Step4：准备最小自测脚本（渲染、回跳、无数据兜底）
- [x] Step5：准备 issue 更新模板（Done/Next/Risk）

输出物：
- 一份“今天的微任务清单”（1~2 小时内能看到进展）
  - 微任务 A：`完成回放列表 mock/真实源切换框架`
  - 微任务 B：`完成锚点回跳动作与详情回显`
  - 微任务 C：`跑 compile 并回填 #31 进展`

### Step 2 开发前准备（10 分钟）

- [ ] 同步代码：`git checkout dev` → `git -c gc.auto=0 pull origin dev`
- [ ] 查看状态：`git -c gc.auto=0 status -sb`
- [ ] 拉依赖（按项目需要）：`npm install` / `bun install`
- [ ] 启动本地环境（按仓库约定）
- [ ] 记录“回滚点”（当前 commit hash）

输出物：
- 可回退 hash（写在 4) 执行日志）

### Step 3 正式开发（1~3 小时，循环）

循环节奏（每 25~40 分钟一轮）：
- [ ] 实现一小段功能（只做一件事）
- [ ] 立刻本地验证（最小命令）
- [ ] 记录结果（成功/失败/下一步）

新手执行原则：
- [ ] 一次只改一个问题，不“顺手大改”
- [ ] 改完马上跑，不攒一堆再跑
- [ ] 错误先定位三类：`输入不对 / 流程不对 / 状态不对`

卡住 > 30 分钟处理：
- [ ] 先降级目标（先通主路径，边缘场景后补）
- [ ] 在 issue 留 blocker，不硬拖

### Step 4 本地自测与验收（20~40 分钟）

- [ ] 先跑最小验证，再跑完整验证
- [ ] 已执行项目测试命令（示例：`npm test`）
- [ ] 必要时已跑单测/关键脚本

四个验收问题（必须逐条回答）：
- [ ] 能不能跑通主流程？
- [ ] 错误时有没有可读日志？
- [ ] 是否符合文档约束（字段、接口、状态）？
- [ ] 有没有引入明显副作用？

规则：
- [ ] 四问通过后才进入提交阶段

### Step 5 提交 Git（10~20 分钟）

- [ ] 查看变更：`git -c gc.auto=0 status`、`git -c gc.auto=0 diff --name-only`
- [ ] 分批提交，不要“一坨提交”
- [ ] 已执行：`git add <files>`
- [ ] 已执行：`git commit -m "feat(obs): add bridge adapter minimal path"`
- [ ] 已执行：`git -c gc.auto=0 push origin dev`

提交信息规范：
- [ ] 使用 `type(scope): summary`
- [ ] 常见 type：`feat / fix / docs / refactor / chore`

### Step 6 更新 issue（10 分钟）

每个关联 issue 至少更新四项：
- [ ] Status：`IN_PROGRESS` 或 `DONE`
- [ ] ETA：是否按预期
- [ ] Done：本次完成了什么
- [ ] Blocker/Risk：还差什么、风险是什么

建议命令：
- `gh issue view <id> --repo MoRen9527/TriMetaverse --json number,title,body`
- `gh issue edit <id> --repo MoRen9527/TriMetaverse --body-file <file>`

### Step 7 开周会（30 分钟）

周会只讲三件事：
- [ ] 上周完成什么（证据：commit/issue）
- [ ] 本周做什么（按关键路径）
- [ ] 当前阻塞什么（需要谁协助、何时解决）

1 分钟发言模板：
- [ ] 我负责 `#16`，本周已完成适配器最小链路并推送 `dev`。
- [ ] 下周做 `#17` 契约校验，预计 1~2 天。
- [ ] 风险是历史事件字段不一致，需要确认兼容策略。

### Step 8 周会后立刻进入下一轮（关键）

会后 15 分钟动作：
- [ ] 把周会决议写回 issue/计划文档（避免遗忘）
- [ ] 调整优先级（优先处理 blocker）
- [ ] 重新定义下一轮“最小完成目标”

进入下一轮命令：
- [ ] `$ts = Get-Date -Format "yyyy-MM-dd-HHmm"`
- [ ] `$target = "docs/runs/run-R{N+1}-$ts.md"`
- [ ] `Copy-Item "docs/执行轮次参考模板.md" $target`

输出物：
- 下一轮执行文件（`R{N+1}`）已创建
- 本轮未完成项已迁移到下一轮
