## 1. 先区分两个概念：赛博公司与 TriCompany

“赛博公司 / cyber company”是一个通用概念，指由 AI 岗位、结构化流程、运行证据和治理规则支撑的经营载体与组织形态。它不是一句营销口号，其背后包含一套关于“公司如何被机器辅助、被规则固化、被证据追踪、被持续迭代”的可复用方法。

`TriCompany` 则不是泛化概念，而是这个概念在 `TriMetaverse` 项目里的具体产品化落点。也就是说：

- 赛博公司是类目名。
- `TriCompany` 是当前项目把这个类目落成可运行产品时使用的名字。
- training、workflow、registry 和代码里的 `TriCompany`，都指向当前项目的具体经营载体，而不是泛指所有 AI 公司。

这个区分非常关键。若不区分，团队会在三种错误之间来回摇摆：

1. 只谈概念，不落产品，最后变成“大家都知道未来很酷，但今天没人知道要改哪份文件”。
2. 只谈工具，不谈经营载体，最后变成“做了一堆 agent，却不知道它们共同在为哪种组织形态服务”。
3. 只谈自动化，不谈经营闭环，最后变成“功能越来越多，但没有真实用户、真实收入和真实治理压力”。

## 2. 为什么 TriMetaverse 需要一个具体经营载体

`tricompany.md` 对这个问题讲得很直白：TriCompany 不是为了“养一个组织”而存在，而是为了把三元宇宙上游形成的规则、方法、内容、产品设计与工程能力，压到真实经营世界里，接受真实收入、真实用户、真实成本、真实交付与真实复盘的检验。

如果没有 TriCompany，TriMetaverse 很容易停留在：

- 白皮书、PRD、workflow 很完整；
- agent 与 prompt 很多；
- 但缺少一个能够把“认知产物 -> 产品决策 -> 研发交付 -> 上线运营 -> 回款复盘”真正串起来的经营壳。

TriCompany 的存在，就是为了补这个“经营壳”。它至少承担四件事：

1. 把上游白皮书与规则转成可以卖、可以交付、可以复盘的产品或服务。
2. 把人类与 AI 的协作方式，从一次次会话经验固化成岗位、流程、对象和审计链。
3. 把成本、预算、产出和收入变成结构化记录，而不是留在口头描述里。
4. 为未来更强的自动治理、宿主迁移与链上透明结算准备数据与流程基础。

所以从产品角度讲，TriCompany 本质上是 **operating shell + human/AI collaboration OS**：一方面它是当前商业实验的经营承载体，另一方面它又像一个人机协作操作系统，把岗位、流程、交接、发布、证据和回写组织起来。

## 3. 为什么不是先做“全自动 AI 公司”

这是 CPO 与 BusinessStrategy 都反复强调的一点：**当前目标不是一步到位做完整自治公司，而是先做最小盈利闭环。**

`tricompany.md` 已经把这个阶段目标写得非常清楚：

- 先让公司“能活、能卖、能复盘、能自动推进”。
- 先在极低成本约束下跑通小闭环，而不是先堆满岗位、系统和治理层。
- 先把经营同步、研发同步、交付同步和回写同步跑顺，再逐步升级自动化。

因此，当前态的 TriCompany 不应该被讲成：

- 完整 DAO 治理已经实现；
- CEO 任免和股东会流程已自动化；
- TriMC 正式宿主已经切换完成；
- 全岗位都已成熟运行；
- 链上透明结算已经上线。

当前态更准确的讲法是：

- 以 `CEO + CEOChiefOfStaff` 为中枢，先跑通真实经营协调；
- 再逐步让 `CPO / CTO / COO / CFO / CHO / CAO / CMO` 等岗位进入统一员工体系；
- 在 `Copilot-host` 当前 live 阶段，把 source 规则、support payload、live 入口与运行证据先打通；
- 在真实试点里证明这套组织方式能带来更快的上线、更低的协调成本和更清楚的治理边界。

## 4. 当前商业目标为什么是“小而盈利”

从产品训练角度，这一点一定要给新人讲透：TriCompany 不是“大公司模拟器”，而是**小闭环盈利优先的经营底盘**。

原因有三层。

第一层，真实经营压力会逼出真正有价值的流程。  
只有当你必须面对成本、交付、用户反馈和收入时，岗位边界、handoff、workbench、audit、发布纪律这些看似繁琐的机制才会变得真实。

第二层，低成本约束迫使系统保持克制。  
`tricompany.md` 里已经明确“一期先求小闭环盈利，再求规模化”，并给出了非常硬的成本边界。这个边界会反过来要求岗位必须可复用、流程必须可裁剪、宿主必须能渐进演进，而不是无限增加复杂度。

第三层，小闭环更适合验证 AI 治理能力。  
如果今天连一个小规模、可交付、可复盘的经营闭环都跑不通，那么谈全自动治理只会变成空转。TriCompany 的路线是：先让最小壳跑起来，再让治理自动化一点点长出来。

## 5. TriCompany 的产品角色：经营载体，而不是单一模块

训练新人时经常会遇到一个误解：有人把 TriCompany 当成“另一个 AI 模块”，像 `TriDev`、`TriMC` 一样只负责某一段工程功能。这个理解不完整。

TriCompany 更接近于项目级经营载体。它要协调的不是单一技术功能，而是：

- 目标如何被翻译成任务；
- 任务如何被不同岗位承接；
- 岗位如何有 source truth、support object 和 live entry；
- 交付结果如何形成审计与治理证据；
- 哪些东西继续留在模块里，哪些上升到中央治理。

换句话说，TriCompany 的价值在于把“项目能做什么”升级为“项目怎样以公司形态稳定做成事”。它不是替代其他模块，而是给这些模块提供一个统一经营与治理承载面。

## 6. 当前态与目标态

| 维度 | 当前态 | 目标态 |
| --- | --- | --- |
| 宿主 | 当前 live 主要由 `copilot chat` 承载 | `TriMC` 自身完成 source -> shadow test -> 正式接管后，通过 `TriModel` 的 Provider/Model 配置进行正式宿主切换 |
| 岗位 | 以最小岗位闭环渐进启用 | 岗位体系更完整，授权矩阵与签字链更清晰 |
| 经营目标 | 小闭环盈利、低成本验证、先卖再扩 | 更稳定的产品矩阵、更多自动治理、更多跨模块协同 |
| 治理 | 以 workflow、registry、audit 和 operating record 为主 | 更强的自动审批、追踪、链上透明结算与长期治理 |
| 研发协同 | source-first + support/live 渐进发布 | 更成熟的宿主适配、验证门禁和独立运行面 |

## 7. 本章小结

TriCompany 的必要性，不在于“我们也想做一个 AI 公司”的愿景表达，而在于它把 TriMetaverse 的技术、产品、流程和经营目标放进了一个必须对现实负责的容器里。只有这个容器存在，`source -> publish -> live -> runtime -> governance` 这条链才有真实意义；也只有这条链在真实经营里被逼着跑通，TriMetaverse 才有机会从概念工程，走向接近全自动运行的 AI 治理公司。
