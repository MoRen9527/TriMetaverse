## 1. TriCompany 里的“员工”到底是什么

在 TriCompany 里，员工绝不是一个孤立的 agent 文件，也不是一次会话里临时起的角色扮演。一个可持续运行的员工，至少同时包含六个面：

1. **岗位定义**：这个岗位为什么存在、负责什么、不负责什么。
2. **源侧五件套**：`agent / soul / memory / colleagues / social` 五个文件，把岗位长期规则与认知边界固化下来。
3. **知识空间对象**：`role / employee / org shared / audit` 四类 workspace，用来承接岗位知识、员工实例知识、组织共享知识和审计证据。
4. **support payload**：当前宿主实际消费或落盘的对象目录、published-copy 与支撑包。
5. **live entry**：真正暴露给宿主发现和调用的入口。
6. **runtime state**：在运行中产生的消费记录、wiki、工作台快照与私有记忆。

只有把这六个面连起来，你才能真正回答“这个员工是怎么上岗的、怎么交接的、怎么变更的、怎么退场的”。

如果把这套设计再压缩成一个便于 onboarding 的教学视角，也可以把它理解成一个“三层模型”。这个三层模型不是替代上面的六个面，而是把同一套工程对象换一种更容易讲透的方式重新组织：

- **自我层**：岗位契约与自我叙事，对应岗位定义与源侧五件套，回答“我是谁、我为什么存在、我长期按什么规则行动”。
- **运行层**：任务执行与记忆写入，对应 employee workspace、support payload 与 runtime state，回答“我如何处理任务、把什么写入连续性对象、哪些结果进入当前宿主运行面”。
- **观察层**：跨角色元认知与审计判断，对应 `org/shared`、`audit`、中央治理回填与跨岗位校正，回答“谁在公司级视角复盘事实、纠偏判断，并把运行结果转回组织可用的知识与证据”。

因此，前面的六个面更像工程展开图，三层模型更像教学压缩图：自我层负责稳定身份，运行层负责现实执行，观察层负责公司级元认知、审计与再校准。

## 2. 源侧五件套：为什么是五个文件，不是一个文件

`TriCompany/runtime/cognition/employee_source_kit.py` 直接把 canonical 五件套写成了：

```python
SOURCE_KIT_SUFFIXES = ("agent", "soul", "memory", "colleagues", "social")
```

这意味着 TriCompany 明确拒绝“把所有东西塞进一个超长 prompt 文件”的做法，而是把不同层次的稳定规则拆开：

- `agent`：岗位定位、输入来源、输出原则、认知分层约束。
- `soul`：人格、语气、风格、禁止退化。
- `memory`：源侧记忆层契约，规定哪些能写进运行记忆、哪些不能写回源码。
- `colleagues`：协作关系层契约，定义长期协作边界，不记录临时聊天纪要。
- `social`：社交层契约，定义社交与关系语义边界，不混入运行态碎片。

这种拆法的价值非常实际：

1. **可维护**：改口吻时不必动职责，改边界时不必动人格。
2. **可验证**：validator 可以检查每层有没有混入不该出现的内容。
3. **可发布**：运行态知识可以落在 support/runtime，不必污染源码。
4. **可交接**：离开当前宿主或更换当前员工实例时，源侧五件套仍然是岗位长期定义。

`employee_source_kit.py` 里的 validator 还做了两类硬门禁：

- 禁止把 `阶段记忆记录`、`工作关系人物档案`、`最近整理时间` 这类消费痕迹直接写回源侧。
- 禁止把 `TriMetaverse/.github/agents/...`、`TriCompany-copilot-host-assets/...`、`.tricompany-cognition/...` 这类当前宿主绑定事实塞进源侧五件套。

这背后的哲学很重要：**源侧文件写“规则”，运行态对象写“消费结果”**。

## 3. 知识空间：岗位与员工为什么要拆开

`TriCompany/runtime/cognition/knowledge_workspace.py` 给了一个非常清楚的抽象：workspace 不是只有员工个人目录，而是至少四类：

- `role`
- `employee`
- `org`
- `audit`

它们对应的含义分别是：

| Workspace | 作用 | 为什么必要 |
| --- | --- | --- |
| `role/<role-id>` | 岗位级可复用方法、长期职责知识 | 岗位可以换人，但岗位方法不能跟着某个实例一起消失 |
| `employee/<employee-id>` | 当前员工实例的工作连续性、inbox、wiki、workbench、audit | 同一岗位的不同实例，需要保留各自工作连续性 |
| `org/shared` | 跨岗位可共享的组织知识 | 避免所有经验都被锁在单岗位私域里 |
| `audit` | 发布、整理、审批、提醒、schedule 等证据 | 没有审计层，就无法让 AI 公司真正可复核 |

这套抽象解决了一个传统 prompt 工程很难解决的问题：**同一岗位的“稳定职责”和“当前实例的临时连续性”如何分离**。  
TriCompany 的答案是：岗位知识归岗位，员工实例知识归员工，跨岗共识归组织共享，所有关键动作留审计。

## 4. 员工的四类生命周期动作

### 4.1 入职

入职并不是“把一个 agent 文件丢进 `.github/agents/`”。在 `host-object-publish-flow.md` 的流程里，入职至少要经过：

1. 明确岗位职责与 owner 边界。
2. 在 `TriCompany/.github/source-agents/<employee-id>/` 生成或补齐源侧五件套。
3. 用 source kit validator 检查是否混入运行态消费数据。
4. 通过 `knowledge_workspace.py` 确认 role / employee / org / audit 的路径抽象。
5. 通过 host object generation / publish wrapper 生成 support payload。
6. 更新 `binding profile`、`host-object-manifest`。
7. 判断是否需要新增或复用 live entry。
8. 最终做 governance / handoff 回填。

这就是为什么 TriCompany 的员工入职，本质上是一个小型发布流程。

### 4.2 岗位变动

岗位变动最容易出问题，因为大家常常只改当前 live 文案，却忘了回链。TriCompany 明确要求：职责变动至少要反查源侧五件套、docs、binding profile、support payload、host manifest 和 live discovery 是否同步。

换句话说，岗位变动不是“改一句岗位描述”，而是一次受控的结构变更。

### 4.3 离职

TriCompany 当前对离职的设计思想不是“删文件”，而是让岗位定义继续留在 source truth，把当前实例的运行痕迹留在 employee workspace / audit / runtime state，以便：

- 继任者可以接手岗位方法；
- 审计者可以复盘上一任员工做过什么；
- 组织可以保留 handoff 证据，而不是靠口口相传。

### 4.4 岗位交接

`host-object-publish-flow.md` 已经把这件事明确分工了：

- `CHO` 负责 handoff checklist 与 completion tracking 的流程设计和监督。
- `CAO` / `CompanyGovernanceRegistry` 负责秘书处、会议制度和治理资料归属。
- `CEOChiefOfStaff` 负责公司级协调、催办与收口。

这说明 TriCompany 把“岗位交接”当成治理动作，而不是临时沟通动作。

## 5. source -> governance publish 为什么是员工设计的一部分

传统团队里，员工生命周期常常被人力流程和技术流程割裂：HR 负责入离调转，研发负责代码，运营负责文档，最后没有任何一个地方知道“谁才是真源”。TriCompany 的原创价值之一，就是把员工设计直接纳入 source -> publish -> live -> governance 这条工程链。

这意味着：

- 员工不是抽象人设，而是可发布对象。
- 岗位不是聊天标签，而是可验证契约。
- 交接不是口头吩咐，而是需要 evidence 的 handoff。
- runtime 不是黑盒记忆，而是要么进 support object，要么进 `.tricompany-cognition` 的运行态命名空间。

## 6. 这套设计借鉴了什么，又原创了什么

### 6.1 借鉴的工程思路

TriCompany 不是凭空创造一切，而是组合了多种成熟工程思路：

1. **docs as code**：规则、流程和培训材料都跟随仓库演进。
2. **声明式 manifest / binding**：像基础设施编排一样，把对象集、绑定事实和发布边界显式声明出来。
3. **package / publish 思维**：source truth 不直接等于宿主运行面，中间要经过发布与校验。
4. **审计优先**：所有关键动作都尽量留下 machine-readable 证据。
5. **角色与实例分离**：类似组织建模里的 role / actor 区分，把岗位方法和实例连续性拆开。

### 6.2 TriCompany 的原创组合

更有意思的是它的原创组合方式：

1. 把员工五件套、support object、live entry、runtime state 和 governance 回填串成一条统一链。
2. 把 `role workspace` 与 `employee workspace` 同时引入，避免“岗位知识”和“员工实例记忆”混写。
3. 把 current host 的 support payload 与 source truth 严格分边界，防止宿主目录变成第二真源。
4. 把 training 文档也纳入六层文档基线，承认 onboarding 本身是工程能力的一部分。

## 7. 本章小结

从培训视角看，TriCompany 对“员工”的定义，已经超出了传统 AI agent 的范畴。它把员工设计成一个既能被源码维护、又能被发布、还能在宿主运行和审计的工程对象。只有理解了这一点，你才会明白为什么 TriCompany 的入职、岗位变动、离职和交接都必须走工程化流程：因为这不是在管理一个 prompt，而是在管理一个可持续运行的组织单元。
