## 1. 目标与范围

- 目标：以 TriMetaverse 现有架构为基础，先落地“可编排、可审计、可中断、可恢复”的基础平台。
- 范围：
  - `TriMC` 统一运行面中的服务域任务执行切片与研发工作流切片；当前 shadow 与正式接管都运行在 `copilot` 宿主上，正式宿主切换通过 `TriModel` 的 Provider/Model 配置实现
  - 双域执行（Server domain / Local domain）
  - ToolBus 强制入口与审计落盘
  - 审批、lease、停止语义（safe stop / force stop）
  - 首个 PRD 分支的实施、测试、部署、放行
- 不在范围：多业务产品线功能（内容工厂/社区/NFT/看板等）并行落地。

## 2. 归并说明（与架构文档融合）

- 本 PRD 归并 `arch-storage-migration.md` 的核心工程约束，作为首个可执行产品分支。
- 架构文档保留“平台级长期约束与参考细节”；本 PRD 负责“首分支执行边界与验收口径”。
- 后续新增 PRD 按 Intelligence 决策渐进产生，不回退到上游阶段直接产出。

## 3. 核心能力拆解

### F1：运行面编排与分支执行

- 支持主线阶段：DISCOVERY -> INTELLIGENCE -> DESIGNING。
- 仅 INTELLIGENCE 决策是否新增 PRD 并创建分支。
- 分支固定链路：DESIGNING -> CODING -> VERIFY-INTEGRATION -> REDTEAM -> QA -> DEPLOYMENT -> ASSURANCE。

### F2：双域执行与 ToolBus 强制策略

- Server domain 负责网络/数据库/发布等服务侧能力。
- Local domain 负责代码修改、构建、渲染、自动化等本地能力。
- 所有有副作用调用必须经 ToolBus，拒绝绕过。

### F3：审计、审批与可恢复

- 审批对象统一落库，支持多端 first-wins。
- capability lease 与策略状态可追溯。
- safe stop / force stop 行为可审计，任务可 reconcile。

### F4：首分支交付闭环

- 完成首分支 CODING 到 ASSURANCE 全链路。
- 产出首分支部署资产与测试报告。
- 为后续 PRD 分支复用同一平台底座。

## 4. 非功能需求

- 可观测性：关键阶段、审批、门禁、回流必须可追踪。
- 一致性：状态变更以审计事件为真相源。
- 安全性：高风险动作必须经过审批或策略放行。
- 可恢复性：异常后可从阶段或分支恢复，不破坏已通过分支状态。

## 5. 验收标准

- A1：主线运行可驱动 Intelligence 产生 PRD 并创建分支。
- A2：首分支可完整通过 CODING 至 ASSURANCE。
- A3：至少形成一套可复核的审计证据与门禁报告。
- A4：首分支部署资产可验证，且不影响后续分支并行接入。

## 6. 测试策略

- 功能：分支创建、阶段推进、回流逻辑。
- 集成：Server/Local 双域协同与 ToolBus 强制。
- 红队：高危路径、越权路径、审批绕过测试。
- 放行：ASSURANCE 覆盖漏洞/压力/安全/回归。

## 7. 里程碑（PRD001）

- M1：主线三阶段稳定运行并可触发 Intelligence 决策。
- M2：首分支实施与单元/集成测试通过。
- M3：红队与 QA 达标。
- M4：部署与 ASSURANCE 通过，进入待统一交付状态。

## 8. 交付约定

- 本 PRD 对应“首个分支先跑通”。
- 最终交付仍遵循“全部 PRD 分支完成后统一 DELIVERY”。
- 后续 PRD 在 Intelligence 渐进新增，不影响本 PRD 已完成分支状态。
