## §〇·一句话

将 CEO 治理闭环（裁决→台账→COS 筛→任务书→挂平面→face 路由→树执行→销账→C 面沉淀）标准化为 FADE 体系下的治理闭环实例——**治理循环的每一个环节映射 FADE 管线的一个阶段**，段间交接即角色交接。

## §1·Plan——台账筛选与任务书起草（P）

- **输入**：CEO 裁决产物 + 台账积累（挂账≥1 条即入筛选池）
- **筛选判据**（可自含打包，三条同时满足才入批）：
  1. 边界明——任务范围不含未裁开放项
  2. 验收锚齐——有可判定完成的标准
  3. 无需 CEO 逐步拍板——CEO 只批首尾，不逐条指令
- **输出**：合并同类→起草任务书（树协议七步链格式）
- **角色**：COS
- **例外**：裁决交互链（需要 CEO 实时拍板的）不进本段——人工门，产物事后回灌本段（台账积累）

## §2·Attach——攒批挂平面（A）

- **触发条件**：攒批≥**5 件**（试运行口径，周二/周五触发）或**固定节奏日兜底**（每周三固定挂，防攒不足饥饿）
- **输出**：周工作平面上挂任务书队列（face 路由可拾取形态）
- **角色**：COS

## §3·Commission——face 路由拾取派工（C）

- **face 路由规则**：
  - `server-executable` → 服务域（sg）
  - `local-executable` → 本地域（本机）
- **输出**：拆树→每树一文件夹→daemon 自动拾取（FADE face 路由既有管线，fade-pipeline-architecture 在卷）
- **角色**：DAEMON（自动，无人工）

## §4·Echo——树执行与回声沉淀（E）

- **执行**：树协议七步链——任务书→挂平面→face 路由→自动拾取→拆树→每树一文件夹→节点收口报告
- **收口**：每节点收口报告落树文件夹
- **销账**：台账销账必附树路径+收口报告指针（缺指针不得销账）
- **回声终点**：C 面沉淀（三个面做的每件事最后都沉淀回 C，公司因此长记性——CEO 00:05 立规原文）
- **角色**：DAEMON（自动）+COS（销账）+C 面（沉淀终点）

## §5·必备要素

1. **幂等**：重复拾取同一任务书→同一结果（不做增量——树协议天然幂等）
2. **防重放**：同一任务书 ID 不得入两次平面（挂账台账主键去重）
3. **SLA**：台账筛选段≤1 工作日；攒批段≤触发阈值+1 兜底日；树执行段按任务书 SLA 逐树计
4. **验收锚**：每任务书必附可判定完成的标准（台账筛选判据 2 复用）
5. **与晨检+周迁移两 cron 的邻接关系**：晨检（TriMLC cron 8713）与周平面迁移（河源 TriRMC cron 周日 23:00）均为**独立 cron 事務**，不进 FADE-008 管道——邻接关系=时间窗错开（迁移窗冻结 sg watcher 已有纪律），无管道级依赖
6. **故障恢复语义**：树在即接续（收口报告在树文件夹=进度锚），会话可死（daemon 重启不丢树状态——树文件夹是持久化锚点非会话内存）

## §6·与 007 的邻接关系

007（context-reservoir）=受控压缩机制；008（governance-loop）=治理闭环标准化——两者独立无管道依赖，共用 FADE 编号空间但作用域正交。

## §7·验证与试运行

- **试运行口径**：攒批阈值 5 件/周二·周五触发（BOD 令原文）
- **试运行成功判据**：首批 ≥1 棵树走完七步链+销账附指针+C 面沉淀 = 试运行 PASS
- **试运行失败**：节奏让位质量，调整阈值或分段策略后再试

## §8·干活流程全自动化（候批-催办-审批环自动化；2026-09-22 CEO 批入册；源=七席联审合流稿 v2 七席 7/7 全合零分歧）

> 本章=FADE-008 自我应用：用本管线把本管线自身的候批-催办-审批环自动化。行为纪律正身=D-27（v2 台账同步/v3 催办双型）援引不复制。

### §8.1 机制总图

```
员工席任务至候批态
  →①收口钩子自动写候批信（daemon 模板零 LLM）＋台账同刻挂账（D-27 v2 扩展）
  →②BOD notify 拉取即见（信箱=待办聚合器）
  →③daemon 轮询判定超时（确定性，频次与 token 解耦）→COS 事件出场地催（不靠记忆）
  →④BOD 提醒 CEO（24h hook 注入清单+48h toast 双保险——human-in-session 克制设计）
  →⑤CEO 批→信箱 resolved＋台账销账同刻双写→自动回流开工
```

机制化三件：轮询器自动触发催办＋催办信自动生成＋状态文件自动更新——判定全在 daemon 层，席位只事件出场。

### §8.2 候批信信件规格

信封（notify-mailbox 扩展：action 词汇三增 `submit-approval`/`approve`/`urge`）：`type`（pending-approval/pending-review）｜`source_seat`｜`target`（bod+coo 双投）｜`task_ref`（双向映射键：任务书路径#节点 id 或 LG-xxx）｜`state`（pending-bod/pending-ceo/pending-window）｜`track`（三轨 normal/blocked/red，red 直达轨永不积压按违时处理）｜`waiting_since`（素材齐备时点 T+0 起算锚）｜`sla`（D-27 v3 双型锚载体：hard:<绝对时点>/normal:24h）｜`required`（human 徽标——审批转呈/最终确认/敏感面三类，自动化到此为止不越）｜title+body。

body 四行模板（每槽≤40 字模板值，零 LLM）：`干了什么 → 候谁决什么 → 已候多久（时点+累计） → 批后会怎样+超时会怎样`。

触发/幂等/留痕：生成点=进入候批态瞬间（收口 notify 与候批信同刻双发+台账同刻挂账）；信箱层幂等覆盖；留痕层只追加——六+二字段（任务书号/状态/时点/催办对象/参与席/事由＋首写时点/覆盖计数）；候批时长=已批时点−首写时点；状态跃迁发状态更新信。

### §8.3 三层催办机制

| 层 | 触发 | 执行者 | 时点 |
|---|---|---|---|
| ①催执行席 | 在办超时 | COS 事件出场（轻量注入≤2K） | hard 到点即催／normal 24h；三要素+终点（首催→重申一次→到顶按已收意见先行汇总+缺席标注） |
| ②催审批链 | 候批超时 | daemon 判定→COS 催 BOD | hard 到点即催／normal 沿 CPO 节奏表 T+0→4h→1d→2d→5d；BOD 提醒 CEO：24h 随 CEO 下次消息 hook 注入三行清单＋48h 独立 toast 双保险（不主动打断） |
| ③催督办面 | 升级态+批量积压 | COS→COO | 48h 升 COO→72h 呈 CEO 汇总；积压三档：常规同族≥3/阻塞同族≥2/red 不入档；族级升级=整族决策点+督办红档+晨报瓶颈段 |

配套律：不吵五律＋催办对表三律（催状态不催人/升级不改口/动作即清催）＋超时≠批准（保留条款）＋督办读数两轮挂晨窗/夜航窗＋催办留痕=绩效效率源（一账两用）。

### §8.4 台账-信箱映射与真源（分层双真源定谳）

映射键=`task_ref`；双写同刻（发生侧+裁决侧）；COS/daemon 巡检双态对表（漏挂/漏写/不同步三型差口=告警源）；闭环判据=零差口。

**真源定谳（三席归口闭环：CTO 终裁/CAO 终判接受/COS 执行者接受）**：**分层双真源**——实时态真源=信箱（letter-store 状态机：机器写入/事件驱动/append-only 审计同构）／治理确认态真源=台账（COS 维护治理口径：绩效/督办/呈报引用确认态）。**跨层唯一通道=COS 核认门**（实时态→确认态，核认即定谳；防未核认信息直接引为治理口径的旁路）。COS=确认者非誊抄员。过渡口径（双写零差口）=核认前流转窗口短暂双写合法。CTO 载体裁：notify-mailbox 扩展采纳（独立状态文件否=第三真源风险；台账联动降为映射层非载体）；状态机主链不动（pending→delivered→read→done），候批语义走 payload.type+target 路由。

### §8.5 本地域 human in session

人工保留点六条（清单外一切流程自动化——此即「基本自动」的边界定义）：①CEO 呈批转呈（BOD 质检后）②敏感面操作（Tristaciss/SEC/凭据/PAT）③升级终裁④红线例外批准⑤走查抽验（非作者质检）⑥治理定调（架构级决策）。技术形态：三类信标 `required=human` 徽标，自动化到此不越；三面可见（信箱/toast/台账）现役复用 100%，本地域零新机制。

### §8.6 成本红线（R1-R5）

R1 零巡检原则（判定一律 daemon 确定性代码，严禁定时唤醒 LLM 巡检=唯一翻车形态）/R2 信件模板化零 token/R3 催办 ≤1 轮·周 100 万护栏/R4 BOD 摘要 ≤500 tokens/封/R5 分域计费（服务域模板化零积分；本地域 deepseek 按量照记）。审计红利：状态留痕四件套补齐 LG-034 轮级净耗归集缺口+衍生指标（候批时长/催办响应/收口周期）零成本入绩效观察列。

### §8.7 服务域自动拾取制度化

①拾取器：sg TriMMC daemon cron 扫 FADE face 路由平面新挂任务书→自动拆树开工（值席脚本序固化挂 cron+异常告警）；②候批自动信：收口 notify 追加候批信自动生成；③超时催办器：阈值到→COS 催办事件自动生成（BOD 提醒 CEO 段仍 human——机器只做到「推到 BOD 面前」）。§12.4 衔接：收口 notify=回流常态化触发器，watcher 冻结窗照旧优先；候批/审批状态不进 git 流（正交不缠绕）。

### §8.8 分期

一期（服务域全自动）：letter-store action 扩展+候批信模板+seats.json 补 coo；次落=拾取器 cron 化+超时催办器。二期（本地域基本自动）：随首落自然生效；BOD 提醒 CEO 职责**即日生效**（纯行为纪律零技术件）。三期：七席整合+制度正身（本章入册即完成）。

### §8.9 边界与 D 系整合

敏感面永不自动化（CEO 终裁/SEC/不可逆操作保留人工）；BOD human in session=设计非缺陷；现役机制复用优先（notify/信箱/台账/Sync-Alert 已就位，本命题=编排层整合非新建基础设施）。D 系嵌入点：D-27 v2 台账同步（自动流转每次状态写=台账写）/D-29 无窗直启禁令（自动拾取 job/cron 新增守窗）/D-30 先源后部（信箱/notify/mailbox 扩展脚本入 ops 域真源化）——三纪律原文覆盖自动化场景，无需各自 v 增补（归口裁 2026-09-21）。

## 大白话摘要

把老板说的「裁决→筛选→攒够→挂出来→自动接活→执行→汇报→沉淀知识」这一整个循环，套进公司现有的 FADE 体系框架里。核心变化=以前这些步骤散在各处靠人记，现在写成一个标准流程，任何满足「边界清楚+有验收标准+不用老板逐条盯」的任务都自动走这个管道，不用每次临时想怎么派活。
