## 二、版本路线图

### 2.1 版本编号规则

**采用日期基准版本号（calver）**：`vYYYY.MMDD.N`

| 段 | 含义 | 示例 |
| --- | --- | --- |
| `YYYY` | 年份 | `2026` |
| `MMDD` | 月日 | `0804` |
| `N` | 同日序号（当天第 N 次构建） | `0`, `1`, `2` |

示例：`v2026.0804.0` = 2026年8月4日第1次构建。

Tag 不着急打，视构建质量而定——跑过 Smoke Test 的构建才打 tag。

### 2.2 里程碑（渐进小版本）

```text
v2026.0802.0 ──→ v2026.08XX.0 ──→ ... ──→ 生产稳定
 (v0.3.0)      服务固化+MSI           日常无人值守
```

**不再用大版本号跨越**，改为渐进式小版本迭代。每完成一组可验证的能力跃迁就发布一个小版本。版本号由构建日期自动决定，Tag 不着急打——跑过 Smoke Test 的构建才打 tag。

## 三、双轨互促机制

### 3.1 核心原则

**dev 和 prod 共享同一个 TriMetaverse 工作面**。不是两个独立的工作面，而是同一套 OP 记录、同一套 registry、同一套 agent 定义。区别在于：

| | 开发侧（dev） | 生产侧（prod） |
| --- | --- | --- |
| 分支 | `dev` | `main` |
| 运行环境 | 源码 + CLI（`claude`） | MSI 安装版（`trilc daemon`） |
| 节奏 | 天级迭代 | 周级 Release |
| 谁在用 | AI C-suite + 人类开发者 | 人类用户 + daemon 自治 |
| 代码修改 | 直接编辑文件 | 通过 TriCode 自研能力（或提 Bug 给 dev） |
| 工作面对齐 | 推送到 dev → | ← 生产自研提交 PR |

### 3.2 互促闭环

```text
① 需求/缺陷发现
   生产轨 ──→ 用户反馈 + daemon 运行日志 + cron 执行记录
        │
        ▼
② 实验/开发（dev）
   开发轨 ──→ agent 分析问题 → 生成修复 PR → CI 门禁
        │
        ▼
③ 合入/构建
   dev → main PR → review → merge → 构建 → MSI + ZIP
        │
        ▼
④ 部署/验证（prod）
   生产轨 ──→ trilc update → 下载 → 静默升级 → 稳定性监控
        │
        └──→ 回到 ①
```

### 3.3 生产侧自修复分级

生产环境 TriLC 遇到问题时，按能力分级处理：

| 级别 | 问题类型 | 处理方式 | 示例 |
| --- | --- | --- | --- |
| **L1 自修复** | 配置错误、文件缺失 | TriLC 自行修复并记录日志 | settings.json 丢失 → 重建默认配置 |
| **L2 自研修复** | 代码小改、逻辑修正 | 通过 TriCode 生成 PR → CI → 自动合并 | cron 表达式解析边界情况 |
| **L3 提 Bug** | 基础设施缺陷 | 自动提交 issue 到 dev，等待修复后更新版本 | TriLC daemon 崩溃、NSSM 注册失败 |

### 3.4 生产 TriLC 自身的生产级要求

**生产环境的 TriLC 编排和自研能力也必须是生产级的**——这是一条递归约束：

- TriLC 的 cron 调度自身 bug 不能影响 cron 任务执行
- TriLC 自研循环失败不能破坏已有功能
- 始终保留手动 CLI 作为 fallback（`trilc daemon stop` → 手动操作 → `trilc daemon start`）

### 3.5 互促规则

| 规则 | 说明 |
| --- | --- |
| 所有功能先在 dev 实验 | 生产轨不接受未经 dev 验证的代码 |
| 生产 Bug → dev 修复 → 发版 | 不允许热补丁，必须走 dev→main→构建→安装版更新 全流程 |
| 安装版滞后 ≤ 2 周 | dev 合入的功能最迟 2 周内出现在安装版中 |
| dev/prod 共享工作面 | OP 记录、registry、agent 定义为同一套，两侧共同完善 |
| 生产自研优先，提 Bug 兜底 | 能自己修的自己修，修不了的走正规 Bug 流程 |

### 4.3 核心理念：先有公司，后建项目

```text
创建赛博公司
  └── 定义公司管理体系（模板 + 工作流）
       └── 创建项目 A
       │    └── 从公司员工池分配人力
       │    └── 项目级成本收益核算
       └── 创建项目 B
            └── 从公司员工池分配人力
            └── 项目级成本收益核算
                 │
                 ▼
            多项目核算聚合 → 公司级财务报表
```

**不是先有项目再上岗团队**，而是：

1. 先建立赛博公司（管理体系 + 员工池）
2. 根据业务需求创建项目
3. 从公司员工池中分配人力到各项目
4. 按项目核算成本和收益
5. 多项目聚合形成公司级财务视图

### 4.5 TriCade 项目初始化一致性

TriPilot（VS Code 扩展）和 TriLC（CLI daemon）都可以初始化项目，需确保：

- **幂等性**：已存在的资产不重复创建，已配置的不覆盖
- **统一模板**：两边使用同一套十件套模板（从 `@tricompany/core` 读取）
- **检测优先**：初始化前先扫描 `.claude/`、`docs/` 是否存在，存在则跳过或询问

### 5.2 三个 ADE 含义（仅 ADE-1 是正式定义）

v2 方案中的"保持 ADE 不变"裁定基于错误前提——当时讨论的是 ADE-2 + ADE-3，未引用正式规范。

### 5.3 小乔产品建议

**首选方案**：

| 概念 | 名称 | 理由 |
| --- | --- | --- |
| 执行模式 | **ADE**（不变） | 正式规范 v1.2、17 文件引用、7 CLI 实现 |
| 委托协议 | **ADP**（Agent Delegation Protocol） | Phase 2 未实现，改名成本为零 |

**次选方案**（CEO 坚持时）：执行模式改为 **ADEA**（Agent-Deterministic-Execution-Automation），17 文件需同步更新。

**待 CEO 最终裁决。**

### 5.4 周平面与 ADE 的关系

周平面自动化是 ADE 执行模式的上层用例：Agent（小贾）plan → Deterministic CLI（`weekly_plane.py`）executes → Agent closes。归属 TriLC Cron/Heartbeat 基础设施调度。

### 5.5 共享工作面机制

dev 和 prod 使用**同一个 TriMetaverse 工作面**（同一套 OP 记录），周度平移由 daemon cron 自动触发：

```text
周日 23:00（cron 触发）
  │
  ▼
weekly-plane shift:
  1. 读取当前周 OP 索引（从 docs/workflow/operating-records/）
  2. 计算未闭合项 → 生成 carry-over 清单
  3. 创建新周目录 + OP JSON + 树目录骨架
  4. 通过 localbus 通知小贾审核
  5. 4周/8周预警自动升级（超期 → 标记 → 通知磨人）
  │
  ▼
dev 侧同步：
  - 生产侧平移结果通过 PR 合入 dev（或 dev 自动拉取）
  - dev 侧继续在新周目录下推进开发
```

### 5.3 两侧内容同步规则

| 内容类型 | 主责侧 | 同步方向 |
| --- | --- | --- |
| 周度平移（OP 记录） | prod（daemon 自动执行） | prod → dev（PR） |
| 功能开发（代码） | dev（agent 开发） | dev → prod（MSI 更新） |
| 基础设施 Bug 修复 | dev（小狄+小全） | dev → prod（MSI 更新） |
| 生产自研优化 | prod（TriLC 自研循环） | prod → dev（PR） |
| 十件套/Registry 更新 | dev（小贾+小狄） | dev → prod（安装版同步） |

## 六、区块链时间集成（占位设计）

### 6.1 产品判断

小乔评估结论：

- **FREEZE 区块链集成本身**（TriChain 首版占位，Phase 3+ 之前不做实现）
- **APPROVE 最小接口预留**（当前 cron/heartbeat 实现窗口期，预留成本接近于零）

### 6.3 TimeSource 抽象接口

在 TriLC cron 引擎中预留可替换的时间源接口（**当前仅实现 SystemTimeSource，不改变任何行为**）：

```typescript
interface TimeSource {
  now(): number;                      // 当前时间 (ms since epoch)
  scheduleAt(targetMs: number, fn: () => void): Disposable;
  readonly source: TimeSourceType;    // 'system' | 'blockchain' | 'hybrid'
}
```text

在 TriMC DDL 中追加字段（**向后兼容，默认值正确，迁移成本为零**）：

```sql
ALTER TABLE tmv_task ADD COLUMN time_source VARCHAR(20) DEFAULT 'system';
-- 值域：'system' | 'blockchain' | 'hybrid'
```

## 七、自研循环 v1 技术栈

### 7.1 当前设计

自研循环（`self-dev-loop-design.md`）的架构：

```text
TriLC（agent 执行，产出代码变更）
  → TriCode（编排：diff → branch → commit → PR）
  → OpenCode / Claude Code（代码生成引擎）
  → prod/Wxx 分支（暂存）
  → main PR（review + CI 门禁）
  → TriCade 生产（拉取 + 热更新）
```

### 7.2 v1 验证方案

| 方案 | 说明 |
| --- | --- |
| **A：TriCode + Claude Code/OpenCode** | 完整链路，依赖外部代码生成引擎 |
| **B：TriLC 自身编码能力** | 不依赖外部引擎，测试 TriLC 的 agent loop 直接产出代码变更 |

**v1 优先验证方案 B**（TriLC 自身编码能力），结果标注清楚。如果方案 B 通过，说明 TriLC 的 agent 编码能力已经达到基础自研要求；如果不通过，再引入方案 A 的外部引擎。

无论哪种方案，生成的代码变更必须经过**完整的 CI 门禁**（tsc + test + lint）才能合并。
