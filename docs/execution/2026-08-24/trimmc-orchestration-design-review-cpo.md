## 一、工作循环的产品语义（P1/P2/P3）

### 1.1 场景直译与缺口

把 §一场景 2（cron 工作循环）直译为用户故事：

- US-O1 自主推进：当我不在线时，公司按当前周工作面自主推进**已批准且可执行**的工作，周一回来看到进展而非停滞。
- US-O2 安静守恒：一个周期里我收到的每一封邮件都值得打开。
- US-O3 打扰即重要：只有三类事件即时找我，其余自裁（CEO 常驻授权既定）。
- US-O4 透明可查：我随时能答出"谁在干什么、干到哪一步、产出在哪"。

逐句对照设计原文的缺口：

| 设计原文 | 直译后果 | 缺口 |
| --- | --- | --- |
| "检查当前工作面是否有待办" | 把一切非 done 条目当待办 | G1 → P1（见 1.2） |
| "有则按优先级找 docs/execution 下文档" | 引用了不存在的数据源 | G2 → P3（见 1.4） |
| "无待办发邮件通知 CEO" | 每 tick 一封 | G3 → P2（见 1.3） |
| （未写） | — | G4：缺"做了什么"的可见性闭环故事 → §二承接 |

另注一处衔接：CTO S6 已裁定 watcher 避开周日 23:00-23:59 迁移窗与 disk-hygiene 窗——产品面对应口径是"迁移夜编排静默属预期行为"，须进观测界面与通知文案的预期管理（§二.4），否则 CEO 会把静默误读为宕机。

### 1.2 待办判定的产品定义（P1）

**数据源实盘**（本日实读，2026-W35）：待办信号实际散在三层异构载体：

1. 树层：`trees/<treeId>/tree-op.json`——tree.status（pending/in_progress/done）＋ nodes[].status；
2. 周平面层：`OP-YYYYMM-Wnn-001.json`（activeTrees/nextActions/carry_over 面）＋ `*.unresolved-items.md` §1 活跃表——唯一携带公司级四态（active/frozen/stale-review/closed，术语 owner＝CompanyGovernanceRegistry）的面；
3. CEO 新指令：push 进 `docs/execution/` 的批准计划文档（场景 1）。

**裁定：待办准入三重门（全部满足才计入可执行待办集）**：

1. **状态门**：事项级 status ∈ {active}。frozen/stale-review/closed 一律不算。这不是风格偏好而是治理红线——frozen 是 CEO 冻结裁决的产物（W35 实例：CARRY-20260728-004/006"W35(8/24) CEO 裁决：冻结维持"在册），自动化执行冻结项等于用代码推翻 CEO 裁决；stale-review 处于审查池未定性，同样不得自动接单。
2. **可执行门**：前置条件全满足——依赖节点 done、时间窗到达、审批已获（如 spec §5.1 转正类 CEO 门）、CHO 批次 ref 在册（CTO §5.3 判定规则同源）。时间门反例现成：quadmig-1 Q1-4"影子试跑 ≥2 周（跨周日自然触发窗口）"——30 分钟 tick 循环若把它当普通 pending 节点，会每 tick 重试一件永不动工的活。
3. **域路由门**：仅接服务器域授权清单内事项（写向 operating-records/ 与 execution 域，兼容面冻结清单继续有效）；域外事项只登记不接单。这条不做，编排器第一个周末就会跨域：W35 活跃面唯一 P0 主线 CARRY-20260728-001（trilc TUI 对齐 CC）是本地研发仓/TriLC 侧工作——按现文"pending/in_progress × 优先级"它就是最高优待办，而服务器侧根本没有它的执行面。

**三源合并排序**（K=4、同 tick 至多一棵主线树约束内）：

1. CEO 新指令（插队最高——push 即注入下一 tick 判定，对应 V5 指标）；
2. P0 主线 carry（CEO 已裁决推进类）;
3. 时间门临近项；
4. 其余轻树。

**判定输出是四态而非二值**：可执行待办集 / 等待中（active 但被时间门或审批门阻塞）/ 域外（登记不接）/ 空。"无待办"的正确输出不是一个笼统邮件，而是带原因码的状态（见 1.3 的 N3）。

**断言失败路径**：指针周 ≠ ISO 周（CTO S2）归三类升级之"系统硬约束"，且**连续 2 个 tick 断言失败即自动暂停 watcher**（把 CTO §5.1 编排超时降级扩展到指针断言）——否则周末无人值守时每 30 分钟一封同样的失败邮件，与 P2 同型的狼来了效应。

### 1.3 清零邮件的频率控制（P2）

水平触发（每 tick 发）不可接受：tick=30min 即一天 48 封，一周内 CEO 必然开始不看邮件——届时真正重要的三类升级也会被一起忽略。**通知是稀缺资源，只花在状态变化的边沿上**：

- 待办集指纹（可执行待办集合的稳定 hash）：本 tick 与上一 tick 相同 → 不发；变化才发。
- "全部清零"只在非零→零的**边沿**发一次；持续为零不发。
- 同一升级事件去重（SessionRegistry 记 notified ref），状态实质更新才追加。

**通知词汇表固定六类**（模板化；MVP 做 N1-N3 ＋ E 三类过滤）：

| 代号 | 名称 | 触发 |
| --- | --- | --- |
| N1 | 开工 | 新可执行待办出现且已完成派工（附树 ID 与节点清单） |
| N2 | 清零 | 可执行待办集从非零→零的边沿 |
| N3 | 受阻 | 存在 active 事项但全部不可执行——列阻塞原因码（时间门/审批门/域外/依赖未竟） |
| E1-E3 | 三类升级 | 重大不可逆 / CEO 保留权 / 系统硬约束，即时发 |

N3 同时修正原文案的语义缺口：CEO 实际需要知道的是三种状态——开工了、干完了、卡住了——而不是"没有待办"这个实现细节。

### 1.4 数据契约先行（P3）

设计 §三步骤 1"读盘三件：W35 平面 JSON ＋ **week-plan.md** ＋ SessionRegistry 快照"中的 `week-plan.md` **全仓不存在**（`**/week-plan*` 与 `**/*weekplan*` 双模式零命中，本日扫描）。第二数据源落空；按字面实现会在 M0 直接失败，或逼实现者临场发明平行格式——后者必然制造第二真源。

裁定：待办数据契约按现役真源冻结——`OP-YYYYMM-Wnn-001.json`（树台账＋carry 面）＋ `unresolved-items.md`（唯一携带细粒度状态的活跃表）＋ `trees/*/tree-op.json`（节点级状态）。WorkPlaneWatcher 如需聚合视图，由确定性代码生成**只读快照**（如 `$TRIMC_CONFIG_DIR/orchestrator/todo-snapshot.json`），不新增任何周平面写方——周平面写权单主体纪律不变。若未来确需 week-plan 类聚合文档，走周度平移 SOP 修订另立，不在本方案内顺手造。

## 二、观测体验

### 2.1 会话列表呈现（三层信息架构）

CEO 经 tripilot/trirlc chat 连 daemon 后的第一屏建议分三层：

1. **概览行**（一眼态）：当前 tick 状态（编排运行中/空闲/暂停降级）、活跃树数、本周完成节点数、最近一次通知代号——回答"公司活着吗、在干活吗"。
2. **会话卡片列表**：每卡片＝agent 身份（渲染位角色名）＋所属 treeId＋运行时长＋state（running/idle/stalled/dead）＋最近一句动作摘要。GET /internal/v1/sessions（编排运行视图）与既有 /internal/v1/agents（原始注册表）的双视图字段映射表进设计文档（CTO §1.4.1 已提，此处确认为消费端产品要求）。
3. **详情抽屉**：tail 尾读（n ≤ 200 行限流，S9）＋产物链接。

### 2.2 读到的粒度：三级，默认最省

- **L1 卡片**：registry 字段，零额外成本，默认呈现；
- **L2 尾读**：CEO 主动展开才拉，限流 ≤200 行；
- **L3 产物锚点**：tree-op.json 节点状态＋commit hash 直链——**看结果优先于看过程**。CEO 高频问题其实是"干完了吗、落到哪个 commit"，tail 只是怀疑时的取证工具。L3 让观测从"盯屏"变成"抽查"。

### 2.3 "介入"能力：MVP 明确不做（P4）

CEO 向某会话直接发消息是全新权限面，建议 MVP 不做、M4 后评估。两条独立理由：

1. **机制上当前不成立**：现役唯一跨会话原语是 `--fork-session` 副本语义（CTO B3 实证）——CEO 对员工会话"发消息"实际是对副本说话，回复来自副本，原会话听不到。做一个用户以为在对话、实际在对空气说话的介入按钮，是最差的产品形态。
2. **验证失真**：这套系统的核心命题是无人值守自治（V1 自治率）。一旦提供实时介入，所有失败路径都会退化为 CEO 远程微操，MVP 指标作废，且永远得不到"到底能不能自持"的答案。

**替代方案（MVP 内就有，覆盖介入需求绝大部分）**：

| 诉求 | 权威通道 |
| --- | --- |
| 叫停失控会话 | stop 端点（B2 鉴权整改后，CEO 身份调用） |
| 改变工作方向 | 写 `docs/execution/` 指令 push——下一 tick 判定自然消费且插队最高优先（§一.2 排序第 1） |
| 裁决/解冻/关闭 | 邮件回复＋周平面裁决登记（既有 SOP） |

三者共同保持"编排循环是唯一驱动源"的单主体纪律，且全部自带审计留痕。若未来介入需求真实成立，建议**介入文件化**：CEO 在约定目录写 directive 文件，watcher 高优消费——异步解耦、审计原生、不破坏 fresh-per-tick 语义。

### 2.4 预期管理

- 新鲜度文案：heartbeat 捎带为分钟级延迟（S11），界面标注"数据延迟 ≤N 分钟"，不卖实时直播预期。
- 静默即预期：周日迁移窗与 disk-hygiene 窗编排静默（S6）时，概览行显示"计划内暂停＋下次唤醒时间"，防误读为宕机。

## 三、B4 双轨生命周期的产品确认

**确认接受双轨制**（员工绑树 / 编排绑 tick，CTO §1.3 修订案）：编排会话本就 fresh per tick，绑 tick 是对设计原意的如实表述；绑树反而制造跨 tick 归属歧义。产品面补四个配套件：

1. **跨 tick 连续性的载体是盘，不是记忆**——这正是"知识全在盘上"的本意。三层：
   - 结构化台账（tree-op / OP JSON / SessionRegistry）：事实层，天然跨 tick，无需新增；
   - **tick 交接摘要（关键补强）**：WorkPlaneWatcher 每 tick 用确定性代码（git diff＋Registry 快照，零 LLM）生成 ≤30 行"上一轮快照"注入编排 brief——上 tick 派了哪些树、哪些节点完成、哪些受阻及原因码。上限硬编码防膨胀。这解决"小贾不记得上次"的最痛部分：不需要记住，只需要读到；
   - 周粒度聚合走既有周报螺旋四行段模板（experience/spiral-weekly-template），编排内不重造周报。
2. **人格连续性口径**：向 CEO 明示——服务器侧小贾是**值班实例**，不是同一个记忆体。落地：N/E 邮件与观测界面署名统一为"TriMMC 编排·chief-of-staff 渲染位·tick 实例"形态，防止 CEO 对"连续的小贾"产生错位期待后体验人格断裂。
3. **CHO 台账接口**：CTO §5.3 规定 spawn 必须先有 CHO 批次 ref——编排 tick 实例若无树绑定，逐 tick 审批流水显然荒谬。建议**编排常设编制一次性备案**（standing batch ref），tick 实例一律挂该 ref。此项并入 B4 修订案提交 spec §八修订，勿留白。
4. **验收判据挂钩**："已关树未释放实例数＝0"连续 4 周成立＋编排槽位泄漏＝0，纳入 §六 V 系列门禁。

## 四、R 面移植成熟判据（CEO 指令第 6 条）

移植的本质（依 CEO 两套永续系统架构）：把编排协议从 claude code 特定机制（--fork-session、agents --json、headless 旗标）抽象为 **harness 无关契约**，使 TriRLC/agent-core 可实现同一协议。抽象层未做之前不动工。

**五正向信号（建议全部满足再立项移植树）**：

| # | 信号 | 判据 |
| --- | --- | --- |
| 1 | 稳定性 | 连续 ≥4 个完整周无人值守零人工救火；僵尸回收四形态各自然发生 ≥1 次并被正确处置（不能只有注入测试） |
| 2 | 质量 | 三类产品缺陷（误执行冻结项/跨域接单/错误派工）零发生，或发生但被门禁拦截且根因修复；关树不变量违规＝0 |
| 3 | 成本 | 月度成本连续 ≥2 个月落在 Q-C 批准预算内；单位树完成的 token 成本实测基线在册（R 面 agent-core 对照输入） |
| 4 | 价值 | ≥1 个完整业务周期服务器侧独立交付真实价值（一次完整周日迁移 FADE 收口＋≥1 棵非迁移树端到端完成）——证明循环不止自持，而且产出 |
| 5 | 文档 | 方案总结完成 harness 无关抽象（协议契约＋CC 特性映射表），经一轮 CPO×CTO 联合评审 |

**三反向信号（任一出现即推迟移植评估）**：月度超预算触发降级；连续两周人工干预救火；CEO 反馈升级邮件进入被忽略状态（狼来了实锤）。

## 五、Q-D / Q-E 裁定建议（报 CEO 确认稿）

### Q-D：C-level 随树修订是否同步本地域

**建议：不同步，维持域不对称**（与 CTO §1.3 技术输入一致）。

1. 产品体验：本地域员工是 CEO 直接对话对象（TriCade/trilc chat），人格与上下文连续性是核心体验资产；随树生灭等于杀死该连续性。服务器域无人类实时附着，生灭零体验损失。
2. 架构一致性：CEO 两套永续系统裁决（2026-08-16）——训练系统（服务器域套壳试错）生灭、生产系统（本地域）热备连续；生命周期语义应跟随系统定位，不强行对称。
3. 边界注记：本地域豁免 ≠ 本地域无生命周期治理——本地域沿用 session 管理设计与分身 HC 机制（均已立项），两条线互不并入。

### Q-E：编排会话默认 agent 身份

**建议：显式锚定渲染位 `ceo-chief-of-staff`（小贾）**，采纳 CTO S10 方向，附三条件：

1. **为何是渲染位而非通用 default**：编排职责集（待办复查、周平面维护、carry-over 管理、升级过滤、秘书处协调）与 chief-of-staff 岗位合同高度重合——锚定渲染位使编排实例自动继承岗位 soul 与护栏（不越权做产品终审/工程终审），这是通用 default 给不了的治理属性；三类升级过滤也需要 chief-of-staff 的权限框架与升级链依据。FADE 灌入语义随之成立：渲染位合同更新随 git 同步生效于下一 tick，编排行为与组织合同保持单一真源；通用 default 游离于岗位体系之外，FADE 对它无从灌入。
2. **条件一（署名区隔）**：呼应 §三.2——所有产出标注 tick 实例身份，与人类协作面的小贾区分。
3. **条件二（CHO 备案）**：按 §三.3 常设编制 standing batch ref 入账；spawn 先有批次 ref 再动 Registry 的判定规则对编排槽位同等适用。
4. **条件三（fallback 审计）**：pin 旗标以 M0 步骤 0 核对为准；若 fallback 到 brief 指令＋Agent tool spawn，per-run 日志必须记录实际生效身份——身份锚定失败而日志无痕，等于治理属性静默丢失。
