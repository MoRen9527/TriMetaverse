## 2. 四层资产定位

| 层级 | 位置 | 性质 | 核心规则 |
|------|------|------|----------|
| **模块真源** | `TriCompany/` | 赛博公司研发仓，产品/工程/registry/workflow/execution/training 六层真源 | 默认先查此层；岗位制度、host object 发布链均在此维护 |
| **宿主支撑包** | `TriCompany-host-assets/` | 当前 Copilot 宿主的 runtime、knowledge 与 host-object manifest | 支撑包不承载文档真源；文档真源统一在 `TriCompany/docs/` 维护。不可当成第二真源 |
| **Live 宿主入口** | `TriMetaverse/.github/` | 当前总助 agent 入口、会议 prompt、共享 workflow 入口 | 仅承担 live 入口职责，不是 TriCompany 模块内部研发资产的长期真源 |
| **中央摘要层** | `TriMetaverse/docs/` | 项目级架构说明、模块边界、workflow 协议、registry 索引、运营记录 | 不长期维护 TriCompany 的模块实现细节；不把 support root 物理路径写入中央协议正文 |

### 2.1 物理工作区布局（必读）

TriMetaverse 是公司级 **root workspace**，所有模块仓库是 **独立 Git 仓库**，以同级目录（sibling）方式挂在 TriMetaverse 旁边：

```
<父目录>/
├── TriMetaverse\          ← root workspace（当前工作目录）
├── TriCompany\            ← 独立仓，模块真源所在
├── TriMC\                 ← 独立仓
├── TriDev\                ← 独立仓
├── TriPilot\              ← 独立仓
├── TriAvatar\             ← 独立仓
├── TriStaciss\            ← 独立仓
├── TriLC\                 ← 独立仓
├── TriModel\              ← 独立仓
├── TriSkill\              ← 独立仓
├── TriGateway\            ← 独立仓
├── TriMobile\             ← 独立仓
├── TriMem\                ← 独立仓
├── TriWeb4\               ← 独立仓
├── TriChain\              ← 独立仓
├── TriDeployment\         ← 独立仓
├── TriTest\               ← 独立仓
├── TriTraining\           ← 独立仓
├── Tride\                 ← 独立仓
├── vscodium\              ← 独立仓
└── Tripilot\              ← 独立仓（旧名，待清理）
```

**关键纪律：**
- 模块真源文档（如 `TriCompany/docs/training/`）不在 TriMetaverse 的子目录中，而在同级 `../TriCompany/` 下。
- 搜索模块真源时，必须跨到**兄弟目录**查找，不可只在 TriMetaverse 树内搜索后得出"不存在"的结论。
- **禁止在 TriMetaverse 子目录下创建任何模块仓文件**：所有模块代码、文档、配置和 registry 必须落在该模块的独立仓库中（`../<模块名>/`），绝不在 `TriMetaverse/<模块名>/` 下创建。此规则适用于新建文件、迁移文件和复制文件；唯一的例外是 TriMetaverse 自身的项目级文档（`docs/`、`.github/`、`reference/` 等）。
- **禁止暴露绝对路径**：所有项目文档中不得出现真实文件系统绝对路径（如 `D:\Code\ai\`），统一使用 `<父目录>/`、`../` 或模块相对路径替代。这是永久规则，适用于正式章节、代码示例、PowerShell 命令、JSON 字段、tool output 与 archive 记录。
- 各模块仓路径、层级、分支策略详见 `docs/github-repo-governance.md` §1-§2。

## 3. 关键治理纪律

### 3.1 术语严格模式

- 正式章节（目标、输入、输出、门禁、验收、里程碑、交付清单）中禁止使用非标准别名。
- 术语单一事实源：`docs/workflow/terminology.md`。
- 非标准别名仅允许出现在术语表、变更记录、自检命令示例中。

### 3.2 模块六层文档协同系统

`INTELLIGENCE` 产出的每个已审核 PRD 分支，标准落地面为六层：

| 层级 | 目录 | 承接内容 |
|------|------|----------|
| 产品 | `docs/product/` | PRD 范围、需求、原型映射、产品路线、产品状态 |
| 工程 | `docs/engineering/` | Spec、技术方案、技术路线、技术状态 |
| 执行 | `docs/execution/<prd>/<phase>/` | 分支执行证据（designing → coding → … → assurance） |
| 登记 | `docs/registry/` | 分支稳定结论对 business/product/code 状态的回写 |
| 流程 | `docs/workflow/` | handoff、rollout、迁移、编排和治理机制 |
| 培训 | `docs/training/` | 岗位、模块、代码和流程导读 |

系统不替代十阶段主线；十阶段定义流程状态机和门禁，六层系统定义 PRD 分支落地后文档、执行、培训和收口应放在哪里。

> 注（2026-09-11，LG-034 八件套标准）：模块 `docs/` 标准件套以 `TriCompany/docs/registry/company-governance-state.md`「模块标配」节为唯一真源（八件套：engineering／execution／product 含 prd 子目录／registry／training／workflow／contract／testing；runs 不立）；本节系 PRD 分支落地语境的六层定义，两者语境不同，不一致时以 registry 真源为准。

### 3.3 Registry 命名与更新规则

| Agent 类型 | 命名规范 |
|------------|----------|
| 商业模式资料 | `<Module>BusinessStrategyRegistry` |
| 产品资料 | `<Module>ProductRegistry` |
| 代码资料 | `<Module>CodeRegistry` |
| 公司治理资料 | `CompanyGovernanceRegistry` |

更新规则：
- 只有用户明确要求"记录"或"更新"时才可修改 registry 文档。
- 默认只记录经过确认的状态，不记录聊天中的临时猜测。
- 低成熟模块必须如实标为"占位 / 待初始化"，禁止虚构进度。

### 3.4 文档元信息规范

- **文档元信息**：专指文档在"真源 → support/live → archive"链路中的同步与发布层级元信息。
- **文档同步元信息**：`sourceOfTruth`、`syncMode`、`lastSyncedAt` 字段族。
- **文档头信息**：`版本`、`日期`、`状态`、适用范围等普通头部说明，不与文档元信息混用。

#### 3.4.1 标准文档头正形（2026-10-25 CEO 令定·BOD 拟制；实证源=TriCompany 发布链规范头形+host-assets knowledge frontmatter 族+本仓 §3.4 三字段）

适用域：治理/设计/规范/制度/契约类文档。**豁免域**：operating-records/ 运行记录（周记、拍报、树节点报告）、机器产物（mailbox/manifest/数据 json）、archive 冻结载荷（published-copy-refresh-sop 冻结条款）。

标准头=**头信息三件＋同步元信息三字段＋变更记录表＋关系层（relatedRefs）**（正名注：初版口径「两层六项」指头信息层＋同步元信息层共六字段；层三变更记录表与层四 relatedRefs 增补后，本句为现行全形口径，旧称不再单用）：

**层一·头信息三件**（紧跟标题，列表或 blockquote）：

| 项 | 形态 | 作用 |
|---|---|---|
| 版本 | `V<x>.<y>` **两段式** | 大版本=重大重写；小版本=内容增补。勘误级改动不升版本，由变更记录锚列承载 |
| 日期 | `YYYY-MM-DD 立 · YYYY-MM-DD 末版` | 立稿与末版时点；日期不做版本号（与 lastSyncedAt/updatedAt 职能分离） |
| 状态 | `定稿 / 候批 / 生效 / 已废止`（按需加阶段注） | 生命周期定位；批程纪律：候批禁写成已批/生效，批后据实更新 |

**层二·`## 文档同步元信息` 块**（三基础字段+发布链按需扩充）：

| 字段 | 值域 | 作用 |
|---|---|---|
| sourceOfTruth | 真源路径 | 真源定位；自体真源件写本件路径 |
| syncMode | `manual`（源头直改）/ `sync`（镜像自真源）/ `source-only`（源侧独有无副本） | 同步关系定性；旧值 `static` 归入 `source-only` |
| lastSyncedAt | 同步时点 | 镜像面与真源的最后追平锚 |
| （发布链扩充） | publishedFrom / publishTier / supportPublishedCopy / supportSyncRule | 仅 support 发布链件按需加（TriCompany 发布链先例形） |

**层三·`## 变更记录` 表**（可审计性硬规则）：

- 列式：`| 版本 | 时点 | 锚 | 摘要 |`——一行一版，锚=commit hash 或批令时点，摘要一句。
- **禁止多版合并单行叙述**（可审计性红线；肥单行修订记录=违例形态）。

**版本号形态裁决（2026-10-25 CEO 令授权自定）**：统一 **x.x 两段式**为正形。三段式（x.x.x）不再新用——patch 级勘误的追溯由变更记录「锚」列（commit hash）承担，不重复设版本位；既有三段式件（如 FADE spec v2.0.4）不强制降版，下一版起收敛。日期不做版本号。

**层四·关联关系（relatedRefs）与自动知晓**（2026-10-25 21:5x CEO 追问令增补——三字段只答「我源自谁」，关系与变更传播由本层承载）：

| 字段 | 承载方式 | 作用 |
|---|---|---|
| `dependsOn` | 依赖路径列表（**手工**·少量精） | 我语义依赖谁——其条款变更，本件受影响须复核 |
| `consumers` | 消费方列表（**手工**：门/CLI/管线名或路径） | 谁机器消费我——改本件前先对消费面 |
| 反向索引（谁引用我） | **禁手写·机械构建** | 手写反向索引必腐化（发布面静默滞后先例）；由索引器全量扫出 |

**自动知晓三段**（一处改动 → 多处知晓 → 对齐）：

1. **索引**：`scripts/doc-graph-scan.py` 全仓扫 md 引用关系（头部字段+正文路径引用）→ `docs/doc-graph.json`（每件 cites/citedBy/lastCommit）；巡检慢通道每日一跑；落卷时反查 `--who-cites <path>` 得知会清单。
2. **知会**：改动落卷时将 citedBy 清单写入 commit message/落卷报告；`syncMode=sync` 的镜像件由对应 owner 按 supportSyncRule 追平。
3. **对齐**：索引器比对镜像件 `lastSyncedAt` vs 真源件最后 commit 时点 → 滞后=漂移清单入巡检报（门拦截先例：frontmatter parity 门、derived_drift 计数）。对齐不靠自觉，靠漂移读数。

**关系语义四层**（知晓义务递减）：真源链（sourceOfTruth/supportPublishedCopy——必须追平）> 语义依赖（dependsOn——必须复核）> 机械引用（正文路径提及——知会备查）> 消费面（consumers——破面即修）。

**示范正形**：`docs/execution/weekly-plane-charter-tree-redesign-20261023.md` 头部（版本/日期/状态/同步元信息块/变更记录表五件全齐+relatedRefs 示例）。

### 3.5 真源优先原则（前置核查顺序）

1. 默认先查 `TriCompany/docs/product/PROJECT.md`、`REQUIREMENTS.md`、`STATE.md`。
2. 默认先查 `TriCompany/docs/engineering/DESIGN.md`、`metacognition-architecture.md`。
3. 默认先查 `TriCompany/docs/workflow/` 下的编排、迁移和治理文档。
4. 默认先查 `TriCompany/docs/registry/product-state.md`、`code-state.md`。
5. `TriCompany-host-assets/` 只维护 runtime、knowledge 与 host-object manifest，不承载文档真源；文档真源统一在 `TriCompany/docs/`。

### 3.6 开源吸收链

统一路径：`TriMetaverse/reference/ → 模块/vendor/ → 模块真实实现`

核心约束：
- reference 只用于阅读、对照、拆解、留档，不得直接当作本地运行时真源。
- vendor 默认优先保持上游原貌，用于从最小版跑通到完整复刻之间的持续参考。
- 不得跳过 reference 直接散改上游代码，也不得把 vendor 误写成自研主干。
- 如开源吸收动作会引入新的长期主模块或改变既有模块边界，必须先咨询 `BusinessStrategy`。

### 3.7 模块边界变动规则

- 涉及新的长期主模块、既有模块边界变化或正式宿主边界变化时，必须先咨询 `BusinessStrategy` 做范围裁决。
- 在中央真源口径更新前，不得把边界变化写成既成事实。
- 模块级 `business-state.md` 是同模块 `product-state.md` 与 `code-state.md` 的业务上游约束；若中央 `BusinessStrategy` 与模块 business registry 冲突，先以中央边界裁决为准。
