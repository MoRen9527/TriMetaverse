## 1. 文档定位

本文档是本轮“中央 registry 先行 -> 模块逐仓摸底 -> 教程化沉淀 -> 长期分批续跑”的主执行锚点。

当前文件是 TriMetaverse 中央 registry 摸底与教程化推进计划的本地真源，承担的是执行计划、波次管理和中央收口锚点职责；模块事实、岗位规则和 source-side owner 边界仍以 TriCompany 与各模块 registry 真源为准。

目标不是一次性把所有模块写完，而是建立一个可以长期、分批、不间断续跑的总计划文档。后续每完成一个模块，都在本文件更新状态和下一步入口，再进入下一个模块，避免上下文断档、批次混乱和口径漂移。

## 2. 本轮总目标

- 先把中央模块主旨、命名和边界真源钉住，再开始模块级扫描。
- 为每个模块分别产出产品侧摸底、代码侧摸底、gap 清单和后续计划。
- 在模块事实摸底完成后，为每个模块补一份“小白级但事实准确”的教程化说明文档。
- 并行收口中央 registry 的文档治理规范：模块 `Product Registry` 按业务切面拆分多文档维护，模块 `Code Registry` 对每条业务走线提供教学级代码文档。
- 自动化路径先走 `Prompt 先行`，首批自动动作只生成报告和计划，不直接批量改代码。

## 3. 当前硬约束

- 第一批只覆盖现役代码模块，不把空模块 / 占位模块混入首批深度扫描。
- 中央文档、registry、计划文档统一使用 `TriGateway` 作为规范名；规范目录已修正为 `TriGateway/`，历史路径 `TriGatway/` 作为兼容别名保留，并继续单列 alias 风险直到引用全部收敛。
- `example`、`sample`、`template`、`fixture` 文件只可作为模板和样板，不可单独当成模块事实证据。
- 模块教程的详细程度可以参考 `TriStaciss/docs/React + FastAPI 登录流程完整指南.md` 的展开方式，但只能参考叙事深度与拆解方法，不能复用其中事实结论。

## 4. 产出物标准

每个模块最终至少产出 4 类结果：

| 产出 | 目标 | 约束 |
| --- | --- | --- |
| 中央 registry 对齐项 | 让中央 `BusinessStrategy`、模块 map、边界文档与模块现状保持一致 | 只写中央确认过的边界，不凭猜测补事实 |
| 产品侧摸底文档 | 说明模块定位、用户价值、当前能力、待补功能、非目标和阶段成熟度 | 以模块 `AGENTS.md`、`README.md`、产品文档为主，不把代码猜测当产品事实 |
| 代码侧摸底文档 | 说明代码结构、入口、关键包、运行链路、冗余区、风险点和测试状态 | 以真实目录树、源码、脚本、测试配置为准 |
| 教程化文档 | 让产品和开发新人都能完整理解模块，从环境配置一路看到启动、调用流、代码索引和风险点 | 必须重新核对正确性，不允许照搬参考文档内容 |

## 5. 教程文档写作标准

教程文档统一采用“总 -> 分 -> 总”的叙事结构，面向“小白级产品 + 开发”双读者。

每份教程至少覆盖以下内容：

1. 模块是什么：一句话主旨、和其他模块的边界、当前成熟度。
2. 如何启动：环境准备、依赖安装、启动命令、配置入口、常见端口或宿主要求。
3. 启动后发生什么：从入口到核心业务流 / 调用流 / 数据流的逐段解释。
4. 涉及哪些实现面：关键目录、关键包、关键对象、关键协议、关键脚本。
5. 代码与配置索引：新人第一次读代码应先看哪些文件、按什么顺序看。
6. 当前缺口：未实现功能、冗余代码、待收敛文档、测试缺口、命名风险、成熟度风险。
7. 最终总结：这个模块当前能做什么、还不能做什么、下一个动作是什么。

如果模块存在协议、数据包、任务对象、调度链、宿主切换链、Provider 路由链，也必须写清“请求从哪里进、到哪里转、在哪里落盘、由谁负责回写”。

## 5.1 并行任务：教学级文档治理规范收口

除按模块逐仓摸底外，本轮再新增一条长期并行任务：把中央 registry 的文档治理规范钉住，并在后续每个模块执行时一并检查。

这条并行任务固定五条要求：

1. 模块 `Product Registry` 必须按业务角度拆分维护多份文档，分别承接业务目标、能力边界、用户价值、成熟度和阶段状态。
2. 模块 `Code Registry` 必须按每个业务走线补教学级代码文档，不怕展开，不怕细，必要时逐段到逐行解释入口、调用流、配置流、状态流和关键对象。
3. 所有代码设计、实现、修改和维护，都必须同步回写代码文档；不能让源码变化脱离教学级文档沉淀。
4. 各业务线教学文档都必须写清模块内端到端链路：输入的生产者是谁，输出的消费者是谁；如果不是数据业务流，也要写清等同或类似的端到端输入方、处理方和消费方关系。
5. CodeGraph 仅作为各模块 `Code Registry` 的本地辅助索引；先随现役代码模块按波次试点，不对低成熟 / 占位模块做强制初始化。
6. 对现役代码模块做入口、调用链、关键对象和依赖摸底时，默认先用 CodeGraph，再进入定点源码阅读和人工收口；只有 literal text 检索或索引缺口场景才退回全文搜索优先。

执行层含义是：后续每次做模块摸底、设计、整改或重构时，不只产出“结论文档”，还要同步评估该模块是否已经具备让小白快速读懂业务结构和代码调用流程的文档面。

## 6. 执行波次

### Wave 0：中央真源钉住

目标：先把模块主旨、边界、命名和 alias 风险写到中央文档里。

本次已落动作：

- 在 `docs/三元宇宙架构与模块说明.md` 增补模块主旨与 `TriGateway` 命名规则。
- 在 `docs/registry/business-strategy-module-map.md` 补入 `TriCompany`、`TriDev`、`TriGateway`，并显式记录 alias 风险。
- 在 `docs/registry/business-strategy-boundaries.md` 同步补齐边界基线。
- 将物理目录修正为 `TriGateway/`，并保留 `TriGatway/` 兼容别名以支撑平滑迁移。

### Wave 1：中央 registry 总收口

目标：把中央层先梳理干净，再下沉到模块层。

执行项：

- 核对中央模块 map、边界文档、成熟度状态和 source-of-truth 路径是否一致。
- 标出所有“中央写法和模块现实不一致”的地方。
- 明确哪些模块可以进入现役扫描，哪些模块只能写占位结论。

### Wave 2：现役代码模块首批摸底

首批顺序按“先从更容易形成业务闭环与教程样板的模块切入，再回到运行核心与工具链”推进：

| 顺序 | 模块 | 本轮目标 |
| --- | --- | --- |
| 1 | `TriStaciss` | 先摸清 API 平台、多 provider 路由、前后端联动，并形成首份教程化样板 |
| 2 | `TriMC` | 再回到运行核心，摸清 runtime 切片、planner/context/tools/模型调用链 |
| 3 | `Tride` | 摸清 CLI/runtime/SDK/orchestration 与 PC 软件开发工具层 |
| 4 | `TriPilot` | 摸清 VS Code 扩展 / webview 用户入口与交互层 |
| 5 | `vscodium` | 摸清 IDE 宿主层与本地定制 vs upstream 边界 |
| 6 | `TriAvatar` | 摸清 Web 入口、前端结构和未来入口规划边界 |
| 7 | `TriLC` | 摸清本地域控制器、本地 runtime、tool bus |
| 8 | `TriDeployment` | 摸清部署资产、模板、GitOps 与交付完备性 |
| 9 | `TriTest` | 摸清测试资产、模板、报告与门禁能力 |
| 10 | `TriCompany` | 摸清赛博公司研发编排资产、Copilot 宿主资产与 Hermes 融合草案 |

CodeGraph 试点随 Wave 2 执行：仅在模块根目录按需初始化，并排除 `reference/`、`vendor/`、依赖目录、构建产物、缓存、生成物和 secrets；`.codegraph/` 只作为本地缓存，不作为模块真源提交。模块 `CodeRegistry` 只接收扫描摘要、commit / 版本锚点、主要入口、调用链发现、排除规则和待确认缺口。

### Wave 3：低成熟 / 占位模块梳理

第二批处理 `TriDev`、`TriModel`、`TriSkill`、`TriGateway`、`TriMobile`、`TriMem`、`TriWeb4`、`TriChain`。

这一批的目标不是伪造实现，而是明确：

- 当前是空模块、半成品还是已有局部资产。
- 期望功能主旨是什么。
- 现阶段缺的是真源文档、README、代码骨架，还是执行 owner。
- 暂缓 CodeGraph 初始化，避免把空目录、占位 README 或未确认边界误登记为代码事实。

### Wave 4：自动化与定期扫描

在前两批手工口径稳定后，再补自动化：

- `Prompt 先行`：先做模块扫描 prompt 套件。
- `只生成报告和计划`：先不做自动写回代码。
- 等模块级文档结构稳定后，再评估 resident / cron / cloud 批处理入口。

## 7. 单模块执行循环

每个模块都按同一个循环执行：

1. 读取中央主旨与边界真源。
2. 读取模块 `AGENTS.md`、`README.md`、`docs/registry/`、核心源码目录。
3. 输出产品侧摸底结论。
4. 输出代码侧摸底结论。
5. 做中央 fan-in，更新中央 registry 对齐项。
6. 再写模块教程文档。
7. 回到本计划文档更新状态，切换到下一个模块。

## 8. 续跑规则

- 任何新批次开始前，先更新本文件的状态表和“下一模块”字段。
- 同一时间只允许一个模块处于 `in-progress`，避免跨模块事实串线。
- 若扫描中发现中央模块主旨写错，先回中央文档修正，再继续模块扫描。
- 若模块真实资料不足，必须明确标注缺口，不得自行补齐不存在的能力。

## 10. 下一步

按当前节奏，下一动作固定为：

1. 继续推进中央 registry 其余模块的一致性复核与补齐。
2. 回到 `TriStaciss`，继续做深入摸底、细化问题和证据收口。
3. 在后续每个模块推进时，并行检查该模块的 `Product Registry` 是否已按业务切面拆文档，以及 `Code Registry` 是否已补教学级代码走线文档；现役代码模块可同步试点本地 CodeGraph 索引摘要。
4. `TriStaciss` 细化完成后，先回头确认 `TriMC` 的收口状态。
5. CodeGraph Wave 2 现役代码模块试点可收口；下一步只在出现真实源码骨架、parser 可覆盖文件或明确 CTO 技术线要求时，再评估 `TriWeb4`、`TriChain`、`TriMobile`、`TriMem`、`TriDev` 等低成熟 / 占位模块，不强制初始化。
6. `Tride` 必须在 `TriMC` 已确认且用户明确确认“开始tride”后再启动，当前不自动切换。
