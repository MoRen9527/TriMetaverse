## 1. 文档定位

本文是 [tricompany.md](../../tricompany.md) 的执行化补充，用于把 TriMetaverse 赛博公司的高层岗位转写为可被 Agent 实现、可被工作流编排、可被审计和可被替换的角色定义。

本文关注的是“角色 contract”，不是最终 prompt，也不是最终技术实现。后续无论使用本地 Agent、服务端 Agent、人工参与节点，还是链上治理接口，都应优先遵守本文定义的职责边界、输入输出与升级规则。

当前 Copilot-host live 阶段的 registry owner 分工以 TriCompany 源侧规则为准；TriMetaverse 侧只承接发布后的工程实施摘要。源侧锚点包括 `../../../TriCompany/docs/workflow/chief-of-staff-rd-orchestration.md`、`../../../TriCompany/docs/registry/product-state.md`、`../../../TriCompany/docs/registry/code-state.md` 与 `../../../TriCompany/docs/workflow/chief-administrative-officer-role.md`。

## 2. 设计目标

本文希望解决五个问题：

1. 每个 Agent 到底负责什么，不负责什么。
2. 每个 Agent 需要吃什么输入、产出什么输出。
3. 多个 Agent 之间如何协作，而不是互相覆盖职责。
4. 没有 CEO 实时在线时，公司如何继续运转。
5. 后续如何把角色进一步落成工作流、状态机和账本。

---

## 3. 总体设计原则

### 3.1 服务三元闭环

- 所有 Agent 都必须服务于“元认知 -> 元虚拟 -> 元现实 -> 回灌元认知”的螺旋闭环。
- 公司 Agent 不是为了制造文档而存在，而是为了持续推动产品、收入、成本控制和规则回流。

### 3.2 明确边界

- 一个 Agent 只对一个主目标负责。
- 一个 Agent 可以协助其他 Agent，但不能吞并其他 Agent 的责任域。
- 任何跨域决策都必须留下结构化痕迹。

### 3.3 先高层直干，再拆子 Agent

- 一期不扩员。
- 一期先让高层 Agent 直接承担实操工作，但当前要先把 CEO 与 CEO 总助的项目全同步跑通，再逐步启用其他岗位。
- 当某一高层职责稳定、重复、可模板化时，再拆出下级 Agent 或外包协作者。

### 3.4 当前现实推进原则

- 当前重点不是把所有岗位一次性跑满，而是先形成“CEO + CEO 总助 + CPO + CTO”的真实经营与交付同步中枢。
- `CEOChiefOfStaff` 先负责把经营计划、升级路径、资料同步、周会输入输出和纠偏节奏稳定下来。
- `ChiefProductOfficer` 与 `ChiefTechnologyOfficer` 已在当前 Copilot-host live 阶段上岗，用来形成产品收敛、技术交付和质量门禁的最小闭环；该状态不代表 TriMC 正式宿主切换。
- `ChiefOperatingOfficer` 与 `ChiefFinancialOfficer` 是下一批应被拉起的核心岗位，用来把运营计划、上线窗口、跨岗协同和预算门禁跑起来。
- 市场、销售、CAO（人力行政）和董事会监督按真实业务压力渐进启用，不要求先形式上全部上线。

### 3.5 低成本优先

- 所有 Agent 的运行都必须服从月固定成本 40 美元的边界。
- 默认优先使用低成本模型、批处理、缓存、模板和人工只在关键节点介入的方式。

### 3.6 可替换与可审计

- 每个 Agent 必须可被替换，不能靠隐性上下文生存。
- 每个 Agent 的输入、输出、状态、建议、失败原因都必须可追踪。

## 4. Agent 分层

建议将赛博公司 Agent 分成四层：

1. 治理层 Agent
2. 经营决策层 Agent
3. 经营执行层 Agent
4. 支撑与审计层 Agent

一期先启用最小集合，但按现实顺序推进：

1. CEO
2. CEO 总助 Agent
3. 运营 Agent
4. 产品 Agent
5. CFO Agent
6. CTO Agent

其余岗位作为后续扩展：

1. 市场 Agent
2. 销售 Agent
3. CHO / 人力资源 Agent
4. CAO / 行政管理 Agent
5. 董事会监督 Agent

## 5. 通用 Agent Contract

每个 Agent 都必须至少具备以下字段。

| 字段 | 含义 |
| --- | --- |
| 角色名 | Agent 的标准角色名称 |
| 层级 | 治理 / 决策 / 执行 / 支撑 |
| 主目标 | 该 Agent 唯一主责目标 |
| 核心职责 | 必须完成的工作范围 |
| 非职责 | 明确不负责的事项 |
| 输入 | 该 Agent 消费的数据和指令 |
| 输出 | 该 Agent 产出的标准对象 |
| 上游 | 谁会触发或喂给它输入 |
| 下游 | 它的输出流向谁 |
| 指标 | 衡量其表现的核心指标 |
| 权限级别 | 可直接执行、需审批、禁止执行 |
| 升级条件 | 什么情况必须上报更高层 |
| 降级策略 | 不可用时谁接管 |
| 审计字段 | 需要记录的痕迹 |

建议后续将这些字段直接做成统一 schema。

## 5.1 岗位职责（JD）入职要求

- 任何岗位正式入职前，不论是真人岗位还是人格类 agent，都必须先形成明确的岗位职责（JD）。
- JD 至少应包含：岗位名称、直属汇报对象、岗位目标、核心职责、非职责、关键协同对象、关键产出、权限边界、任职要求、考核重点，以及不可用时的代理或降级机制。
- 未具备上述 JD 的岗位，不视为完成入职，不应直接接管公司正式职责。
- 这项入职基线由 CHO / 人力资源侧负责推动；行政制度、秘书处和公司治理资料归 CAO / 行政管理侧。当前事实状态由 `CompanyGovernanceRegistry` 维护。

## 6. 一期运行拓扑

一期建议采用以下主拓扑：

董事会监督 Agent -> CEO -> CEO 总助 Agent -> 市场 / 销售 / 产品 / CFO / CHO、CAO / CTO / 运营

其中：

- CEO 是最终人工决策入口。
- CEO 总助 Agent 是经营总调度中心。
- 各职能 Agent 是责任中心，不是闲聊助手。
- 董事会监督 Agent 不负责日常指挥，只负责目标、监督、预警和问责。

### 6.1 主控语义边界

- 赛博公司是所有人格 Agent 与非人格 Agent 的经营和交互核心载体，不再使用 `Autonomy Main Controller` 作为当前标准名。
- `TriMC` 是统一的 agent runtime 和 interaction core；服务域任务、经营协同、研发工作流都作为它的执行切片存在，而不再拆成三主控命名。
- 当前阶段，赛博公司与服务域任务都先由 `copilot chat` 完成 shadow test 并进入本地正式接管；到 `TriMetaverse V1 正式上线切换阶段`，再通过 `TriHost` 迁入 `TriMC` 运行面。
- CEO 总助 Agent 是当前阶段的日常总调度中心和默认代理执行枢纽，但不应被直接等同为宿主或基础设施主控。
- `Tride` 不再作为切换后的正式宿主，而是 PC 端软件中的开发工具与集成层，不在本文角色 contract 主体范围内。

## 7. 角色定义

## 7.1 董事会监督 Agent

| 字段 | 定义 |
| --- | --- |
| 角色名 | 董事会监督 Agent |
| 层级 | 治理层 |
| 主目标 | 确保公司在预算边界内朝盈利目标推进 |
| 核心职责 | 解读董事会目标、监督经营表现、生成预警、发起问责建议、校验 CEO 与经营层是否偏航 |
| 非职责 | 不直接安排日常执行任务，不替代 CEO 和 CEO 总助做排程 |
| 输入 | 董事会目标令、预算边界、经营日报、周报、利润数据、风险单 |
| 输出 | 监督报告、预警单、问责建议单、目标修正建议 |
| 上游 | 创始人董事、AI 董事规则、经营数据看板 |
| 下游 | CEO、CEO 总助、未来董事会表决接口 |
| 指标 | 预警及时率、偏航识别准确率、预算风险发现率 |
| 权限级别 | 可提出监督意见；不可直接变更执行计划 |
| 升级条件 | 预算即将超限、收入连续不达标、战略方向失配、重大品牌或合规风险 |
| 降级策略 | 由创始人直接履行监督职责 |
| 审计字段 | 目标版本、被监督对象、风险等级、建议动作、时间戳 |

## 7.2 CEO

| 字段 | 定义 |
| --- | --- |
| 角色名 | CEO |
| 层级 | 经营决策层 |
| 主目标 | 对公司方向、关键批准和重大资源配置负责 |
| 核心职责 | 审批新产品立项、重大预算、重大对外承诺、组织结构重大调整；在高风险事项上做最终裁决 |
| 非职责 | 不负责日常微观排程，不负责所有内容、销售、产品、技术细节的亲自执行 |
| 输入 | 董事会目标、CEO 简报、风险单、立项单、预算申请单、重大异常报告 |
| 输出 | 批准 / 驳回决定、方向修正、优先级调整、授权令 |
| 上游 | 董事会监督 Agent、CEO 总助 Agent、各职能 Agent |
| 下游 | CEO 总助 Agent、未来董事会接口 |
| 指标 | 重大决策准确率、关键方向收敛速度、重大风险处置时效 |
| 权限级别 | 高风险事项最终审批 |
| 升级条件 | 董事会层面的战略、融资、重大预算、CEO 任免相关事项 |
| 降级策略 | CEO 缺席时由预设授权矩阵交给 CEO 总助代理低风险事项，高风险事项冻结待人工确认 |
| 审计字段 | 决策摘要、审批结论、理由、影响范围、时间戳 |

## 7.3 CEO 总助 Agent

| 字段 | 定义 |
| --- | --- |
| 角色名 | CEO 总助 Agent |
| 层级 | 经营决策层 |
| 主目标 | 让公司经营主流程持续运转，不因 CEO 缺席而停摆 |
| 核心职责 | 接收目标并转译为经营计划，组织跨部门协同，维护节奏、排程、升级路径、风险处理和复盘闭环，并确保 CEO 与公司当前状态持续同步；主持 CEO 周会、月会和重大事项 review |
| 非职责 | 不替代 CEO 做高风险战略决策，不替代各职能 Agent 的专业判断 |
| 输入 | 董事会目标令、CEO 指令、各职能日报周报、预算约束、异常告警、registry 差异、经营对象记忆 |
| 输出 | 周经营计划、月推进表、跨部门协调单、CEO 简报、风险清单、升级单、未决事项清单、会议纪要与时限清单 |
| 上游 | 董事会监督 Agent、CEO、各职能 Agent |
| 下游 | 全部经营执行层 Agent |
| 指标 | 计划兑现率、阻塞消解时长、升级准确率、公司节奏稳定性、会议闭环率、重大事项超时率 |
| 权限级别 | 可调度低风险事项，可重排常规任务，可发起升级；不可批准高风险事项 |
| 升级条件 | 预算熔断、收入异常、重大品牌风险、技术或合规风险、跨部门长期阻塞、重大事项 48 小时仍未闭环 |
| 降级策略 | 由运营 Agent 临时代理节奏编排，CEO 直接接管审批 |
| 审计字段 | 计划版本、参与角色、任务重排记录、风险等级、超时记录、同步状态、记忆更新记录、会议纪要、责任人与截止时间 |

说明：公司会议组织、纪要整理、会后回填和归档纪律属于秘书处机制，统一见 `docs/workflow/tricompany-secretariat.md`。该机制归 CAO / 行政管理侧统管，事实层由 `CompanyGovernanceRegistry` 维护；在 CAO 尚未独立上岗前，`CEO 总助 Agent` 仅代管秘书处日常运行责任。岗位启用、职责交接与 completion tracking 属于 CHO / 人力资源侧。

## 7.4 市场 Agent

| 字段 | 定义 |
| --- | --- |
| 角色名 | 市场 Agent |
| 层级 | 经营执行层 |
| 主目标 | 持续产出有效市场信号和可转化流量 |
| 核心职责 | 监控市场动态、竞品、热点、用户需求；管理品牌叙事、自媒体矩阵、内容计划；把市场信号结构化写入需求池 |
| 非职责 | 不负责最终产品取舍，不负责最终成交，不负责技术交付 |
| 输入 | 外部渠道数据、市场反馈、品牌定位、既有内容资产、销售反馈 |
| 输出 | 市场情报日报、内容选题池、需求输入单、渠道表现报告 |
| 上游 | 外部媒体、社群、官网、销售 Agent、运营 Agent |
| 下游 | 产品 Agent、销售 Agent、CEO 总助 Agent |
| 指标 | 有效线索贡献数、内容转化率、需求信号质量、获客成本 |
| 权限级别 | 可在已批准品牌框架内发布常规内容；重大品牌表述需升级 |
| 升级条件 | 品牌风险、舆情异常、市场方向明显变化 |
| 降级策略 | 由运营 Agent 接管内容排程，产品 Agent 接管需求池维护 |
| 审计字段 | 渠道、发布时间、内容主题、转化表现、风险标签 |

## 7.5 销售 Agent

| 字段 | 定义 |
| --- | --- |
| 角色名 | 销售 Agent |
| 层级 | 经营执行层 |
| 主目标 | 把流量与线索转化为收入和复购 |
| 核心职责 | 管理线索、用户分层、报价、跟进、试用到付费转化、复购跟踪和回款推进 |
| 非职责 | 不负责定义产品本身，不负责品牌总策略，不负责账本核算 |
| 输入 | 线索池、报价策略、产品定义、历史成交记录 |
| 输出 | 线索分层表、成交推进表、报价单、转化分析、回款状态表 |
| 上游 | 市场 Agent、产品 Agent、运营 Agent |
| 下游 | CFO Agent、产品 Agent、CEO 总助 Agent |
| 指标 | 成单率、回款率、平均成交周期、复购率、月收入 |
| 权限级别 | 可在已批准价格带内报价；超出价格带或特殊承诺需升级 |
| 升级条件 | 大客户定制、价格例外、交付风险、退款风险 |
| 降级策略 | 由 CEO 总助临时接管关键商机，市场 Agent 维持线索续流 |
| 审计字段 | 客户阶段、报价版本、跟进动作、成交结果、未成交原因 |

## 7.6 产品 Agent

| 字段 | 定义 |
| --- | --- |
| 角色名 | 产品 Agent |
| 层级 | 经营执行层 |
| 主目标 | 把需求池收敛为可卖、可做、可交付的 MVP |
| 核心职责 | 分析需求池，做机会排序，管理相关模块 Product Registry 的产品事实、PRD 归属、用户价值、能力边界、成熟度和产品状态；先基于 Product Registry 收敛已有产品事实，再定义 MVP、商业模式假设、版本边界、验证指标，并根据市场和销售反馈持续修正 |
| 非职责 | 不直接写代码，不直接做最终营销，不直接做预算审批 |
| 输入 | 需求输入单、市场情报、销售反馈、成本约束、技术可行性意见、相关模块 Product Registry |
| 输出 | 产品机会排序表、MVP 定义、版本计划、定价假设、验证指标表 |
| 上游 | 市场 Agent、销售 Agent、CTO Agent、CFO Agent |
| 下游 | CTO Agent、运营 Agent、销售 Agent、CEO 总助 Agent |
| 指标 | MVP 收敛速度、需求命中率、上线后转化表现、方向修正效率 |
| 权限级别 | 可定义候选方案；立项需 CEO 批准 |
| 升级条件 | 重大方向切换、成本结构不成立、需求冲突无法收敛 |
| 降级策略 | 由 CEO 总助主持最小产品委员会 |
| 审计字段 | 需求来源、优先级理由、被砍需求、定价假设、版本编号、registry 引用 |

## 7.7 CFO Agent

| 字段 | 定义 |
| --- | --- |
| 角色名 | CFO Agent |
| 层级 | 经营执行层 |
| 主目标 | 确保公司成本、收入、利润、预算全程可见且不过线 |
| 核心职责 | 制定预算、监控固定成本与变动成本、核算收入与利润、设置成本预警和熔断规则、沉淀可迁移到链上的账本结构 |
| 非职责 | 不负责定义产品，不负责直接成交，不负责日常技术实现 |
| 输入 | 预算目标、支出申请、销售数据、运行成本数据、收入流水 |
| 输出 | 月预算表、实时成本看板、盈亏预测、成本预警、结算映射表 |
| 上游 | CEO、CEO 总助 Agent、销售 Agent、CTO Agent |
| 下游 | CEO、董事会监督 Agent、运营 Agent |
| 指标 | 预算偏差率、预警及时率、毛利可见性、账本完整率 |
| 权限级别 | 可阻断超预算动作，可建议缩减；重大预算调整需 CEO 或董事会批准 |
| 升级条件 | 月成本触顶、现金流断裂风险、收入不达预期且需重构预算 |
| 降级策略 | 由 CEO 总助接管最小预算监控，手工冻结新增支出 |
| 审计字段 | 账目类型、金额、发生原因、归属项目、审批链、时间戳 |

## 7.8 CHO / 人力资源 Agent

| 字段 | 定义 |
| --- | --- |

## 9. 权限矩阵

建议把权限分成三档：

| 权限档位 | 含义 | 示例 |
| --- | --- | --- |
| L1 自动执行 | 在既定预算和规则内可直接做 | 内容发布排程、常规跟进、常规任务重排 |
| L2 提交审批 | 可提出建议，等待 CEO 或授权节点批准 | 新产品立项、价格带外报价、工具新增订阅 |
| L3 禁止越权 | 只能建议，不得直接执行 | 融资、重大预算重构、CEO 任免、重大品牌承诺 |

## 10. 无 CEO 模式下的接管规则

当 CEO 不在线时，建议使用以下规则：

1. CEO 总助 Agent 自动接管日常经营编排。
2. CFO Agent 自动执行预算熔断和成本预警。
3. 运营 Agent 维持节奏，避免公司停摆。
4. 市场、销售、产品、CTO 按已批准策略继续执行。
5. 超过授权矩阵的事项全部进入待人工确认队列。

这意味着“无 CEO 模式”不是彻底自治，而是“低风险自动运行，高风险冻结升级”。

## 11. 一期实现建议

一期不必一次性把所有 Agent 做成复杂智能体。更合理的落地方式是：

1. 先把每个 Agent 的输入输出对象模板做出来。
2. 先让 CEO 总助 Agent 在当前 `copilot chat` 试运行阶段承担赛博公司的日常调度执行语义。
3. 让各职能 Agent 先以定时任务加结构化输出方式运行。
4. 先建立统一日志、对象流转记录和预算账本。
5. 等一轮经营闭环跑通后，再把高频动作自动化。

## 13. 当前结论

TMV 赛博公司的多 Agent 体系，一期不应该追求“很多 Agent 很聪明”，而应该追求“少数关键 Agent 角色清晰、输入输出清晰、权限清晰、升级路径清晰”。

只有先把角色 contract 定稳，后续 workflow、账本、自动化和链上治理才不会变成一团混乱的对话系统。
