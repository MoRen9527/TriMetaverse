## 1. 版本策略

### 1.1 版本独立性

- TriMetaverse 是独立 git 仓，**自身文件变动 → 自身版本号**。
- 子模块（TriCompany、TriMC、TriStaciss、TriAvatar 等）各为独立 git 仓，各自维护独立版本号。
- **子模块版本变动不影响 TriMetaverse 版本**，不存在"大版本包含子版本"的耦合关系。

### 1.2 版本命名规则

```
<模块名> v<YYYYMMDD>
```

示例：
- `TriMetaverse v20260710`
- `TriCompany v20260709`
- `TriMC v20260710`

### 1.3 兼容性矩阵

- 当前阶段不强制维护模块间兼容性矩阵。
- 未来由中央 `BusinessStrategy` registry 记录模块兼容性映射，当前以各模块独立发布为准。

### 1.4 练兵场发布与回退规则

- **copilot-host 是练兵场**：用于验证规则、流程、agent 契约和模块实现。
- **练兵场总结输出的是规则**，不携带经营数据（用户身份、钱包、密钥、营收数字等）。
- **向 GitHub 更新代码版本**：只提交干净的代码、规则、流程、模板、脚本、ADR 和脱敏训练总结。
- **发布**：练好的业务模块 → 向 GitHub 对应模块仓独立更新发布。
- **回退**：练不好 → 回退该模块到上一个稳定版本重新开始。
- **其他模块不受影响**：单模块回退不联动其他模块版本。
- **线上 TriMetaverse**：从 GitHub 各模块的稳定版本通过 TriDev（含 TriDeployment）自动部署到服务器，日积月累产生公司实际经营数据。

## 2. 经营记录分层

### 2.1 三层切分

| 层 | 内容 | 提交 GitHub | 进入 release 制品 |
|----|------|:---:|:---:|
| **规则层** | Agent 定义、流程文档、模板、脚本、ADR、脱敏训练总结 | ✅ | ✅ |
| **运营记录层** | `operating-records/` 下的训练期任务记录、改进过程、会议纪要、决策追溯 | ✅ | ❌（`.releaseignore` 过滤） |
| **经营数据层** | 用户身份、钱包地址、私钥/助记词、API 密钥、营收数字、敏感讨论细节、具体经营参数 | ❌ | ❌ |

### 2.2 运营记录层细则

- `operating-records/` 下的文件**可以提交 GitHub**，作为过程档案和决策追溯。
- 历史训练记录具有存档价值，记录了改进过程。
- **必须在 `.releaseignore` 中声明过滤**，确保运营记录不进入 release 制品。
- 运营记录中如涉及经营数据层的敏感信息，必须在提交前脱敏处理。

### 2.3 经营数据层禁入清单

以下内容**绝对不得提交 GitHub**：

1. 用户个人身份信息（姓名、邮箱、手机号、身份证号等）
2. 区块链钱包地址、私钥、助记词
3. API 密钥、access token、service account credential
4. 公司营收数字、具体金额、交易记录
5. 敏感商业讨论（涉及外部合作伙伴、未公开的商业策略细节）
6. 未经脱敏的内部争议或人事讨论

### 2.4 `.releaseignore` 最小规则

```gitignore
# 运营记录——不在 release 制品中
docs/workflow/operating-records/

# 经营数据备份——绝对不入仓
**/secrets/
**/*.secret.*
**/credentials/
```

## 3. 边界裁决

- 如某文件是否属于"规则层"或"运营记录层"存在争议，默认先咨询 `BusinessStrategy`。
- 如经营记录中意外混入经营数据，立即撤回、脱敏、重新提交。
- 练兵场与生产数据的分离边界，由本文作为中央口径；模块级 registry 不得自行放宽。
