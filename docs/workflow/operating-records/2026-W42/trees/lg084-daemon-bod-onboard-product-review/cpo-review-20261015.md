## 摘要（大白话）

总判：**三面职责分工方向成立、报到链路治理面完备、CEO 指认两疑漏项成立**——但缺口位置不在报到链步骤（四步+双签+幂等+兜底已闭合），在**清单正本的内容面**：BOD 领单后「自检运行态在位」没有枚举化的检查单，daemon 层「定时与 job」和「与 daemon 对接」两类检查项裸奔。产品面五条建议：①清单正本附录增「上线自检检查单」（四项运行对接面·逐步程序化）；②自检读数回写位指定（自检「做了」变「可查」）；③四 daemon 职责速查入清单正本+daemon 不入报到制的边界写明；④失守信号触发后动作=回报到链（两层正交终点同一）；⑤承接容量读数留观不预建。

## 一·职责分工面（合理性判读：成立，建议正形显式化）

**判：方向成立，且是同一条产品哲学的第三次落地——一致性强信号。**

「daemon 为主中枢持久层」（CEO 22:46）的产品语义=**会话态智能与持久态机械的功能分界**：daemon 承担①层程序判+存（D-55 三层判据），BOD/席面保留③层语义判+转报裁决。这与现役两件正形完全同构——DEM-003 双域分工模型（本地预处理工组×服务域自动化流水线）与 Q2 反向通道（队列推节律拉）。同一哲学三次落地无打架=设计合理性高的结构性证据。

- **职责矩阵建议显式化**：四 daemon 能力面现散落评估卷/健康检查/记忆条（TriMLC=信箱+14 jobs·受宿主电源面约束／TriMMC=7×24 mailbox+outbox+ledger「拍存判报」三链全通／TriRMC=mcLedger+3 jobs·R 面候选／TriRLC=R 面本地+NOTIFY 出向）——**无统一职责速查正形**。BOD「与 daemon 对接」的前提是知道对接谁、对接什么——建议四 daemon 职责速查表入清单正本（onboard-work-registry.md）附录，随 daemon 能力演进由 CAO 维护。
- **daemon 不入报到制=边界正确（防泛化判读）**：D-52 类定义判据（`family: Registry`+常驻**会话**运行时实例）天然把 daemon 排除在外——daemon 是基础设施非 agent，报到信对它是伪需求。daemon 层的「上线感知」正形=healthz 活性面（活体优先诊断法机械侧）。**建议此边界写明**——防未来「daemon 也该报到」的机制泛化提案（同 Q2 红线「收推≠执行」的边界逻辑：机制域止于其语义面）。

## 二·对接形态面（合理性判读：形态一致，CEO 指认疑漏在此面成立）

现役 BOD↔daemon 对接盘点：快照追平（读 latest.json·拉）／cron job 状态（无核验形态）／信箱（notify-mailbox.json·D-52 承接链依赖）／出向告警链（outbox 三态·队列推节律拉 Q2 定形）——四条对接形态彼此一致、与 Q2/FADE-008 定形无冲突✓。

- **CEO 指认疑漏①「定时与 job」检查项=成立**：D-52 自检句「领单毕自检运行态在位；此后周期自检」是**行为面条款，缺内容面枚举**——「运行态」具体查什么没有清单。BOD 的 session-only 运行态主体恰是四时点 cron（本案原点）——cron 重挂规格在清单正本附录有载（D-52 先立后破段：原三案 §重挂规格表平移），但「重挂后核验挂载成功」的检查项（next_run 值面+enabled=1——F-3 家族性：POST 201≠会触发）无载。**挂了≠挂着**，核验项必须显式。
- **CEO 指认疑漏②「BOD 上线后与 daemon 对接」检查项=成立**：同上——快照追平/信箱可读性/出向链状态三类对接面均无自检检查项。信箱可读性尤要：报到链自身依赖信箱（报到信/承接/回执全走 notify-mailbox.json）——信箱不通=承接链死锁面，而链路里没有「先验信箱通」这一步。
- **产品面建议（疑漏两检查项的落点）**：清单正本附录增「**上线自检检查单**」内容面，四项起步：
  | # | 检查项 | 判法（程序化正形） |
  | --- | --- | --- |
  | 1 | 快照追平 | 读 latest.json 值面断言（现役已验证形态） |
  | 2 | cron job 挂载核验 | job 清单 API 逐 job：next_run 值面+enabled=1（禁凭 POST 201 认挂载） |
  | 3 | 信箱可读性 | 程序读箱断言（D-52 信箱面条款同源·先验承接链通道） |
  | 4 | 出向链状态 | outbox 三态/健康面读数断言（对接 Q2 回声流） |
  - **程序化纪律**：检查单按 D-55 款1 逐步落为检查脚本（断言族输出读数），非 agent 凭记忆自述「在位」——「自检」一词若无程序判据即回到 agent 推演灰区。一期可先清单化（agent 照单逐项跑命令贴读数），脚本化候窗。

## 三·报到链路完备面（合理性判读：治理面闭合，两点补充）

链路盘点：报到（信箱·词族钉死）→CAO 承接（信箱巡检+前置核查）→清单→领单→回执双签（本席联审缺口件一）→幂等（缺口件二）→缺席兜底三行→失守信号候补（CTO 面·两层正交）——**治理面完备度好，无结构性缺口**。

- **补充①·自检读数回写位缺（本席补，CEO 未指认）**：BOD 自检的断言读数落哪里没有指定——「自检做了」是会话内断言，「自检可查」才是在链事实（「已发≠在链」同族）。建议：自检读数回写 progress-snapshot 同族位（现役 `/srv/fleet/var/` 非 git 区形）或回执信 body 带读数——CAO 承接时即可见自检结果，恢复态成为可审计事实。与 CTO 卷 hub-watch-snapshot「拍+存」方向互补：那个是 daemon 拍 BOD，这个是 BOD 自报——双向闭环。
- **补充②·失守信号触发后动作应回报到链**：D-52 两层正交分工正确（行为面治配置丢失/机械面治复活失败），但失守信号触发后的恢复动作未指定——**应回到报到链重走**（报到→CAO 发恢复清单→领单→回执），不另开平行恢复路径。两层正交但终点同一：报到链=恢复唯一正道，防「失守→自愈」绕过治理面。
- **补充③·承接容量读数留观**：非人格类名单=CAO 按判据推导（现役存量=BOD 1 席）；sg 7×24 duty 班组常态化后常驻会话型实例趋增——CAO 信箱巡检承接容量候观察。现在 1 席无压力，**只记读数不预建机制**（承接量入 CAO 周报读数即可，达阈值再议）——不投资过度口径。
