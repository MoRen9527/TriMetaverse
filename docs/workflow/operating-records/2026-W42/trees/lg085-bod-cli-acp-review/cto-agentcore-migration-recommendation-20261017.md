## 结论先行

1. **分层形态成立**——「harness 管席组施工+agent-core 管常驻管理」=自然分工非二选一。技术精化一条：**分层的主语是场景不是席位**——不迁「席位」迁「例行件」；同一席可施工面留 harness、例行巡检面进 agent-core 托管。
2. **迁移序三步**：非人格例行件先行（已发生：bod-tick 转报链/催办定时器生产在跑·首日 4 催 4 闭环零误催）→偏运营人格席的**例行巡检面**拆件迁移（单轮+state 文件正形）→**人格交互面不迁**（工具生态与交互纠偏差距在交互场景不可收窄）。
3. **范式不打乱·正延续**：「运营件归消费侧自持」主语=消费内核的 daemon；agent-core 承载管理后运营件仍由承载 daemon 自持——四面分布实证（§三）。

## ③ 分层范式技术判读：不打乱·正延续

1. **主语辨析**：范式「运营件归消费侧自持」的消费侧=消费 agent-core 内核的 daemon 进程。agent-core 承载常驻管理后，管理 agent 成为 daemon 内托管会话，其运营件（补跑/重试/节拍/值守）仍由承载 daemon 自持供给——**范式主语未变·两层世界（tmux claude 进程+TriMLC 机制面）合为一层（daemon 托管）恰是范式纯化**。
2. **建造时实证**：agent-core 从 openclaw 吸收 scheduler 全族时统一裁掉五运营件（delivery/隔离 agent/reaper/启动补跑/heartbeat-wake·概念卷 8.1 血统表头注实锚）——「内核薄」是设计行为非演进遗漏，范式刻在包的骨头上。
3. **分布规律**：件跟着宿主环境与职责域走（桌面宿主 RLC/MLC 有电源面·服务域 MMC/RMC 无——9.4 表）——agent-core 承载管理不改变此规律，反而以四面 `file:` 同源共享（9.5：CEO 提议形态=现状已如此）把「内核统一·运营分化」制度化。

## 风险与门禁

- **最大风险**：agent-core 管理场景判断力质量与长跑**零实测**（6-8 件工具缺口可控但未验）。门禁=**双案实测窗（P3·不插主线·10-16 建议照守）**：挑 1-2 个非人格例行件试点扩面（催办定时器/bod-tick 已在生产——扩巡检面），读数门禁三条=误催率/补跑成功率/轮均 token 成本，双周读数后裁第 3 步。
- **file: 直连风险**：改包四面立受零灰度——产品化/扩面前必须解（版本化或 lockfile pin），列治理显性化前置件。
- **隔离 agent 持久会话膨胀**：配 reaper+压缩配套后才开第 3 步持久形；单轮+state 形优先。

## 建议裁决（并表候裁·终裁 CEO 保留权项）

分层形态**采纳**；迁移序三步（例行件已行→巡检面拆件→人格交互面不迁）；移植前提=收口非重移植（两零一半）；P3 双案实测窗开勘不插主线；治理显性化（≥2 面消费进包判据+file: 版本化）随批候条款化。技术位无 FREEZE 项。
