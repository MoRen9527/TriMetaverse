## §一 密钥生成与持有面

- **每席一密钥对**：生成=首次上岗（或席位注册）时在**本席宿主本地**生成，私钥永不出席（不进会话链/不进消息体/不进 registry）。
- **算法（候选定谳）**：**Ed25519**——跨平台库覆盖最广（libsodium/openssl/Go rust node python 安卓全绿）、签名快验签快、确定性签名无随机数坑（ECDSA 随机数缺陷家族免疫）；链上映射广（Solana/Cardano/Polkadot 系原生）。
- **私钥保管**：OS 凭据箱分立原则（CEO 约束）——Windows 凭据管理器 / macOS Keychain / Linux Secret Service / 安卓 Keystore；凭据箱只管「存」，签名动作由席位进程本机调用——保管面与签名层互补不合流。
- 公钥登记：注册面（号册/名址）登记**席位↔公钥**映射；公钥非秘密可全公开。
- 轮换：候新窗细节段（初稿立场=支持轮换·轮换须旧钥签发新钥证书链式锚定）。

## §二 签名字段格式

- **签名覆盖面=指令完整语义体**：令文全文+发令席 ID+收令席 ID+时间戳（防重放窗）+序号（防重放·与编号防伪并轨锚点）。
- **消息封装格式（初稿）**：`X-Stamp` 头结构= `{alg:"ed25519", from, to, ts, seq, sig, pk_ref}`——payload 原文不变（兼容现有消息体），签名附于外层头；`pk_ref`=号册公钥指纹（收侧查册验签·消息体不带全钥防膨胀）。
- 编码：sig/pk_ref 均 base64（标准基，URL-safe 变体候细节段）。
- **防重放窗**：ts+seq 双锚，收侧拒超窗重放（窗宽候细节段，初判 ±5min）。

## §三 验签点（SendMessage 收信侧）

- **验签位置=收信侧入站网关层**（非各席业务逻辑内）——收信侧在投递前统一验签：验签通过→投递+盖章标记；验签失败→**拒投+告警**（数据不执行不派活=CEO 原话）。
- 实现形态候选（候新窗定谳）：宿主层 hook（Claude Code hooks 面）/消息总线中间层/收席入口 shim 三选——倾向 hook 面（零改消息协议·宿主原生机制）。
- 验签日志：验签结果（过/拒）+拒因（无签/坏签/超窗/查无此钥）留痕可审计。

## §四 无签降级策略

- **两阶段灰度（初稿立场）**：
  - 阶段一 warn-only：无签消息照投+显著标记「未盖章」+验签日志计数——观察期 ≥1 周（灰度素材：误伤率/漏签率读数）。
  - 阶段二 enforce：无签=拒投（数据不执行）——切换判据=阶段一误伤率读数达标（阈值候细节段）。
- **白名单降级例外（候 CPO 会签）**：系统级 bootstrap 消息（席位复活链/SOP 恢复期）或新席注册前首信是否豁免——倾向「例外也须签（注册席以引导钥签）」非裸豁免，细节候新窗。
- CEO 已认可方向不回头批——降级策略属方案要素内裁量，灰度节奏候 BOD/CEO 知情。

## §五 与既有编号防伪纪律并轨

- 编号防伪（发令序号/令牌核对）=**应用层语义防伪**；指令盖章=**密码学层身份防伪**——两层并轨不互斥：seq 序号复用编号体系（同一序号域），盖章使序号从「可核对」升级为「可验证」。
- 既有编号纪律不废止；enforce 后编号防伪从「人工核对」降为「验签附带产出」（sig 覆盖 seq→序号伪造在密码学层即拒）。

## §六 TriChain/TriWeb4 对表结论（BOD 22:45 令面）

- 实勘两仓 registry 三面（22:53-22:55）：**两仓均结构预留空壳**——TriChain=预留公链模块（链上执行/集成/公链能力承接·零代码零设计·占位态）；TriWeb4=预留 Web3/Web4 钱包与合约模块（钱包/链上交互能力承接·占位态）。两仓 code-state 明示「占位模块误写成已有实现」=首要风险注记。
- **结论一（勿另起炉灶的正确打开方式）**：无既有签名原语/身份模型可对齐——「对表既有」实际=对齐两仓**预留边界定位**：指令盖章系公司席间治理层，**不侵入两仓模块边界**（不预写链代码/不占 TriChain 公链位/TriWeb4 钱包位），仅以「身份映射接口」预留亲和。
- **结论二（迁移路径天然锚点=TriWeb4）**：席位密钥对=未来席位钱包身份的自然种子——公钥派生链上地址是标准做法（以太坊地址=keccak(pubkey) 截段/Solana 地址=pubkey 本身）；TriWeb4 承接钱包面时，席位公钥册可直接升格为「席位钱包地址册」——**零密钥迁移，只加映射层**。
- **结论三（TriChain 接入时）**：链上执行层（合约/交易签名）与席间治理签名（本机制）分层——本机制签「公司指令」，链面签「交易」；两签系可同源（同钥）或分钥（治理/资金分离·安全最佳实践）——**倾向分钥**，候新窗细案。

## §七 跨平台兼容评估（CEO 约束三·框架级）

- 密码学原语：Ed25519 全平台一致（RFC 8032 标准无平台分叉）✓。
- 凭据箱面：四平台各异（Win CredMan/mac Keychain/Linux libsecret/Android Keystore）——**抽象层接口统一**（`keychain.get/set/del` 适配器模式），签名层不感知平台差异。
- 安卓特有注记：Android Keystore 硬件背钥（TEE）不支持导出私钥——席位若落安卓端，私钥生成须走 Keystore 内生成+签名（密钥不出 TEE），与「私钥永不出席」原则同构兼容✓（细节候新窗）。
