## 一、方案摘要

**复用 `@tricompany/agent-core` 共享 scheduler（croner + JSON store + JobExecutor，已存在且有测试），TriMC 仓只写服务域适配器 `src/cron/`（命令执行 handler + HTTP 端点 + CLI + 进程装配），以定时确定性命令触发 `weekly_plane_shift.py` 五段链，在服务器舰队克隆执行周平面迁移 + git 提交推裸仓，本地 pull 回流。**

一句话判据：parity V1.1 §1 禁止复制 TriLC/src 到 TriMC/src，§2 声明共享 core 已含 scheduler——因此 TriMC 侧只允许"薄适配器"，不允许移植 TriLC cron，更不允许新写一套调度核心。

## 二、三个定案点（派单要求）

### 2.1 命名避让（①）——定案：`src/cron/`

- 现状冲突：`src/orchestration/employee-scheduler.ts` 已占用 "scheduler" 语义（员工任务调度/排班，agent 域）。
- 共享核心已位于 `TriCompany/packages/agent-core/src/scheduler/`（COS-005 规划的落点，R7 2026-08-12 迁至公司维度并经 CEO 批准）。
- **TriMC 侧新增模块命名 `src/cron/`**：
  1. 与 CLI 动词 `trimc cron <add|list|run|...>` 一致（对标 `trilc cron`）；
  2. 与 TriLC host 层 `src/cron/` 命名对齐（TriLC cron 是本方案的行为对标基准，不是代码移植源）；
  3. 与 employee-scheduler.ts 零语义冲突。
- 边界声明（写进 `src/cron/index.ts` 模块头注释）：`src/orchestration/employee-scheduler.ts` = 员工调度（agent 域）；`src/cron/` = 定时任务（cron 域）；共享调度核心在 agent-core，本目录只是服务域装配面。

### 2.2 语言选型（②）——定案：TypeScript

依据：

1. **共享 core 是 TS 且已全量导出**：`TriCompany/packages/agent-core/src/index.ts` L124-178 导出 scheduler 全部 API（JobExecutor/CronJob/job-store/cron-engine/backoff 等）。消费共享 core 即 TS。
2. **宿主进程是 TS**：TriMC server（`src/server/app.ts`，raw `node:http`）为 TS 进程，scheduler 必须装配进该进程（HTTP 端点 + start/stop 生命周期）。
3. **croner 已在 TriMC dependencies**：`package.json` 含 `croner: ^10.0.1`（与 TriLC 同版），依赖面零新增。
4. **COS-005 决策记录延续**：「Python heartbeat 保持 IPD 职责不变；新增 TS 侧任务执行心跳」——Python 在 TriMC 只存在于 `src/heartbeat/` 域。
5. **服务器运行时兼容**：服务器 Node v18.20.8（M0 实测记录），agent-core job-store 为纯 `node:fs` JSON（无 `node:sqlite` 依赖——这正是不能移植 TriLC cron store 的硬理由之一，TriLC 用 `node:sqlite` DatabaseSync，Node 18 不可用），TS 适配器无原生模块，v18 可跑。
6. **跨语言边界**：执行器经 `child_process` spawn `python3 -m runtime.cognition.weekly_plane_shift`（TriCompany 侧现成 CLI），属进程级调用，不构成 TriMC 新 Python 模块。

### 2.3 复用 vs 移植（③）——定案：复用共享 core + TriMC 薄适配器（不移植、不复制）

依据：

1. **parity V1.1 硬约束**：§1 明文禁止「复制一份 TriLC/src 到 TriMC/src」；§2 声明共享 core 已包含 scheduler。
2. **共享 core 已实现且带测试**：`agent-core/src/scheduler/` 8 文件 1066 行 + 5 测试文件（cron-engine / job-store / job-executor / backoff / stagger / heartbeat-policy / types），即 COS-005 规划的完整落点，含 croner 解析缓存、JSON 原子写（tmp+bak+rename）、JobExecutor 调度循环、backoff/retry 原语。
3. **TriLC src/cron 的角色 = 行为对标基准**：CLI 契约（`trilc cron add/list/run/log/status`）、HTTP 路由表、防并发（running 守卫 + 锁）、超时（10min）、连续失败降级（3 次 degraded）等行为语义对齐；其 session/LLM/localbus 耦合部分（sessionStore、runHeartbeatAgent、`publish`）正是共享 core 已剔除的部分，TriMC 侧不需要。
4. **版本差标注**（溯源义务）：COS-005（2026-07-16，前任 CTO 实例交付）规划 TriMC `src/scheduler/` 落点 + JSON store + croner；实际演进为共享 core 移入 `TriCompany/packages/agent-core`（R7，2026-08-12 CEO 批准），TriMC 侧落点修正为 `src/cron/` 薄适配器。本方案沿用 COS-005 关键决策（croner、JSON 原子写、Python 域边界），修正的是落点与消费方式，不推翻结论。

## 四、调度设计（触发源 / 存储 / 执行器 / 失败重试 / 审计）

### 4.1 触发源

- cron 表达式：**`0 23 * * 0`，timezone `Asia/Singapore`**（服务器 UTC+8）——周日 23:00，ISO 周翻转（周一）之前触发。
- 解析：croner（agent-core cron-engine，带实例缓存 + year-rollback workaround）。
- week token 规则（适配器纯函数，与触发窗口匹配）：
  - `toWeek = ISO week of (today + 1 天)`；`startDate = toWeek 所在周的周一`；`fromWeek = toWeek − 1`。
  - 验证：周日 08-16 跑 → to=W34 ✓；周一~周六任意一天补跑（catchup）→ 明天仍在 W34 窗口内 → to=W34 ✓；下周日 08-23 跑 → to=W35 ✓。规则对全周正确。

### 4.2 调度存储

- 复用 agent-core job-store：JSON 文件 **`$TRIMC_CONFIG_DIR/cron/jobs.json`**，版本化 schema（`CRON_STORE_VERSION=1`），原子写（tmp + .bak + rename，0600），内存缓存 + save 后失效。
- 服务器落点：`TRIMC_CONFIG_DIR=/var/lib/trimc`（root 可写、持久、不进 git），在 `/usr/local/sbin/trimc-start.sh` 导出或 trimc.service `Environment=` 注入。
- 说明：COS-005 原决策「JSON 先行，后续迁 SQLite」修正为「后续迁 **PostgreSQL**」——服务器已有 postgres:16（127.0.0.1:5432）且 `pg` 已在 TriMC dependencies；但 Node 18 无 `node:sqlite`，SQLite 路线不可行。store 接口不变，迁移只换底层，r1-2 不实施（MVP 裁减，登记为跟进项）。

### 4.3 执行器

- **JobExecutor**（agent-core）：tickMs 1s / maxTimerDelay 60s 调度循环；`state.runningAtMs` 守卫防并发重入；`consecutiveErrors` 累计；隐式 catchup——首 tick 即执行 `nextRunAtMs ≤ now` 的 due job，服务器重启/错过窗口自动补跑（无显式 catchup 代码，行为由 r1-3 实测确认）。
- **command-handler**（TriMC 适配器，确定性命令执行，无 LLM）：
  1. 读取 `job.payload`：`{ command: string; cwd: string; timeoutMs?: number; runAs?: string }`；
  2. token 替换：`{fromWeek}` `{toWeek}` `{startDate}`（week-math 计算）；
  3. spawn shell（`/bin/bash -e`，`&&` 链式，失败即停），`cwd` 按 payload；
  4. runAs 降权：`runAs: "fleet"` 时以 uid/gid 1001 执行（复用 `env.ts` TRIMC_RUNAS 的 M1 session-bridge 降权模式）；未设则以进程用户执行（本地开发）；
  5. 超时：默认 10min（对齐 TriLC DEFAULT_JOB_TIMEOUT_MS），payload.timeoutMs 可覆盖，超时 SIGKILL；
  6. 输出：stdout/stderr 捕获，写 per-run 日志 `$TRIMC_CONFIG_DIR/cron/logs/<jobId>-<ISO时间戳>.log`，同时进 systemd journal（console 回显），失败时错误尾部入 `lastError`。
- **stale-run 恢复**（适配器补的缺口，agent-core 无）：service.start() 时把所有 `runningAtMs ≠ null` 的 job 重置为 null（崩溃残留恢复），否则 job 永久卡 running。
- **防并发**：runningAtMs 守卫 + 单 systemd 实例（无多副本）→ 迁移窗口内单实例执行。K8s 多副本场景需要 lease，MVP 不覆盖（单节点服务器事实）。

### 4.4 失败与审计

- **无自动重试（MVP 裁减）**：一次失败即记 `lastError`；agent-core 已有 `withRetry`/backoff 原语，P2 接入。重跑 = `trimc cron run <id>`，重跑安全由脚本幂等（create/carry_over 有守卫）+ commit 段 no-op 容忍保证。
- **降级可见**：`consecutiveErrors ≥ 3` → degraded → `/healthz` cron 块 + `GET /internal/v1/cron/status` 暴露。
- **审计三层**：① jobs.json state（lastRunAt/lastRunStatus/lastError/lastDurationMs/runCount）持久化；② per-run 日志文件；③ 文件级：脚本产出 `.shift-ade.json`（新周目录内，随 git commit 进仓）+ git 提交固定身份（`TriMC Scheduler <trimc@tri.company>`，`-c` 内联不依赖全局 config）。

## 五、周平面文件服务器端写路径（生产级开发期 §三方向例外）

### 5.1 命令模板（payload.command，安装进 job）

```bash
cd /srv/fleet/TriCompany && python3 -m runtime.cognition.weekly_plane_shift \
  --from {fromWeek} --to {toWeek} --start-date {startDate} \
  --operating-root /srv/fleet/TriMetaverse/docs/workflow/operating-records --sync \
&& cd /srv/fleet/TriMetaverse \
&& git add docs/workflow/operating-records \
&& (git diff --cached --quiet || git -c user.name="TriMC Scheduler" -c user.email="trimc@tri.company" \
     commit -m "ops: weekly plane shift {fromWeek}->{toWeek} (TriMC scheduler)") \
&& git push /srv/git/TriMetaverse.git HEAD:dev
```

- `--sync` 是唯一写开关（脚本默认 dry-run，不写文件、不通知）；五段链 create→migrate→carry_over→validate→agent_close 全确定性，退出码 0/1，产出 `.shift-ade.json` 并投递邮件通知（脚本内建，非阻塞）。
- commit 段 `git diff --cached --quiet ||` 容忍重跑 no-op（幂等重跑安全）。
- 推裸仓走本地路径（同主机，无网络、无凭证）；`HEAD:dev` 对齐裸仓 HEAD=dev。

### 5.2 git 链路与回流边界

1. 服务器侧：fleet 克隆 commit → push `/srv/git/TriMetaverse.git`（TriMC 编排层维护周平面文件，§三方向例外授权）。
2. 本地回流：`git pull sg-server dev`——**运维回流步骤，由编排层（小贾）执行，调度器不负责**（服务器无法触发本地动作，边界显式声明，写入 runbook）。
3. 写方向单主体纪律不变：服务器侧只写 `docs/workflow/operating-records/` 周平面文件；代码文件仍本地发起。

### 5.3 服务器前置检查（一次性，r1-2 checklist）

## 八、硬 deadline 保障与裁减

- **裁减（MVP out，显式登记）**：自动重试（P2 backoff 接入）、store 迁 PostgreSQL、K8s 多副本 lease、通知集成（脚本已内建 email）、daemon/service 管理（systemd 已覆盖）。
- **触发保障**：08-16 23:59 前 `trimc cron run <id>` 可触发真实 W33→W34 迁移（08-17 周一新平面激活）；r1-3 验证「deadline 前可触发性」用测试根 dry 链 + 真 job 状态检查，不误跑真迁移。
- **兜底**：scheduler 未就绪 → 迁移走既有路径（服务器手工执行同命令链），树按实际状态收口，不伪报。
