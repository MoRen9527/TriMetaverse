### 1.3 分歧点分析

- **实质分歧：无，两席结论方向一致。** 两席在各自被派的面（M 面迁移必要性 / R 面引入必要性）分别独立得出「不引入」的一致方向，且 E2 证据边界 9 自述「E1 产出的 sdk-eval-m-face.md 本节点未读（避免跨席评估互相污染）」（sdk-eval-r-face.md L225）——两结论来自互不污染的独立证据链，收敛性比同席连评更强。
- **表述层面差异（非分歧，如实呈现）**：E1 称「SDK 能力面是现 M 面契约的严格超集，但增量部分无现役消费者」（sdk-eval-m-face.md L32），E2 称「SDK 能给的形态，R 面已自研持有」（sdk-eval-r-face.md L110）。两句主语不同（M 面契约消费视角 / R 面自研资产视角），合并读即：SDK 相对 M 面「多出来的没人用」、相对 R 面「等价的已有」——不构成冲突。
- **边界条款互补**：E1 的 C1-C5 是 M 面重启条件替换评估的触发器；E2 的条件 A/B/C 是 R 面重审门。E2 条件 C 明言未来引入即便发生也只限 M 面，而 E1 现判定 M 面亦不做——两者是「条件框架」与「当前判定」的关系，不矛盾。两条触发器族应合并到单一监控面（见第四节清单 #6），避免双轨漂移。
- **独立收敛点（合成增量）**：两席在互不引用的情况下各自得出同一关键事实——「SDK 不消除 Claude Code native CLI 运行时依赖」（E1 维度②2.3 L59 / E2 ②-1 转引快照:44）。该事实同时削弱 M 面「换库即换实现」的预期收益与 R 面「引入即自主」的可能叙事，是两份报告最硬的共同支柱。

### 1.4 共同证据弱点（不影响结论方向）

两席全部 SDK 能力/条款陈述同源转引自编排层 WebFetch 快照（要点级转录、非字节级镜像；E1 证据边界 3 / E2 证据边界 3），且 E1 自评 Python SDK 信息缺口为「本报告最薄弱证据点」。合成判定：该弱点不翻转结论方向——两份报告的「不引入」判定都不依赖 SDK 能力细节的精确性，而依赖「增量零消费者 / 零能力缺口 + 成本与原则代价」这类与快照精度弱相关的本地证据。但若未来任一触发器命中、需进入条件复评，应先做原文级复核（见第四节清单 #7）。

## 二、M 面 Popen→SDK 迁移优先级：不做（维持现状）

### 2.1 档位判定与映射论证

三选一逐项对照 E1 结论：

| 档位 | 判定 | 论证 |
| --- | --- | --- |
| 立即可做 | 否 | 无收益驱动力：SDK 增量能力在现契约下零现役消费者（E1 维度①），等价能力 CLI 参数已覆盖；「立即」投入三处深层重建换零功能增量，直接与 E1 成本-收益倒挂判定冲突（sdk-eval-m-face.md L61） |
| 列入工程窗 | 否 | 「工程窗」语义是「已决意做、只差排期」；E1 的判定性质不是排期问题而是「不值得做」。列入工程窗意味着无谓占用工程窗容量，且按 E1 维度③将连带触发段-实现映射表两处改登与 pid 锚/Close CLI 载体重建义务——为「零消费者」的能力付确定性资产回归的代价 |
| **不做（维持现状）** | **是** | 与 E1「不替换」逐字同构：维持 Popen + CLI 子进程形态为长期形态，非「暂缓」而是「除非触发器出现否则不启动」。C1-C5 作为监控项挂出（零迁移工作量），任一命中即重启条件替换评估 |

结论：本建议选择「不做（维持现状）」档。E1 的「不替换」不是「暂缓迁移」——其附带的条件复评触发器属于监控面而非工作项，故不落入「列入工程窗」档；映射关系如实论证如上。

### 2.2 理由（自 E1 推导，逐条对应）

1. 收益侧为零（E1 维度①判定表）：流式 StreamEvent / 会话 resume-fork / hooks 三项判「冗余」（无现役消费者），allowedTools 判「零增量」，结构化 outputFormat 判「低增量」。
2. 成本侧在下游基建而非 spawn 段（E1 维度②）：pid 锚全链（`_pid_alive`/锁四通道/锁内补记/registry ticks）+ harvest 与 Close CLI 载体（CTO-F7 立法载体，FADE-006）+ 异步 detach 语义三处深层重建；测试回归面覆盖 O_EXCL 原子锁/陈旧锁四通道/战役续跑指纹/预算双门/harvest 去重/spawn cwd 树路由全部确定性资产。
3. 依赖代价与护栏相悖（E1 理由 4）：商业条款闭源运行时绑定 + Python/TS 宿主绑定，与 M 面低成本少依赖姿态冲突；且 SDK 不消除 native CLI 运行时依赖——迁移换来的只是约 30 行编排代码的库化。
4. 叙事一致性（E1 理由 4 + E2 条件 C）：R 面 agent-core 是自主可控原则的承重面（E2），M 面引入 SDK 会在叙事上削弱「编排引擎自主可控」一致性——两席独立同向。

### 2.3 附条件监控面（监控项，非工作项）

C1-C5（sdk-eval-m-face.md L92-98）登记为 M 面复评触发器监控：C1 流式消费需求（trilc push-as-push 落地后）、C2 跨 tick 会话恢复需求、C3 schema 输出需求且接受连带重建、C4 Python SDK 对 python3.8 宿主与现有凭据实证可用、C5 CLI `-p` headless 路径进入弃用周期（监控点=官方 changelog 入口，转引）。触发后的复评按 E1 维度③须遵守细则 10（接线+实测才算立法完成，不得纸面换声明），并先完成第四节清单 #7 的原文级复核。

### 2.4 协议面影响（本档位下为零）

选择「不做」：当下不触发 §2.8 降级合同重审（E1 3.1），也不产生段-实现映射表改登义务（E1 3.2 的两处改登仅在「未来真做迁移」时生效）。本档位对 FADE 协议面的运行成本为零；node-E1.md 断点交接 2 的映射表改登提示保持「待触发」状态，不转为执行项。
