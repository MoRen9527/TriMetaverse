## 2. 本周观察到的大模型能力问题与体验

### 2.1 多仓 workspace 结构下，模型默认只在当前工作目录内搜索，不会自动跨到兄弟目录查找模块真源

- 现象：
  在 TriMetaverse 的 root workspace 多仓结构中（21 个独立 Git 仓库以同级 `../` 目录挂在 TriMetaverse 旁边），模型在执行文件搜索时，默认只在当前工作目录 `TriMetaverse/` 的子树内查找，不会自动跨到兄弟目录（如 `../TriCompany/`）去定位模块真源。

- 具体表现：
  当需要查找 `TriCompany/docs/training/` 下的培训文档时，模型先在 `TriMetaverse/` 树内找到了 `TriCompany-copilot-host-assets/docs/training/`（宿主支撑包的 published-copy），并把它当成真源使用。即使该支撑包目录下确实有文件，它也不是模块的真源——真源在 `../TriCompany/docs/training/`。模型没有意识到"当前工作目录下找不到"不等于"不存在"，应该跨到兄弟目录继续查找。

- 根因分析：
  1. 模型对多仓 workspace 的物理布局缺乏默认感知：`TriMetaverse/` 是 root workspace，但 `TriCompany/`、`TriMC/`、`TriDev/` 等 20 个模块仓是独立 Git 仓库，位于同级 `<父目录>/` 下（即 `../`），而非 TriMetaverse 的子目录。
  2. 四层资产定位规则虽然已在 `docs/文档治理与真源文件系统.md` §2 和 `docs/github-repo-governance.md` §6.2 中明确记载（模块源仓 = 真源，支撑包 = 宿主发布包，不是第二真源），但模型在搜索时没有先查阅治理规则判断"我应该去哪里找"。
  3. 前置核查顺序（先查 TriCompany 源侧 → 只有涉及宿主特有发布副本时才补看 copilot-host-assets）虽然写入了 agent 指令，但在实际执行中被跳过。

- 解决方案：
  1. 在 `docs/文档治理与真源文件系统.md` §2.1 中补入了完整的物理工作区布局图（21 个兄弟目录树），并新增"关键纪律"条目，明确写出：**"搜索模块真源时，必须跨到兄弟目录查找，不可只在 TriMetaverse 树内搜索后得出'不存在'的结论。"**
  2. 在 `docs/github-repo-governance.md` §2 中维护了 workspace 文件夹注册表（21 个挂载点，含物理目录路径），作为可查询的 machine-readable 索引。
  3. 在 W28 未决事项中标记此问题，并要求在共学周记中长期跟踪。

- 问题影响：
  这类错误不是偶发的搜索遗漏，而是系统性偏差：只要模型不主动跨到兄弟目录，就会持续把支撑包的 published-copy 误判为真源，或在 TriMetaverse 树内搜不到时错误地得出"文档不存在"的结论。对于多仓项目，这会直接导致修改错误文件、漏扫真源、形成影子真源。

当前经验：

- 项目经验：
  多仓 workspace 项目中，必须在治理文档里显式画出物理目录树和兄弟目录关系，不能只靠"模块在另一层"这样的抽象描述。每个模块的真源路径必须可枚举、可查询。
- 模型自查：
  在回答"某个文件是否存在"或"某个模块的文档在哪里"之前，必须先查阅多仓治理规则和 workspace 布局，确认应该搜索的物理目录范围；不要只在当前工作目录子树内搜索后就下结论。

### 2.2 已写在治理文档里的规则，模型在长链路任务中仍然会跳过

- 现象：
  CEOChiefOfStaff 的 agent 指令中已经包含完整的前置核查顺序（先查 TriCompany 源侧 → 再查支撑包），`docs/文档治理与真源文件系统.md` §3.5 也写了同样的优先原则。但在实际执行长链路任务时，模型仍然会直接跳到支撑包去查找文件，跳过源侧核查。

- 具体表现：
  查找 training 文档时，模型先访问了 `TriCompany-copilot-host-assets/docs/training/`（支撑包），没有先到 `../TriCompany/docs/training/`（模块真源）。

- 根因分析：
  规则虽然在指令和治理文档中都写了，但模型在执行任务时受"当前工作目录就近原则"的影响，优先搜索了 TriMetaverse 树内的文件。治理规则的"先查源侧"没有被转化为强制的搜索步骤。

- 解决方案：
  1. 在 `docs/文档治理与真源文件系统.md` §2.1 中把物理布局写成了可执行的搜索指引（"必须跨到兄弟目录查找"），而不仅是抽象规则。
  2. 建议未来在 agent 指令中把"先搜索 ../TriCompany/ → 再搜索 TriCompany-copilot-host-assets/"写成可操作的搜索步骤，而非依赖模型自行判断。
  3. 此问题作为长期观察项，持续跟踪是否还会复现。

- 问题影响：
  如果规则写在文档里但模型反复跳过，说明当前治理规则的"执行可达性"还不够——规则需要写成模型能直接转化为搜索动作的形式，而不是停留在"应该优先"的描述层面。

当前经验：

- 项目经验：
  治理规则不仅要写"应该优先查哪里"，还要写"具体应该搜索哪个物理路径"，让模型可以直接执行。
- 模型自查：
  在开始搜索文件前，先读治理文档中的物理布局章节，确认搜索范围包含所有需要跨到的兄弟目录。

### 2.3 治理规则明确但模型仍然反复在 TriMetaverse 子目录下错误创建模块文件

- 现象：
  虽然 `docs/文档治理与真源文件系统.md` §2.1 已经画出完整物理布局（TriMC、TriCompany 等均为 `../` 兄弟目录），`docs/github-repo-governance.md` §2.2 也逐行列出 workspace 挂载表（TriMC → `../TriMC`），模型在需要创建或写入模块文件时，仍然反复使用 `TriMetaverse/<模块名>/` 的错误路径，而非正确的 `../<模块名>/`。

- 具体表现：
  1. 更早的对话中，模型曾在 `TriMetaverse/TriMC/` 下创建了心跳检测代码（Python heartbeat），而真正的 TriMC 独立仓在 `../TriMC/`。该错误目录不含 `.git`，是孤立代码副本。
  2. 本日对话中，用户要求查找 TriMC 的 `DESIGN.md` 时，模型再次先查 `TriMetaverse/TriMC/docs/engineering/`（不存在），再错误地认为文件缺失，而非直接跨到 `../TriMC/docs/engineering/DESIGN.md`（实际存在且为 26KB 的成熟设计文档）。
  3. 更严重的是：模型在"找不到"时选择了**创建新文件**而不是跨仓搜索——在本日对话中创建了 `TriMetaverse/TriMC/docs/engineering/DESIGN.md`（新空文件），覆盖了真实 TriMC 仓中早已存在的 517 行设计文档。

- 根因分析：
  这是一个**复合错误模式**，区别于 2.1（仅搜索遗漏）和 2.2（跳过规则）的地方在于：
  1. **就近创建偏好**：模型默认把 `TriMetaverse/` 当作"我的项目根目录"，当需要为某个模块创建/修改文件时，第一反应是在当前工作目录下创建 `<模块名>/` 子目录，而不是跨到兄弟目录。
  2. **搜索-创建短路**：模型在 TriMetaverse 子树内搜索失败后，直接跳到"文件不存在，我可以创建"的结论，跳过了"先跨到兄弟目录查找"这个中间步骤。
  3. **治理文档的被动性**：即使物理布局图（§2.1）和 workspace 挂载表（§2.2）都已明确，模型在"创建"动作上没有把"先查表确认模块路径"作为强制前置步骤。
  4. 这与 2.1 的"搜索遗漏"不同——2.1 是搜索范围不够，2.3 是连**创建动作的路径选择**都错了，后果更严重（产生影子目录、覆盖真源）。

- 解决方案：
  本轮处理：
  1. 将错误创建的 `TriMetaverse/TriMC/` 中的心跳代码迁移到正确位置 `../TriMC/src/heartbeat/`，然后删除整个 `TriMetaverse/TriMC/` 目录。
  2. 将 TriMetaverse git 中的删除操作正确 stage（`git add TriMC/`），确保错误副本不再出现在版本历史中。
  3. 在 `../TriMC/docs/engineering/DESIGN.md` 中恢复了完整的 517 行设计文档（确认真实 TriMC 仓内容未被覆盖）。
  长期修复：
  4. 在 agent 指令层面，需要把"确定模块物理路径 → 先查 workspace 挂载表"固化为任何文件创建/搜索动作的前置步骤，不能依赖模型"顺便想起来"。
  5. 在治理文档中，首次在 §2.1 末尾加写"禁止在 TriMetaverse 子目录下创建任何模块仓文件"，把"不做什么"也写清楚。

- 问题影响：
  这个问题比 2.1 严重——搜索遗漏只会导致"找不到"，路径创建错误会导致影子仓库、内容冲突、版本历史污染和真源分裂。对多仓 workspace 项目，模型如果不能在创建动作上也遵循物理布局纪律，会在不经意间制造大量需要事后清理的垃圾目录。

当前经验：

- 项目经验：
  1. 多仓项目的治理文档不仅要写"在哪里找"，还要写"不许在哪里创建"。物理布局的"禁止区域"和"允许区域"同样重要。
  2. 模型的"就近创建"偏好是一个真实存在的系统性问题——它把当前工作目录当作项目根目录的默认行为，在没有显式纠正的情况下会自动产生错误路径。这需要治理规则和执行步骤共同钳制。
- 模型自查：
  1. 在创建或修改任何文件之前，必须先确认目标模块是否为独立仓库。如果是，必须查 `docs/github-repo-governance.md` §2.2 获取正确的物理路径（`../<模块名>/`），绝不默认在 `TriMetaverse/<模块名>/` 下创建。
  2. 在某路径下找不到文件时，不要直接跳到"创建"——先执行跨仓搜索确认文件是否存在于兄弟目录中。
  3. 如果"找不到"发生在独立模块仓的资源上，把"跨仓搜索"作为必选步骤排在"创建新文件"之前。
