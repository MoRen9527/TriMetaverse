## §1 机制总图

```
员工席任务至候批态
  →①收口钩子自动写候批信（daemon 模板零 LLM）＋台账同刻挂账（D-27 v2 扩展）
  →②BOD notify 拉取即见（信箱=待办聚合器）
  →③daemon 轮询判定超时（确定性，频次与 token 解耦）→COS 事件出场地催（不靠记忆）
  →④BOD 提醒 CEO（24h hook 注入清单+48h toast 双保险——human-in-session 克制设计）
  →⑤CEO 批→信箱 resolved＋台账销账同刻双写→自动回流开工
```

**机制化三件（CEO 23:24 指正直答）**：轮询器自动触发催办＋催办信自动生成＋状态文件自动更新——判定全在 daemon 层，席位只事件出场。

## §2 候批信信件规格

### 信封（CTO 案一 notify-mailbox 扩展：action 词汇三增 `submit-approval`/`approve`/`urge`；payload 定型）

| 字段 | 说明 |
|---|---|
| `type` | `pending-approval`（候批）/`pending-review`（候审，席间域） |
| `source_seat` | 写信席 |
| `target` | **bod+coo 双投**（seats.json 名册解析已就位 baedc02——零新增路由代码，补 coo 可达项即可） |
| `task_ref` | **双向映射键**：任务书路径#节点 id 或 LG-xxx |
| `state` | `pending-bod`/`pending-ceo`/`pending-window` |
| `track` | 三轨：`normal`/`blocked`/`red`（red 直达轨永不积压按违时处理） |
| `waiting_since` | 素材齐备时点（候批信或台账较早者——T+0 起算锚） |
| `sla` | D-27 v3 双型锚载体：`hard:<绝对时点>`/`normal:24h` |
| `required` | `human` 徽标（审批转呈/最终确认/敏感面三类——自动化到此为止不越） |

### body 四行模板（CPO 定稿；R2 模板槽位每槽≤40 字，零 LLM 生成）

`干了什么 → 候谁决什么 → 已候多久（时点+累计） → 批后会怎样+超时会怎样`

### 触发/幂等/留痕

- 生成点=进入候批态瞬间：收口 notify 与候批信同刻自动双发+台账同刻挂账；
- 信箱层幂等覆盖；**留痕层只追加**——六+二字段（任务书号/状态/时点/催办对象/参与席/事由＋首写时点/覆盖计数）；候批时长=已批时点−首写时点；
- 状态跃迁发状态更新信。

## §3 三层催办机制

| 层 | 触发 | 执行者 | 时点 |
|---|---|---|---|
| ①催执行席 | 在办超时 | COS 事件出场（轻量注入≤2K） | hard 到点即催／normal 24h；三要素+终点（首催→重申一次→到顶按已收意见先行汇总+缺席标注） |
| ②催审批链 | 候批超时 | daemon 判定→COS 催 BOD | hard 到点即催／normal 沿 CPO 节奏表 T+0→4h→1d→2d→5d；**BOD 提醒 CEO**：24h 随 CEO 下次消息 hook 注入三行清单（事项/候时长/建议动作，不主动打断）＋48h 独立 toast 双保险（BOD 段定稿） |
| ③催督办面 | 升级态+批量积压 | COS→COO | 48h 升 COO→72h 呈 CEO 汇总；积压三档：常规同族≥3/阻塞同族≥2/red 不入档；族级升级=整族决策点+督办红档+晨报瓶颈段 |

- 不吵五律（CPO）＋催办对表三律（催状态不催人/升级不改口/动作即清催）＋超时≠批准（COO 保留条款）＋督办读数两轮挂晨窗/夜航窗（读数不通知动作才发）＋催办留痕=绩效效率源（一账两用）。

## §4 台账-信箱映射与真源（★一处实质分歧标注候裁）

- 映射键=`task_ref`；双写同刻（发生侧+裁决侧）；COS/daemon 巡检双态对表（漏挂/漏写/不同步三型差口=告警源）；闭环判据=零差口。
- **★真源定谳（三席归口闭环：CTO 终裁/CAO 终判接受/COS 执行者接受）**：**分层双真源**——实时态真源=信箱（letter-store 状态机：机器写入/事件驱动/append-only 审计同构）／治理确认态真源=台账（COS 维护治理口径：绩效/督办/呈报引用确认态）。**跨层唯一通道=COS 核认门**（实时态→确认态，核认即定谳；防未核认信息直接引为治理口径的旁路——CAO 精化随裁，§4 正身明书）。COS=确认者非誊抄员（CEO「COS 在任务书与台账层面催办」的机制语义）。CAO 原裁让位注记：「信箱=投影」表述不精确——信箱系实时层真源本体；投影=「台账的实时镜像（核认前）」与「信箱的治理视图（核认后）」。依据=双腿判据同构（写入方式与保留策略分域）。过渡口径（双写零差口）=核认前流转窗口短暂双写合法。CAO 树内段稿 §2.1 单平面表述由本节取代（段稿留树作合流史档案）。
- CTO 载体裁：**案一 notify-mailbox 扩展采纳**（案二独立状态文件否=第三真源风险；案三台账联动降为映射层非载体）；状态机主链不动（pending→delivered→read→done），候批语义走 payload.type+target 路由。

## §5 本地域 human in session（BOD 段定稿）
