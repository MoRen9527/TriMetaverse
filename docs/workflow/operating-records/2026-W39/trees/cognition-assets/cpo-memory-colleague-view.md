## 一、命题 1 产品语义：记忆可审计的「记住了啥」四问（双腿各答）

| 四问 | 学习腿（knowledge/） | 运行腿（cognition home） |
| --- | --- | --- |
| 内容可列举 | 四区可遍历（inbox 清单/wiki 页清单/audit 记录） | 私域 namespace 可列举（employee/<席>/） |
| 写入可溯源 | 每页/块回指 inbox sourceId+消化 audit 行 | provider 写入带 namespace+actor+时间（kernel 契约既有） |
| 变更可追溯 | 页版本史+归并块时点（增补件 4 冲突规则承载） | append-only 天然可追 |
| 注入可核对 | 注入页↔wiki 页对应（boot 注入清单可核对） | recall 内容↔namespace 记录对应 |

- 产品红线（对齐 CEO「我们需要知道记住了啥」）：**任何一条被记住的内容，四问必须在两次查询内可答**（与 CTO 信封四问可答原则同一判据）。
- 审计≠读取权：可审计=结构与证据链在，访问权限另归治理（防「可审计」被扩读成「可随意翻」）。

## 二、命题 2 产品语义：colleague 动态化的四个定案

1. **维护者=各席自维护**（协作关系的第一手方）；总助只聚合视图不改写各席条目——与命名/登记正名制同构。
2. **更新触发=事件驱动**（派工/联审表态/收口协作发生即更新），非周期重写——动态=事件驱动增量，非定期快照。
3. **变更留痕**：colleagues.agent.md 静态契约保持「协作原则层」；**动态协作账本**为新增面（落点候选=knowledge/<席>/ 四区外新设或运行腿，候 CTO 技术半部裁）——契约（原则）与账本（事实）分立，账本 append+audit。
4. **审计**：协作账本同用信封（why 强制——每次关系变更指认协作事件）。

**与命题 3 依赖声明**（social 件 §五.2 重申）：colleagues 动态账本=社交事件流最大供源，**先 colleague 后 social** 顺序不变。

## 三、与 CTO 命题 4 的咬合点（三处）

1. 信封 asset 三字段（class/leg/seat）——**leg 字段即双腿裁决的制度化**（认知落点归一方案的 legs 进审计信封，两线咬合）。
2. action 五动词——social 关系状态变更映射 `update`+事件引用；promotion 动词=升格通道（组织知识库）专用，语义与 p2 去域化门一致。
3. 分域不混流——社交事件流（学习腿候选）与运行审计分域照办；my 反编造护栏=信封 why 强制的社交版特化（why 必须指 raw 事件 id）。
