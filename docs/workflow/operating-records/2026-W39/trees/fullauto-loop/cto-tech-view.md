## 一、信箱状态机载体：三案评估——**裁案一 notify-mailbox 扩展**

| 案 | 形态 | 判据 | 裁 |
| --- | --- | --- | --- |
| **一·notify-mailbox 扩展** | letter-store 加候批域：action 增 `submit-approval` 类动词+target 路由扩展（bod/coo）+状态机增候批态段 | **现役复用度最高**——LG-036 全族现成（信箱/poller/confirm 双跳/台账/审计/降级语义）；四问审计（含注入核对）同源；状态机严格冻结版已验 | ✓ **采纳** |
| 二·独立状态文件 | 新 JSON 状态机文件 | 与 letter 台账分裂=同一任务两处状态源（第三真源风险）；催办机器查询又要接它 | ✗ 否 |
| 三·台账联动为主体 | 任务书/台账层状态流转 | 台账=人读面（md/JSON 混合），机器查询/状态迁移/审计弱 | ✗ 作映射层非载体（见下） |

**案一扩展设计（增量最小化）**：
1. **action 词汇扩展**：LedgerAction 增 `submit-approval`（候批信寄出）/`approve`（批毕回流）/`urge`（催办留痕）——状态机主链不动（pending→delivered→read→done 照旧），候批语义走 payload.type+target 路由（bod/coo 双发=CEO「写信箱×2」直译）；
2. **target 路由扩展**：现役 target_seat 硬编码 'bod'（LG-036 MVP）——**扩为 seats.json 名册解析已就位**（消费者切换 baedc02 已做！）——本命题零新增路由代码，配 seats.json 补 coo 可达项即可；
3. **候批信模板**：payload 定型 {任务书锚/候批态发起时点/上游催办链/超时计划}——催办三层各自可从信封直接读；
4. **台账映射层（案三降级使用）**：open-items 台账/任务书状态列与信箱状态**双向映射视图**（COS 催办时人读台账，机器查信箱）——映射关系进 CAO 治理细则（非代码同步——防第三真源，台账列值=信箱状态的投影声明）。

## 二、服务域自动拾取制度化（FADE face 路由 sg 侧活化）

**现状→制度的差距实勘**：sg 值席批次（T-a..T-d）已验证「任务书挂平面→拾取→执行→收口 notify」人工在环可行；制度化=把「值席手拉」变「daemon 轮询/事件自动拾取」。

**制度化三件**：
1. **拾取器**：sg TriMMC daemon cron 项（照 trielc cron 惯例+D-29 无窗格式）周期扫 FADE face 路由平面（faces 目录/watch 清单）新挂任务书→自动拆树开工（值席批次流程脚本化——值席批次的手法已是脚本序，制度化=把脚本序挂 cron+异常告警）；
2. **候批自动信**：收口 notify（现役）追加候批信自动生成（收口态→submit-approval 事件自动发 bod+coo 双箱）——**闭环第①②段无人在环**；
3. **超时催办器**：候批超时阈值（如 24h）→COS 催办事件自动生成（或 COS 台账视图高亮）——三层催办中「BOD 提醒 CEO」段仍 human（BOD human in session 职责），机器只做到「推到 BOD 面前」。

## 三、本地域 human in session 的技术形态

**三面可见（现役复用度 100%）**：信箱（LG-036 letter 流+notify 管线）✓现役／toast（Windows 通知）✓现役／台账（COS 台账映射层）——**本地域零新机制**，只有候批信模板与路由扩展（§一）新增。

**BOD human 职责位**：审批转呈/最终确认/敏感面——技术面=信箱里这三类信**标 human-required 徽标**（payload.required=human），自动化到此为止不越（面隔离语义的人类监督点）。

## 四、§12.4 双向同步衔接

- 服务域自动拾取的收口 notify=§12.4 回流方向的常态化触发器（现役回流解法「拉取→merge 归账→重推」已验证——制度化后回流频率升，watcher 冻结窗（周平面迁移期）照旧优先）；
- 候批/审批状态不进 git 流（状态机在信箱/台账，仓流只管内容）——§12.4 与状态机正交不缠绕。
