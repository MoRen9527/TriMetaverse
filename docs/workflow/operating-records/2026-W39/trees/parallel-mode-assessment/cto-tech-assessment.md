## 一、并行竞态的技术面代价（机制分析）

**竞态机制**：git index 是**单文件共享态**——无行级锁、无事务隔离、无席位命名空间。多席交错 add/commit 时的三类竞态：
1. **staged 段混合**（本席 2 例+被吞 1 例）：A 席 add 后 B 席 commit——A 的 staged 段随 B 的 commit 入库。损害=**归属混乱**（内容无损但作者-内容错配，需声明链修复）；
2. **index.lock 撞锁**（1 例）：瞬时排队重试即解——零损害纯摩擦；
3. **半步态暴露**（注入器 5 漏切族）：多线并行推进时，A 线的中间态（删复制体未换引用）在 B 线的验证窗口内不可见——**不是 index 竞态但同根：并行推进侵蚀验证覆盖假设**。

**损害范围实证（48h）**：归属混乱 3 例（声明链可修复，各 ~5 分钟）/数据损坏 **0 例**（git 内容层无损——损害全在「归属与宣称」层，不触及文件内容）/潜在高危 1 例（5 漏切若遇重启=粮道断，恢复小时级——未爆）。

**防御成本评估**：
- 三招（pipefail/门红禁 commit/staged diff 三查）：部署成本≈零（纪律条+习惯），已拦「己方失误」类——**但防不了他席 staged 混入**（三查能发现混合，不能防混合发生；发现后仍需声明链）；
- 结构性防御候选：**per-seat git worktree**（git 原生——每席独立 index+独立工作树，指向同一仓）——结构性消灭 staged 混合（各席 index 物理隔离），成本=一次配置+合流时 rebase 纪律。**三招不够，结构性防御值得立项**。

## 二、串行+COS 自动化的时延量化

- 串行时延成本：每件过 COS 队列=排队+COS 流转（估 5-10 分钟/件，含往返消息）。今晚并行模式我席完成 **9 线**——串行化=9×7.5 分钟≈**+68 分钟纯排队**（还不算 COS 自身处理带宽成为新瓶颈——COS 单点吞吐）；
- 竞态修复时延实耗：4 例合计 **~40 分钟**（声明/协调/验真）+1 例潜在高危（未爆，若爆=小时级）；
- **净比较**：按今晚实证——并行省 ~68 分钟，竞态实耗 40 分钟+低频高危敞口。表面近似打平，但**分布不对称**：串行时延=每件确定性小额成本；并行竞态=低频大额敞口（一旦爆出粮道断/数据级损害=小时天级）。**期望值相近，尾部风险并行大一个量级**。

## 三、建议：**混合制**（独立域并行+同仓串行/隔离+高危独占）

1. **独立域并行保留**：不同仓/不同树域的线照并行（今晚实证零竞态——TriModel 注入器线 vs TriCompany 认知层线 vs 文档联审线全程无互扰）——并行的收益主体在这；
2. **同仓高频共写→隔离或串行**：TriCompany/TriMetaverse 多席共写仓（今夜竞态全部发生地）二选一：
   a. **per-seat worktree 立项**（结构性解，技术优选——评估一次配置成本后推全）；
   b. COS 串行队列（同仓 commit 请求排队——简单但引入吞吐瓶颈与时延）；
3. **高危操作独占窗**：退役/删除/管线切换类（注入器复制体退役/runtime_baseline 删段类）强制低活窗**独占**（窗内冻结他席对该仓操作——注入器 5 漏切的教训：并行推进侵蚀验证覆盖）；
4. 三招纪律保留（零成本防线不拆）。

**建议优先序**：混合制立即可行（零基建）→per-seat worktree 评估立项（结构性根治，候窗）→纯串行不推荐（放弃并行收益主体换尾部风险，代价不对称）。
