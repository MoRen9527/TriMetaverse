# 任务书 TASK-TREE-NODE-CLOSURE-01：树节点收口心跳＋5 分钟超时催办机制

- **归属**：树协议执行层硬化（候授号 LG-057）；催办执行体与 LG-056 挂载点勘定合流
- **发令**：CEO 2026-09-28 00:34 定稿令（方案 A 修订版；BOD date 现查 00:34+0800 星期一）
- **背景**：LG-056 流转链实测 4 分钟全通（23:52 铸→00:00 汇录，回执 id 全在案），但过程对 CEO 面不可见似断链；催办机制（sg duty-urge-patrol）结构性巡不到「回报断链」类欠件且本机席位间消息链无自动化监督。CEO 定稿：**一整条流转链实际就是 tree 的执行——各节点都要落完成报告，才好故障恢复；机制做好后自动恢复、催办、审计全顺畅自动化**。

## 一、机制设计（CEO 定稿口径）

1. **流转链=树主干，节点强制收口**：铸单（BOD）→流转（COS）→拆派（COO）→执行/回报（承接席）→汇录（COS）→验收销账（BOD）——每个节点完成后**落节点收口件**（轻量：时点＋SendMessage 回执 id＋状态 done；形态=树目录状态行/JSON 片段，与既有「节点收口」概念对齐、硬化为全节点强制）。
2. **每个 T 点勘两件事**：①该节点**是否完成**（收口件在否）；②完成后**是否超过 5 分钟无回报**（后继节点收口件未现即超时）——超时自动催后继责任席。
3. **故障恢复语义**：席位会话重启/断线后，接手者读树节点收口件即知全链进度（哪节点完成/哪节点欠），**从最后收口节点续办**——恢复不靠记忆靠树；恢复 SOP 增补此读树续办步。
4. **可审计**：全节点收口件在树目录=天然审计链；与既有纪律「台账销账必附树指针」自然衔接。

## 二、范围

1. 树协议规程增补：节点收口件强制化＋5 分钟超时规则成文（规程正身落点承接席勘定，与工程纪律册/树协议文档对表）；
2. 巡检器（分钟级）：读树节点状态＋时间戳，超时即 notify 催办——**执行体搭 LG-056 三候选勘定的车**（TriMLC 8713 cron/TriRLC 8711 cron/schtasks，周一读数后落位）；过渡期可先由 sg notify-poller 扩检查项或 COS 会话 cron 顶上（明注过渡身份）；
3. 恢复 SOP 增补：读树续办步；
4. 试点：下一张走全链的新单全节点收口（LG-056 本体已自然符合，可作参照案不重跑）。

## 三、验收锚

- **A1** 试点单全链节点收口件齐备落树，任一时刻读树可知全链进度；
- **A2** 5 分钟超时催办实测一轮（真实或人工制造超时，催办消息+催办对象到位）；
- **A3** 故障恢复彩排：中断一中间节点席会话→接手者读树续办成功（留痕）；
- **A4** 规程增补落笔＋恢复 SOP 步骤入册。

## 四、边界

- 不改 SendMessage 机制本体；节点收口件保持轻量（一行/一片段），不给席位加厚负担；
- 5 分钟自「完成证据出现」（收口件/回执）起算，不含承接席作业时长；
- 巡检器不重复 sg duty-urge-patrol 的挂账催办面（各管各段，注记互认）；
- LG-056 执行体落位前，过渡巡检须明注「过渡」身份，落位后切换并销过渡态。
