## 一、背景（CEO 产品理解纠偏，原话语义照录）

TriModel 的定位是**两面（M 面/R 面）×两域（服务域/本地域）组合出的 4 个角色**——TriMMC、TriMLC、TriRMC、TriRLC 四个域面控制器都应能从 TriModel 拉取配置：

1. **现状错误**：配置页面已做「TriMMC 信息卡」，本应是 TriMMC 拉取配置的板块，却被错误用在 R-HY 的本地配置上——**产品理解的错误**；TriMMC 信息卡应回归本职：用于 TriMMC 域面拉取对应的配置。
2. **扩展**：同样设计 **TriMLC、TriRMC、TriRLC 信息卡**（配置功能项与 TriMMC 卡基本一致），实现四个域面控制器的**独立配置和配置拉取**。
3. **鲁棒性**：「这层故障我们才开始逐层降级兜底，提高鲁棒性」——拉取降级梯在四域面全面铺开。
4. **UI 方向**：一页上下滚动太长则**左侧选项卡菜单栏+右侧单页配置**。
5. **CLI 对齐**：四域面控制器 daemon 的**本地配置命令**随网页配置功能升级配置功能项，对齐配置能力。
6. **质量线（CEO 原话）**：「**要做产品，不要做玩具。不要偷懒。**」

## 一之二、终审纠偏（CEO 2026-09-28 09:34，合审回炉依据）

- **「本地卡」概念整体不成立**：CPO 件「TriRLC·R-HY 本地卡」定名被 CEO 终审推翻——「将来 TriModel 要部署在一台独立的服务器，目前在 R-HY 上是迫不得已，所以没有什么本地卡，**都是远程拉取配置**」。
- **产品语义重定**：四张卡同构=四个域面控制器各自**远程拉取 TriModel 配置**的板块；「本地/远程」不是卡的属性；TriModel 现役部署位（本机 3333/R-HY）皆为**过渡形态**（目标=独立服务器），四卡语义须对目标形态一步到位——未来迁独立服务器只换拉取端点，卡语义零变化。
- 修订面：CPO 件矩阵「配置拉取真源」列统一表述（TriModel 服务端，现役过渡位→目标独立服务器位）；CTO 件 R-HY 迁移线「rlc 卡」建卡语义同步修订（TriRLC 域面拉取卡，非本地卡）；凡「本地卡/本地域卡」表述全案清除。

## 一之三、终审二次纠偏（CEO 2026-09-28 10:04，角色↔机位映射纠正）

- **河源那张卡应为 TriRMC**（非 TriRLC）：R-HY 机的域面控制器=TriRMC（R 面·服务域，周平面迁移 cron 现役在河源即其证）。
- **本机上两个才是 TriRLC 和 TriMLC**：TriRLC（8711）与 TriMLC（8713）现役同寄居 dev 机——**条件所限的过渡形态，未来两者分开部署到不同的本地 PC**。
