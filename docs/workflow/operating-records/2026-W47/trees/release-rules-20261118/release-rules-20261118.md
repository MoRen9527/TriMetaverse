## §一 · 版本定义与需求明确标准（裁点①）

1. **版本=已审需求集合的切窗收敛单位**：一个版本的需求集合，来源唯一=周日需求评审通过（转任务）的任务集合（notice-175①门同向）——未经评审的需求不入任何版本（只轻挂公司需求池·`../../company-demand-pool.md`）。
2. **「版本需求明确」标准=验收锚级**（CPO 裁定）：每版本出门带锚清单+每条验收方式——版本任务书批立时，集合内每条任务须有可验锚（锚清单+验收方式+销账条件），无锚任务不批立。
3. **不可测判据不得入冻结**（CPO 裁定）：审定后发现判据不可测=回任务书改可测形再批立，不随冻结带入版本。
4. **附表位①·版本需求七字段模板**（CPO 素材·候落卷并入如实注）。

## §二 · 需求冻结与新增需求路由（裁点②）

1. **冻结时点=版本任务书批立时点**（CPO 裁定）：批立动作即已审需求集合的冻结线——批立前评审通过的全部在集，批立时未入集的一律不在本版。
2. **冻结后新增需求路由**：轻挂公司需求池→周日评审→转任务入**下一版**候选集（notice-175①同向·不插队不扩窗）。
3. **例外准入仅两类**（CPO 裁定·CPO 确认留痕·不重开冻结）：①安全/合规风险 ②生产阻断缺陷。
4. **例外准入≠跳流程**（CPO 修正裁定）：P0 Bug 照 v0.9.x plan §三 L3 全流程走线——**patch 提速不跳步：即时启动全流程**（dev 修复→main→构建→安装版更新·禁热补丁真源援引 plan §三 3.5）；spawn 细化稿「hotfix 即时发」条作废（修正案留痕）。
5. **附表位②·边界例六条**（CPO 素材·合并时以禁热补丁裁定为准·候落卷并入如实注）。

## §三 · 发版节奏（裁点③）

1. **双轨对齐**（CPO 裁定）：prod 周级 Release 延续（真源=v0.9.x plan §三 3.1 节奏表）且与周日评审节律对齐——**周日评审通过需求集合=下一版候选集，周级窗发版**；dev 天级迭代照旧=非发版面。
2. **不为发版而发版**（CPO 裁定）：有验收增量才立版——候选集为空即顺延，零增量不发空版。
3. **技术交付线并轨**：FADE-002（现役发布管线实例）承接技术交付面，**不新增固定窗**——本规则只定版本规划层（什么进版本/版本怎么切/节奏怎么定），交付管道层照 plan §三 既有（禁热补丁/dev→main→构建→安装版全流程/安装版滞后 ≤2 周）不变。
