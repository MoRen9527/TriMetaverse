## 一、三层最小实现的产品定义（白皮书新表述建议）

### 1.0 总判断：同一份缺口清单的两种读法

【实证】R2 盘点 agent-core 缺五项：daemon 抽象、会话存储、上下文聚合、多 agent 运行时注册表、跨节点可见性。
【实证+推断】CEO 三层定义恰好把这份清单一分为二，且两半都是既有资产归类、不是新工作量：

- 元虚拟"不做"清单=宿主原生能力清单：会话生命周期、自研 loop、上下文聚合、多 agent 调度治理、跨节点可见性——全部归宿主（R1 实证：服务器 claude code 路径零 agent-core，会话归官方 claude 的 ~/.claude，主控侧只持内存快照）。
- 元现实自研 backlog=五项中"必须自持"的生产面：会话持久化、权限与审计、调度、无人值守（R2 实证 TriLC 已有 SQLite 会话存储、tier 权限、cron 全家桶、心跳会话）。

产品含义：印证 R3"工程不换、叙事分层换"——白皮书修订是重新归类叙事，不是重写承诺。

### 1.1 元虚拟系统=TriMMC+TriMLC：成熟虚拟研发环境

推荐表述（可直接入 §3.1）：

> 元虚拟系统的最小实现是 TriMMC（元虚拟主控，服务器端成熟宿主环境）+ TriMLC（元虚拟本地控制器，本地研发仓宿主），两者经 bridge 通信构成一个宿主可整体替换的成熟虚拟研发环境：当前宿主为 claude code，未来可整体切换为 codex 或其他成熟 agent 宿主而不改变系统定义。元虚拟不自建会话管理与执行内核——会话、loop 与上下文直接使用宿主原生能力；元虚拟只负责两件事：把员工定义（合同/五件套）经 FADE 发布线灌入宿主，以及把实验成果落盘到元认知仓。它回答"在不伤害现实的前提下怎么试"。

最小实现边界（白皮书可列明的"不做"清单）：

1. 不做会话生命周期管理——归宿主原生（R1 实证）。
2. 不做自研 agent loop——元虚拟侧零 agent-core；这是"整套换 codex 不影响"的技术根据（R1 实证服务器双路径完全隔离无互调）。
3. 不做跨 agent 上下文聚合——各会话归宿主各自管理。
4. 不做多 agent 运行时注册表与调度治理。
5. 不做跨节点可见性——属元现实议题（R2 实证现状为零，R4 范围）。

边界原则一句话：宿主能做的绝不自研；宿主做不到且必须做的，先评估换宿主，仍做不到才进元现实自研 backlog。"成熟虚拟环境"的产品价值正是避免与宿主赛跑。

【实证·既有叙事资产】白皮书图 3-3 已把"OpenCode / Claude Code / Codex 编码 Worker"并列为本地 Worker（tmv-whitepaper.md:393）——宿主无关叙事在白皮书内已有先例，本次是把既有措辞升格为系统定义。

### 1.2 元现实系统=TriRMC+TriRLC（共用 agent-core）：自研工程面

推荐表述：

> 元现实系统的最小实现是 TriRMC（元现实主控）+ TriRLC（元现实本地控制器），两者共用自研内核 agent-core：会话、调度、权限、cron、进程监督与审计由自研代码掌控，不依赖任何单一宿主。元现实承接所有必须自持的生产面——稳定执行、无人值守、权限审计与跨节点协同。

与元虚拟的职责分界线（一句话）：

> 元虚拟消费宿主（能力上限=所选宿主，可整体换宿主），元现实自研内核（能力上限自己掌控）；元虚拟验证"什么值得做"，元现实保证"稳定地做出来"。

资产盘点【实证】：元现实最小实现的主体资产已存在——TriLC daemon 全家（未来 TriRLC）与 agent-core 内核（loop/工具/权限/sub-agent/合同/cron/进程监督，R2 九模块清单）均现成；新建面是 TriRMC。
【推断·供 R4 参考】TriMC 的自研 loop 路径（R1 路径 B：loop+cron+contracts+onboarding 装配）是 TriRMC 的天然候选胚子；以其为起点还是全新建模块，属 R4/R6 决策，产品侧不预定。

### 1.3 元认知系统=项目代码仓：最薄但承重

推荐表述：

> 元认知系统的最小实现就是项目代码仓本身——三层中唯一没有运行时的层，也是三层共同的承重底座：元虚拟的员工定义与实验成果以代码和文档落仓，元现实以 worktree 方式消费仓中事实，并把生产中的需求与缺陷回写为新的实验输入。仓的版本历史就是"我们如何解释与预测"的结构化沉淀；双向螺旋的每一跳都以仓为唯一中转，所有跨层流动都在这里留下可审计的 git 痕迹。

"最薄但承重"的展开：无运行时、无服务，但免费获得四项能力——版本、审计（log/blame）、隔离（branch/worktree）、协同（merge/PR）。
【实证·先例】五维同步的传输载体已经是 TriCompany git 仓本身（R2 五：bundle→git commit→push→服务器工作树读取）——"仓承载数据流"已在现实运转，本定义是把它升格为正式架构层。

### 1.4 三层问答句式全部保留（换轨升级的关键文本证据）

【实证】附录 B 三层词条的问答式定义：元认知"它回答'我们如何解释与预测'"、元虚拟"它回答'在不伤害现实的前提下怎么试'"、元现实"它回答'世界现在是怎样运转的'"。三个问题与最小实现完全兼容——研发环境就是"怎么试"的当前最佳实例，项目仓就是"如何解释与预测"的当前载体，自研工程面就是"稳定运转"的当前承接。新定义不推翻任何一个问题，只是给每个问题补上当前实例。这是"同名换轨升级、非全新"（R3 判断）在白皮书文本层的直接证据。

## 二、双向螺旋语义边界

### 2.1 两个方向的产品语义

- 虚拟→现实（成熟移植）：元虚拟环境跑通的方案，制定移植方案后在元现实（TriRMC+TriRLC）实现同类能力。CEO 例句：周工作平面在 TriMMC+TriMLC 跑通→方案整体移到 TriRMC+TriRLC 上跑。
- 现实→虚拟（需求重放）：元现实的需求、缺陷与事故，作为重放任务进元虚拟环境快速实验；实验产物经评审后才回元现实。

统一语义：螺旋不是自动数据流，是"人工判断+仓为载体"的受控流程；每一跳的两端都落在元认知仓（方案进仓→worktree 消费→成果回仓）。自动判定是远期演进项，白皮书不写成现状。

### 2.2 "实验成熟可移植"判定标准（建议，全满足才启动移植）

1. 复现性：连续≥2 个完整运行周期重放成功、无未解释偏差——接续白皮书 §8.1 阶段 0 验收门禁"评测可复现（同一任务输入在同一版本下可重放对比）"既有口径，不发明新标准。
2. 产物落仓：方案/流程/配置已以文档与代码进入项目仓受保护分支，重建不依赖任何会话记录。
3. 依赖显式化：宿主能力依赖（tools/skills/MCP/模型）逐项列出，且每项有元现实承接路径或明确降级方案。
4. 验收先行：移植前写好"元现实版跑通"的可验证验收条件与回退方案。

治理注：移植决策走既有门禁（TriCompany 签核/IPD 流程），本标准嵌入既有评审，不新增流程层。

### 2.3 与白皮书 §1.3/§3.1 增长螺旋的接续关系

【实证】§1.3 创新点 2 原文"构建'元认知—元虚拟—元现实'三元联动系统，打通虚拟试验、现实生产力提升与认知迭代的增长螺旋"；§3.1 螺旋迭代链"元现实（规则与数据约束）→元认知（建模与假设）→元虚拟（沙盒仿真与并行试验）→回灌元现实"。
判断：新双向螺旋是同一螺旋的系统实例化——"虚拟试验"=元虚拟环境实验、"现实生产力提升"=元现实工程面、"认知迭代"=仓中沉淀；CEO 两个方向=同一环的两段弧，方向、环节、顺序全部一致。
修订动作：两句原文均保留不动；仅在 §1.3 创新点 2 后可选加"（最小实现见 §3.1）"交叉引用。

### 2.4 CEO 例句的表述校准点

【推断·校准点】CEO 例句"周工作平面现在在 TriMMC 和 TriMLC 就能跑通"：现状周平面主执行面在 TriLC daemon cron（TRILC_WEEKLY_PLANE_ROOT，R3 影响面 A 类实证）。例句若入白皮书，需校准为能力断言（"周平面可在元虚拟环境跑通"）而非现状断言，或待 R4 确认宿主侧承载现状后定稿。另注：该例句隐含"周平面执行面上移到宿主侧"的迁移——方向恰是从元现实 daemon 上移到元虚拟宿主，可作为双向螺旋的第一个示范件（供 R6 排期参考）。

## 四、命名定名建议

### 4.1 TriMLC vs TriModel（R3 判定混淆风险最高）

选项评估：

- 改别名 TriMVLC：否决。M/R × MC/LC 的 2×2 对称（元虚拟对/元现实对）是四名方案的核心记忆点；为避一次碰撞引入第三套构词法，破坏对称且再添一个需要解释的名字。
- 文档锚定声明：推荐，作为主方案。
- 前缀/读法约定：采纳，作为锚定声明的内容之一。

推荐方案（三层落地，全部产品面、零代码改动）：

1. 架构文档 §5"命名与别名治理"新增消歧条目（同节已有 TriGateway↔TriGatway alias 维护制度先例）：明确 TriMLC（元虚拟本地控制器，系统模块）≠TriModel（Provider/Model 配置层，npm: trimodel）。
2. 白皮书附录 B 两词条互指"勿混淆"；语域口径：TriModel=组件层（模型配置），TriMLC=系统层（元虚拟本地腿）。
3. 口语读法约定写进命名治理条目：TriModel 读"Tri-Model"（2 音节），TriMLC 拼读"Tri-M-L-C"（4 音节）——音节可分，口语可治理。

支撑理由【实证 R3】：四名全仓零占用（八变体 grep 0 处）；TriModel 与 TriMLC 语域不同、同时活跃但使用面不同。碰撞可治理，不必避让。

### 4.2 TriMMC/TriMC（及 TriRLC/TriLC）过渡期并存策略

产品面要双名过渡期。三条规则：

1. 新叙事面（白皮书、架构文档、各 registry）即刻用新名，首次出现处标"（原 TriMC，2026-08 更名）"式括注。
2. 兼容面不动、归 R6：npm bin（trimc/trilc）、安装目录、NSSM 服务名、schtasks 任务名、TriPilot settings 键（trilc-direct 等已持久化于用户 settings.json，R3 C 类）、CI 路径与产物名（R3 B 类）——产品面双名≠立即改 bin；这些改名有装机态二次迁移成本（R3 F 类推断），必须单独排批。
3. 架构文档 §5 增 alias 映射制度：TriMMC↔TriMC、TriRLC↔TriLC（历史名保留为兼容路径名——直接复用 TriDeployment→TriAuto、Tride→TriCode 先例与 install-tricade.ps1 的 -MigrateLegacy 机制）。

过渡终点：触发式而非时间式——R6 改名批次落地+存量装机迁移完成即收；终点条件写进 alias 条目，防止双名无限延长（新名立不住的风险）。

## 五、理念叙事风险：游戏化虚拟世界/数字生命体/星球城市怎么办

三个选项评估：

- 删除：否决。【实证】数字生命体 NFT 是 §5.1/§5.4 与 §7.2 MVP 条目 2/9 的机制组件；《派客帝国》是 §1.1 愿景与 §2.2 叙事主线——删除是牵动通证经济与学院 MVP 的大手术，伤愿景咬合。
- 移入远期愿景附录：否决。叙事散布 10+ 处且与通证机制耦合，物理搬移成本高且搬不干净，还会打断章节逻辑。
- 保留为无标注平行叙事：否决。读者无法区分"现在是什么"与"未来是什么"，违反"不把规划写成现役"护栏——这正是本次修订要修的病根，不能修一半。
