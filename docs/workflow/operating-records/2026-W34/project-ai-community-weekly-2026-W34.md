## 2. 本周观察到的大模型能力问题与体验

### 2.1 长工具链会话的收尾退化：模型把工具调用"写成文字"而不是真的调用

- 现象：
  用 DeepSeek v4 pro 承载总助角色的多步核查任务（一场 15~40 次真实工具调用），会话尾段模型不再发真正的函数调用，而是把工具调用协议**当成正文文本写出来**，然后停在那里。用户等了几分钟，看到一堆工具卡和一段叙述，最后没有结论。
- 具体表现：
  连续十轮 CEO 实测，模型每场会话发明不同的"伪工具文本"变体：
  1. `[tool_use name=Read]`——方括号族；
  2. `[｜｜DSML｜｜tool_use LS]`，以及无限重复的 `</｜｜DSML｜｜parameter>` 闭合标签（单回合流式刷屏数分钟，观感如死循环）；
  3. `<invoke name="shell_exec"> <parameter name=...>`——XML 族（Qwen 风格调用语法）；
  4. `[调用 shell_exec] {"command": ...}`——学舌宿主 UI 自己的文案造的变体。
  另有两种"无语法"退化：工具后**纯静默**（叙述→工具→沉默）；**纯承诺式结尾**（"最后确认一下 git 工作区"——说要做什么但什么都没做也没结论）。
  根因两层：模型侧是长多轮工具对话后的格式漂移（工具调用格式在上下文里高度富集，生成分布"溢出"到正文通道），同场会话稳定复现，不是随机故障；系统侧是我们初版成功门禁只统计"累计输出文本长度"，叙述和伪文本都算"有产出"，把退化判成了成功。
- 解决方案：
  在 daemon（单一执行体，对两个入口透明）建三层防御：
  1. **流中掐断**：每个回合的流式增量一旦匹配到伪工具语法，立即终止本轮事件循环、停止转发后续垃圾文本，用干净的对话重建进入收尾；
  2. **结构化检测**：所有变体收敛为两族"形状"——方括号族（`[短标签] 紧跟 JSON 载荷`，字符类排除代码下标形态）和 XML 族（`<(tool_call|invoke|parameter|function_call)`）——按形状匹配后模型换任何拼写都逃不掉；
  3. **强制收尾**：检测到无结论（静默/伪文本/承诺式结尾）时，用重建的对话历史额外调一次模型且**不传工具列表**——模型物理上无法再工具调用，只能产出结论文本。
- 问题影响：
  不修的话，Agent 的每场多步任务都有概率"空转完毕"——这是人机协作产品可用性的硬伤。修复后连续三轮实测无逃逸。防御涉及的关键原理：对抗性输入要匹配"结构不变量"而非表面拼写（同 SQL 注入从关键字黑名单进化到参数化查询）；流式协议已发送的帧无法撤回，防御目标是泄漏最小化+明确分隔；不给工具列表是结构约束，比"请不要调用工具"的恳求式提示可靠一个数量级；启发式误伤代价只是一次额外收尾调用时，启发式优于不设防。

当前经验：

- 项目经验：模型行为防御做在 daemon 单一执行体上（两入口零改动受益）；每轮修复必须配 live 复现和反例单测（我们的检测正则维护了 14 条用例，其中 6 条反例防误伤正常结论）。
- 模型自查：遇到"模型调完工具没有最终结论"类反馈时，先查服务端门禁是否被"有文本"骗过，再查模型是否在文本里模拟工具调用；不要假设模型自然会收尾。

### 2.2 这族问题牵出的五个配套工程缺陷（每个都值得自查）

- 现象：
  修复主问题的过程中，连环暴露出五个独立缺陷，共同点都是"跨层契约想当然"。
- 具体表现：
  1. **文本翻倍**：运行时每轮同时发流式增量和完整消息两个事件，daemon 无条件都转发——面板每句话收到两遍；
  2. **工具卡永远"运行中"**：客户端开始事件用随机 UUID、结束事件用会话短 ID——永远配不上，状态从不翻转；
  3. **工具耗时恒 0ms**：上游事件不带耗时字段，daemon 兜底 `?? 0`——"缺字段"被静默变成"合法的 0"；
  4. **Windows 中文乱码**：cmd.exe 中文输出是 GBK 编码，工具层按 UTF-8 解码成乱码；
  5. **参数展示退化**：工具参数是 JSON 字符串，经两层 stringify 后解析回字符串，逐字符索引展示（`LS: 0: {, 1: "`）。
- 解决方案：
  逐个修复：按轮去重标志；daemon 事件携带生产侧真实 id 两端配对；daemon 按调用起止时间戳自计耗时；严格 UTF-8 解码失败回退 GBK；daemon 发送前解析成对象+客户端双层解析防御。
- 问题影响：
  单看都是小毛病，叠加起来让"工具调用透明化"完全不可用。五个缺陷的共性教训：**流式+批量双通道必须有幂等合并点；异步事件关联必须用生产侧稳定 id；跨层字段契约要验证真值，`?? 默认值`会掩盖缺字段；跨进程文本必须显式编码协商；结构化数据尽量在源头定型，别让消费侧猜。**

当前经验：

- 项目经验：修一族问题时顺手做"契约审计"——同一条链路上的 id、耗时、编码、格式逐项过一遍，通常能连带挖出几个潜伏缺陷。
- 模型自查：写 `?? 默认值` 前先确认上游事件确实有这个字段；跨进程读文本先问编码是什么。
