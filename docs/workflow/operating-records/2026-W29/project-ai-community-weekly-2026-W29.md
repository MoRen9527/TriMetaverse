## 2. 本周观察到的大模型能力问题与体验

### 2.1 Copilot CLI 与 DeepSeek 在长会话压缩时重放空 assistant 消息并返回 400

- 现象：
  在 Copilot CLI `1.0.71` 中使用自定义 OpenAI Provider 接入 `deepseek-v4-pro`。普通新会话能够正常回复，但长会话达到自动压缩阈值后，后续消息稳定返回 `400 Invalid assistant message: content or tool_calls must be set`。
- 具体表现：
  现场日志显示，DeepSeek 曾把一段完整的最终答复放入扩展字段 `reasoning_content`，而标准 `content` 为空，结构化工具调用列表也为空。Copilot CLI 仍把该轮当作成功消息持久化。下一次会话在约 `40,101` 个 conversation tokens 时启动自动压缩，压缩请求重放了这条既无正文又无工具调用的 assistant 历史，DeepSeek 随即以 HTTP 400 拒绝。使用同一 CLI、同一模型和同一 Provider 新建无历史对照会话，只要求回复 `OK`，请求成功，证明问题不在网络、密钥或模型服务整体可用性，而在 reasoning-only 消息的持久化与压缩兼容链。类似故障若发生在连续工具编辑中，会中断后续步骤，并可能在本地工作树留下尚未完成、尚未验证的部分改动。
- 解决方案：
  当前先停止恢复已经包含坏历史的会话，改用全新会话，并通过会话摘要、工作树差异和窄范围测试恢复任务现场。长 Agent 任务暂时控制单会话长度；关键编辑后及时检查 `git diff`、类型检查和相关测试。上游修复方向应是在消息持久化、恢复和压缩前，拒绝、丢弃或规范化 `content` 为空且 `tool_calls` 为空的 assistant 消息；若有效答复只存在于 `reasoning_content`，适配层也不能把它作为空标准消息继续重放。
- 问题影响：
  该问题影响自定义 Provider 下长时间 Agent 工作的连续性、工具调用可靠性和会话恢复能力。它不会直接修改已提交或已发布产物，但可能让一次多步骤编辑停在中间状态；如果操作者把 400 当作普通网络抖动后反复恢复，容易遗漏半成品改动和构建错误。它也说明“兼容 OpenAI Chat Completions”不等于已经覆盖 reasoning、工具调用、自动压缩和恢复等完整 Agent 协议。

当前经验：

- 项目经验：
  评估第三方模型的 OpenAI 兼容性时，不能只做单轮聊天和简单工具调用测试，还要覆盖长上下文阈值、自动压缩、工具调用后的最终答复、会话恢复以及中断后的工作树一致性。出现会话层 400 后，先用同配置的新会话做最小对照，再检查原会话最后一条 assistant 消息和项目工作树，能够快速区分服务故障、历史消息损坏与项目代码问题。
- 模型自查：
  后续 Agent 在接手异常中断的任务前，应先确认工作路径、未提交差异和最近验证结果，不要直接从自然语言“继续”推断代码处于完整状态。若宿主暴露的历史消息同时缺少正文和工具调用，应将其视为协议异常并停止恢复，而不是继续把坏消息带入压缩或下一轮请求。

### 2.2 DeepSeek reasoning_content 空投的成因深度分析

经深入排查，该问题涉及 DeepSeek 推理模式下的三个已知机制叠加：

- **成因 1 — 推理链连续性要求**：DeepSeek 推理模型要求对话历史中所有 assistant 消息都必须携带 `reasoning_content` 字段（即使是空字符串）。若历史消息中该字段缺失，会打断连续推理链，导致模型将本该输出到 `content` 的内容全部写入 `reasoning_content`，最终返回空的 `content` 字段。
- **成因 2 — 中间件剥离**：部分中间件（如 OpenAI 兼容 SDK 的消息转换逻辑）会在历史消息重放时自动剥离 `reasoning_content` 字段，触发上述错位问题，尤其在涉及工具调用的多轮对话中更易出现。
- **成因 3 — `<think>` 标签冲突**：部分客户端会把推理内容包裹在 `<think>` 标签内塞进 `content` 字段，和 DeepSeek 要求的字段结构冲突，间接引发字段错位。

**典型修复方案**：
1. 确保所有历史 assistant 消息都保留完整的 `reasoning_content` 字段，不要在消息转换环节随意剥离。
2. 针对工具调用场景，使用代理层/Pipe 函数自动从 `content` 的 `<think>` 标签中提取推理内容，回填到顶层 `reasoning_content` 字段，避免触发 400。
3. 流式请求必须完整消费所有响应块，直到收到 `finish_reason=stop` 的终止块，避免提前终止读取导致误判 `content` 为空。

**TriMC 工程要求**：TriMC 作为自建 Agent Loop 引擎，在实现消息持久化、会话压缩和恢复时，必须从设计层面避免 Copilot CLI 的这个错误——不能把 `reasoning_content`-only 的空 `content` 消息当作合法 assistant 消息持久化或重放。此要求已录入本周待办，由 CPO/CTO 联合设计验收。

## 3. 本周有效做法

- 使用同一 CLI、同一模型、同一 Provider 的全新会话做最小对照，快速排除网络、密钥和模型服务整体故障。
- 同时核对会话事件、压缩触发点与本地工作树，把“协议错误”和“项目实际影响”分开判断。
- 对异常中断后的工程任务执行窄范围类型检查，确认是否留下了新的构建错误，而不是仅凭会话报错推测影响。

- 长会话异常中断后，如何把会话恢复与工作树恢复组合成可自动执行的安全检查？
