### 产品判断

当前最简可验证模型 = **TriMC（入口）→ TriModel（路由）→ TriStaciss（对外计费）→ Provider** 一条链。这 4 个模块构成当前阶段唯一的可交付产品面。

### 最简模型定义

```
用户入口 (Copilot-host)
    │
    ▼
TriMC ─── Agent Loop + 内置工具 (read/write/edit/shell/glob/task)
    │
    ▼
TriModel ─── 协议层：统一 Chat/ToolCall/Stream 接口
    │          Provider 层：DeepSeek (主力) → TriStaciss (fallback)
    │
    ▼
TriStaciss ─── 对外 Credit 计费层（Provider 角色）
    │           消费 TriMetaverse 自产模型 → 向外部客户端计 Credit
    │
    ▼
Provider ─── Anthropic / OpenAI / 自产模型 / 其他第三方
```

### 验证指标（MVP 验收门禁）

### Q1：回退策略 — Copilot-host = 始终热备

#### 产品模型

**Copilot-host 在 TriMC 成为正式宿主后不被下线、不被降级、不被移除。它作为 always-warm standby 持续运行。**

```
         ┌──────────────────────┐
用户 ──→ │   入口路由层         │
         │  (active_host flag)  │
         └──────┬───────────────┘
                │
         ┌──────┴──────┐
         ▼              ▼
   ┌──────────┐   ┌──────────┐
   │ TriMC    │   │Copilot-  │
   │ (active) │   │host      │
   │          │   │(standby) │
   └──────────┘   └──────────┘
         │              │
         │    ┌─────────┘
         ▼    ▼
   ┌──────────────────┐
   │ contract YAML    │
   │ (统一规格层)      │
   └──────────────────┘
```

**回退 = 修改 `active_host` 标志，将入口路由指回 Copilot-host。不涉及 agent 迁移、代码转换或数据搬迁。**

#### 回退触发条件（产品定义，CTO 实现检测）

| 触发条件 | 检测方式 | 回退动作 |
|----------|----------|----------|
| TriMC Agent Loop 连续失败 N 次 | 健康检查端点 | 自动回退（无需人工确认） |
| TriMC 输出与 Copilot-host shadow 输出偏离 > 阈值 | Shadow comparison | 告警 → CPO/CTO 评估 → 手动回退 |
| TriMC 部署崩溃 / 不可达 | 心跳超时 | 自动回退 |
| 用户报告 TriMC 行为异常 | 用户反馈 | CPO 评估 → 手动回退 |

#### 回退速度要求（产品 SLA，CTO 实现）

- **自动回退**（健康检查触发）：≤ 60 秒
- **手动回退**（人工裁决后）：≤ 5 分钟
- **回退期间状态处理**：TriMC 未完成的操作丢失，用户需重新触发（接受）

#### 回退后恢复流程

```
回退到 Copilot-host
    │
    ├─ 1. 确认 Copilot-host 正常运行（健康检查）
    ├─ 2. TriMC 进入诊断模式（不接收流量，只做根因分析）
    ├─ 3. CTO 修复 TriMC → 本地验证 → 部署到服务器
    ├─ 4. TriMC 重新进入 shadow 模式验证 ≥ 3 轮
    └─ 5. CPO/CTO 联合 APPROVE → 切回 TriMC active
```

**关键原则：回退不是失败，是设计内的安全机制。TriMC 的每一次回退都是成熟度信号，不是项目倒退。**

### Q2：代码安全 — 单一写入主控

#### 产品模型

**任何时刻，只有一个 Host 对 TriMetaverse 仓库拥有写入权。这是操作系统/文件系统级别的硬约束，不是约定。**

```
                     TriMetaverse Git Repo
                     ┌──────────────────┐
                     │   Write Master    │
                     │   (有且仅有 1 个)  │
                     └────────┬─────────┘
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
        Copilot-host     TriMC(local)    TriMC(server)
        
        当前 Active → Copilot-host 持有 Write Master
        未来 Active → TriMC(server) 持有 Write Master
        Copilot-host 降为 Read-Only
```

#### 三阶段写入权模型

| 阶段 | Write Master | Copilot-host | TriMC(server) | TriMC(local) |
|------|-------------|-------------|---------------|-------------|
| **当前（Phase Now）** | Copilot-host | ✅ Read/Write | ❌ 不存在 | ✅ 独立演练场 |
| **Shadow 验证（Phase Shadow）** | Copilot-host | ✅ Read/Write | 📋 Read-Only（shadow 输出写入隔离区） | ✅ 独立演练场 |
| **Canary 灰度（Phase Canary）** | Copilot-host | ✅ Read/Write（主） | 📋 Read-Only（验证用） | ✅ 独立演练场 |
| **TriMC 正式宿主（Phase Production）** | TriMC(server) | 📋 Read-Only（热备） | ✅ Read/Write | ✅ 独立演练场 |

#### Shadow 模式的代码安全

Shadow 模式的最大风险：TriMC 在 shadow 验证时需要"假装"修改代码来验证能力，但不能真的修改生产仓库。

**解决方案：Shadow Workspace（隔离工作区）**

```
TriMetaverse/           ← Copilot-host 写入（生产）
    ...

/tmp/triMC-shadow/       ← TriMC shadow 工作区
    TriMetaverse.git/     ← 生产仓库的 clone/checkout
    shadow-traces/        ← TriMC 的操作日志和 diff
```

- TriMC 在 shadow workspace 中执行完整操作（包括写入）
- Shadow workspace 是生产仓库的独立副本，写入不影响生产
- 对比引擎：比较 Copilot-host 生产输出 vs TriMC shadow 输出的 diff
- Shadow 验证通过标准：连续 N 轮 diff 一致率 ≥ 95%

**本地 TriMC 的隔离**：本地 TriMC 始终操作自己的开发副本，永远不直接操作生产仓库。代码从本地到生产的流动必须经过 git push → PR → merge 的标准流程。

### Q3：三轨协作模型

#### 环境定义

```
┌─────────────────────────────────────────────────────────┐
│                    三轨金字塔                             │
│                                                         │
│                    ┌──────────┐                          │
│                    │Copilot-  │  ← 生产层（唯一 Write    │
│                    │  host    │     Master，用户直接交互） │
│                    └────┬─────┘                          │
│                         │                                │
│                    ┌────┴─────┐                          │
│                    │  TriMC   │  ← 预发布/灰度层          │
│                    │ (server) │     Shadow → Canary →    │
│                    └────┬─────┘     Production           │
│                         │                                │
│                    ┌────┴─────┐                          │
│                    │  TriMC   │  ← 开发/演练层            │
│                    │ (local)  │     独立副本，不影响上层   │
│                    └──────────┘                          │
└─────────────────────────────────────────────────────────┘
```

#### 能力迁移流水线（五阶段）

```
Stage 1: 本地验证
  TriMC(local) 通过全部单元测试 + 集成测试
  ↓ Gate: CTO 审查通过

Stage 2: 服务器 Shadow
  TriMC(server) 部署 → 消费与 Copilot-host 相同的输入
  → 在隔离 workspace 中产生 shadow 输出
  → 对比引擎 diff 生产输出 vs shadow 输出
  ↓ Gate: 连续 N 轮 diff 一致率 ≥ 95% + 0 critical 偏差

Stage 3: Canary 灰度
  路由层将 X% 的新会话分配给 TriMC(server)
  Copilot-host 继续处理其余流量
  → 实时对比两者输出
  → 用户可感知差异时触发告警
  ↓ Gate: Canary 窗口期内 0 用户报告异常 + 自动回退未触发

Stage 4: 全量切换
  active_host → TriMC(server)
  Copilot-host → standby（持续运行，健康检查心跳）
  ↓ Gate: 全量运行 ≥ 1 周 0 自动回退

Stage 5: 稳定运行
  正常运营，Copilot-host 保持热备
  TriMC 迭代走 Stage 1→4 的缩略版（本地→Shadow→Canary→全量）
```

#### 三轨之间的数据流

| 流向 | 内容 | 频率 | 约束 |
|------|------|------|------|
| Copilot-host → TriMC(shadow) | 用户输入 + 上下文（session prompt） | 实时 | 只读，不写回 |
| TriMC(shadow) → 对比引擎 | shadow 操作日志 + diff | 每轮 | 存储在隔离区 |
| 对比引擎 → CPO/CTO | 一致率报告 + 偏差列表 | 每日 | 异常自动告警 |
| TriMC(local) → TriMC(server) | 新版本代码 | git push + deploy | CTO 审查 |
| TriMC(server) ← health check | 心跳 + Agent Loop 状态 | 每 30 秒 | 超时 → 自动回退 |

### 更新后的关键原则（CPO-008 四条 + 新增三条）

5. **Copilot-host = always-warm standby**：TriMC 成为正式宿主后，Copilot-host 不被下线、不被降级、不被移除。回退是设计内的安全机制。
6. **单一写入主控（Single Write Master）**：任何时刻有且仅有 1 个 Host 对 TriMetaverse 仓库持有写入权。这是文件系统级硬约束，不是君子协定。
7. **Shadow 隔离**：TriMC shadow 验证在独立 workspace（clone/checkout 副本）中执行，永远不触碰生产仓库，直到正式切换且写入权移交。

## CPO-010：入口路由层 + active_host flag 产品架构详述（CPO 小乔，2026-07-14）

> **状态**：✅ 完成 | **触发**：CEO 要求展开 CPO-009 中的入口路由层设计
> **关联**：CPO-009 §Q1（回退策略的工程基础）

### 核心洞察：Copilot CLI 不可修改

入口路由层设计的**第一约束**：我们无法修改 GitHub Copilot CLI 本身。所有路由逻辑必须在 Copilot CLI 的扩展机制内实现。

当前 Copilot CLI 的扩展点：
- `.github/agents/*.agent.md` → agent 定义
- `.github/prompts/*.prompt.md` → 命令定义
- `.github/instructions/*.instructions.md` → agent 行为约束

**Copilot-host 的 agent 永远是用户入口。路由层的职责是：让 Copilot-host agent 决定「自己处理」还是「转发给 TriMC」。**

### 产品架构

```
                         用户
                          │
                          ▼
              ┌──────────────────────┐
              │   GitHub Copilot CLI  │  ← 不可修改
              │   (用户界面层)         │
              └──────────┬───────────┘
                         │ 加载 agent.md
                         ▼
              ┌──────────────────────┐
              │   Copilot-host Agent  │  ← 永远运行，不可绕过
              │   (e.g. 小乔/小狄)    │
              └──────────┬───────────┘
                         │ 读取 active_host flag
                         ▼
              ┌──────────────────────┐
              │   入口路由层           │  ← CPO-009/010 定义的核心
              │                       │
              │   active_host flag    │     一行配置，两种模式
              │   health check        │     自动检测 + 自动切换
              │   fallback logic      │     故障时自动降级
              └──────┬───────┬───────┘
                     │       │
            active = │       │ active =
            copilot  │       │ triMC
                     ▼       ▼
         ┌────────────┐  ┌──────────────┐
         │ Agent 本地  │  │ Agent 转发    │
         │ 执行模式    │  │ (Passthrough) │
         │             │  │              │
         │ 直接处理    │  │ HTTP → TriMC  │
         │ 读写项目    │  │ server       │
         │ 返回结果    │  │ 中继结果给    │
         │             │  │ Copilot CLI  │
         └────────────┘  └──────────────┘
```

### active_host flag：一行决定一切

```
TriMetaverse/.github/config/active-host.yaml
────────────────────────────────────────────
active_host: copilot    # 或 triMC
triMC_endpoint: http://localhost:11434
health_check_interval_sec: 30
auto_fallback: true
fallback_cooldown_min: 15
────────────────────────────────────────────
```

**就这么简单。** 这是整个路由层的唯一状态。所有 agent 在每次被调用时，读取这个文件的第一行。

#### 两种运行模式

| 维度 | Native 模式（active=copilot） | Passthrough 模式（active=triMC） |
|------|------------------------------|----------------------------------|
| Agent 行为 | 照常执行：读文件、改代码、返回结果 | 将用户输入打包 → HTTP POST → TriMC → 中继结果 |
| Write Master | Copilot-host 持有 | TriMC(server) 持有 |
| 延迟 | 即时（本地执行） | +网络往返（~100-500ms） |
| 用户感知 | 无变化（当前体验） | 透明（不知道背后是 TriMC） |
| Agent 自身逻辑 | 完整 agent 逻辑 | 轻量转发壳 + 错误处理 |

#### Passthrough 模式的 agent 行为

```
Copilot-host Agent 收到调用
    │
    ├─ 1. 读取 .github/config/active-host.yaml
    │      active_host = triMC → 进入 Passthrough 模式
    │
    ├─ 2. 打包请求
    │      { agent_id, user_input, session_context, contract_yaml }
    │
    ├─ 3. HTTP POST → TriMC server
    │      timeout: 120s
    │      失败 → 重试 1 次 → 仍失败 → 触发 fallback
    │
    ├─ 4. 中继 TriMC 响应给 Copilot CLI
    │      TriMC 返回 { output, tool_calls, file_changes }
    │      Copilot-host agent 不做二次处理，原样呈现
    │
    └─ 5. 异常路径
           TriMC 不可达 → 自动 fallback 到 Native 模式
           或 → 返回错误给用户："TriMC 暂时不可用"
```

### 健康检查与自动回退

```
┌─────────────────────────────────────────────┐
│              健康检查循环                      │
│                                             │
│  每 30 秒：                                  │
│    GET /health → TriMC server               │
│                                             │
│    ✅ 200 OK + body { status: "healthy" }    │
│       → 无事发生，继续                        │
│                                             │
│    ❌ 超时 / 非 200 / status != "healthy"     │
│       → 连续失败 3 次？                       │
│          NO → 记录，继续观察                  │
│          YES → 触发自动回退：                 │
│            1. active_host → copilot          │
│            2. 写入 fallback 事件日志          │
│            3. ⚠️ 显式通知用户（项目管理者）：   │
│               "TriMC 连续 3 次健康检查失败，   │
│                已自动回退至 Copilot-host。     │
│                原因：[最后一次错误详情]。       │
│                TriMC 进入 15 分钟冷却期。       │
│                请检查 TriMC 服务状态。"         │
│            4. TriMC 进入诊断模式              │
│                                             │
│   回退冷却期（15 分钟）：                     │
│     冷却期内不尝试切回 TriMC                   │
│     冷却期后 → 重新探测 TriMC 健康             │
│     连续 3 次健康 → 可考虑手动切回             │
└─────────────────────────────────────────────┘
```

### 谁执行健康检查？

**Copilot-host agent 自检。** 不需要独立进程。

每个 agent 在被调用时，在执行任何业务逻辑之前，先做一次轻量健康探测（如果 active=triMC）。这样健康检查的负担分散到每次调用，零额外运维成本。

```
Agent 被调用
  → 读 active_host flag → triMC
  → ping TriMC /health（1s timeout）
     ✅ → 继续 Passthrough
     ❌ → 标记 unhealthy，触发 fallback 评估
```

### active_host flag 的生命周期

```
初始状态: active_host = copilot
    │
    │ TriMC 通过 G1-G5 后
    ▼
CPO/CTO 联合裁决 → 手动改为 triMC
    │
    ├─ 正常运行...
    │
    ├─ TriMC 健康检查连续失败 3 次
    │   → 自动改为 copilot（无需人工确认）
    │   → 记录回退事件
    │
    ├─ CTO 修复 TriMC → 验证通过
    │   → CPO/CTO 联合 APPROVE
    │   → 手动改回 triMC
    │
    └─ ...循环...
```

### 对用户完全透明

~~这是最关键的产品要求：用户不应该感知到 active_host 的切换。~~

**修正（CEO 裁决）**：当前 TriMetaverse 的 Copilot CLI 用户就是项目管理者（CEO/CTO/CPO 等），不是终端消费者。**回退切换必须显式通知，不能静默。**

| 场景 | 用户体验 |
|------|----------|
| Copilot → TriMC 切换 | 手动操作，操作者自知，不额外通知 |
| TriMC → Copilot 自动回退 | **显式通知**："⚠️ TriMC 连续 3 次健康检查失败，已自动回退至 Copilot-host。原因：[具体错误]。TriMC 进入 15 分钟冷却期。请检查 TriMC 服务状态。" |
| TriMC → Copilot 手动回退 | 手动操作，操作者自知 |
| TriMC 完全不可用（调用时） | **显式通知**："⚠️ TriMC 不可达，本次请求由 Copilot-host 本地处理。TriMC 状态：[错误信息]。" |

**通知原则**：
- 自动回退 = 必须显式通知（这是运维信号，项目管理者需要知道系统状态变化）
- 通知包含：发生了什么、为什么、当前状态、建议动作
- 通知不阻塞 agent 继续工作——先切换保活，再通知诊断

### Write Master 与入口路由的耦合

入口路由层只决定「谁处理请求」，不直接决定「谁有写入权」。但两者必须一致：

```
active_host = copilot → Write Master = Copilot-host
active_host = triMC   → Write Master = TriMC(server)
```

**如果出现不一致（例如 bug 导致两个 host 同时认为自己有写入权），这是最高优先级告警。** G8（并发写入安全验证）就是为防止这种状态。

### 产品判断

**`APPROVE`** 本入口路由层设计。

- **最小复杂度**：核心只是一个 YAML 文件的一行配置 + agent 启动时的模式选择
- **零新基础设施**：健康检查由 agent 自身承担，不需要额外的监控进程
- **用户透明**：切换对用户不可见，唯一的用户感知是 TriMC 不可用时的降级提示
- **自动安全**：连续 3 次健康检查失败 → 自动回退，不需要人工介入
