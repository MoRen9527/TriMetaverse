### 1.2 量级判断

1. **CPO 全日窗估成立**——批 B 原案「中」的主因（方案块迁入+内层正名全表）被合一废止项卸掉大半，省回的量正好对冲块 3 行内化新增的量；合一同窗本身又省掉「批 B 先排、深测②再返工」一轮整页返工。
2. **偏满不宽裕，原因单一**：块 3 行内操作列+选中行展开详情是批 B 原案没有的**新交互面**（按钮事件+展开态管理+徽章态联动），落位属一步范围（BOD 合一裁定终态结构已含），但**交互打磨属 CPO「二步」**——打磨不入窗是全日窗成立的**前提条件**，不是可选项。
3. **给施工任务书的三条防溢出钉**（BOD 立书时建议载明）：
   - 条 5 二步（交互打磨）显式划出窗，窗内只落结构位；
   - 行内交互最简形态起步：展开详情用原生 details 或单开关态，不动画不打磨；
   - 三型描述式（CPO 附带提请·候裁项）若 10-08 晨前未获 CEO 定名，按现文案施工不阻塞（文案批可后补一行）。

### 1.3 daemon/UI 工作量比

UI 侧（批 B 终态结构+深测②文案+件① 接线）≈七成；daemon 侧（config verify 三态字段）≈两成；STE 合一走查≈一成。daemon 侧半窗内可毕——**施工序上把 daemon 侧前置**（见 Q2），是「偏满」窗里唯一能并行腾挪的段。

| 段 | 载荷 | 断点（commit 粒度） | 过段门 |

排序理由：daemon 侧（S1）是唯一动服务的段且独立于 UI 结构，前置把服务风险从 UI 返工面剥出；S2 结构层先行+中间走查过门才进 S3 文案层——**结构债不许埋进文案批**（批 A/批 B 分开走查硬约束的同构扩展：结构层/文案层分断点走查）。

### 2.2 批 A 已毕面零回归保障（双保险）

1. **锚复扫**：S3 文案批的 grep 扫描清单并入批 A 验收锚复扫（新名落位零残留+禁改五处原样），每断点 commit 前复跑；
2. **禁改清单**：S2 结构重排禁触碰批 A 已改文案字符串，清单载入施工任务书（FSD 面自证+STE 走查复核双查）。

### 2.3 扫描锚执行口径（一处技术修正建议）

CPO 卷条 8 锚「grep 用户可见面零命中」——执行面建议把「用户可见面」定义为**渲染后 DOM 文本面**（jsdom innerText 扫描）而非源码 grep：源码 grep 会误伤注释（CPO 卷自注「注释级不涉」但 grep 分不出）且漏模板拼接串。UI 交付渲染门纪律（LG-035 家族：code review 对首启 UX 全盲）同构——走查对渲染物不对源码。机读锚强度不降反升。

### 2.4 回滚姿态

四道独立 commit 天然四断点；任一段走查不过=该段 revert 即回，S1 daemon 段 revert 后服务重启即复原三态前行为；整窗最坏回滚=四段连 revert，批 A 面始终在批 A 自己的 commit 里不被裹挟。
