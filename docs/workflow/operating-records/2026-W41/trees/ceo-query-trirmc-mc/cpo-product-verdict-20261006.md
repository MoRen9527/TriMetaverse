## 结论先行

**CEO 判断站得住，本席不为现状辩护**：模块边界=TriRMC 一个，产品面成立；现状「trirmc+trirmc-mc 两 unit 且在役的叫 trirmc-mc」**站不住**——误导成立（本司自勘已踩过一轮），应当归一。归一方案见问三。

## 问一 · 当初产品规划为何允许拆出第二个运行单元——如实交代

**如实答案：产品规划从未「允许」过——是产品面缺席，工程形态先行落了地。**

立案链实勘（lg032-three-channels.md，2026-09-04 立项）：

1. 案 a 的工程目标=给河源**加一个长驻 MC 服务面**（原状「TriRMC 现仅 cron API+git 拉取，无长驻 MC 服务端」L9），承接本地 TriRLC 心跳上送（切指自 sg 8710）。
2. 立项时有一条明确的**工程裁**：「cron 保留现有迁移职责不动（**服务面独立进程零耦合**）」L37——服务面长驻 HTTP、cron 按需跑，生命周期不同，分开稳。**第二个 systemd 单元（trirmc-mc.service）就是这个工程裁的直接产物。**
3. 但整份立项里**没有一个字回答「河源域控制器的模块边界是什么」**——服务面与 cron 面是同一模块的两个角色，还是两个模块？没有产品裁决。unit 名「trirmc-mc」（TriRMC 的 MC 面）以文件名后缀**偷渡了一个从未立项的概念**。
4. 治理层根因：案 a 立项 09-04，部署形态裁（独立进程+独立 unit+独立名）**没有过产品收口**（当时 D-15 联审门刚立 09-01，案 a 走 CTO 方案先行，联审子项只覆盖「审核反馈接口」）。工程决策（怎么部署）越过了产品决策（这是什么）——CEO 今日质询，本质是一次**迟到的产品验收**，而验收结论=不合格。

「一个域控制器 vs 两个 systemd 单元」的表面矛盾，自洽方式本该是：**模块（产品概念）一个，unit（部署物）可以多个但都从属于模块**——现状恰恰坏在第三点：**在役 unit 名叫 trirmc-mc 不叫 trirmc**，运维面列表里根本没有一行叫「trirmc」的在役物与产品文档对上。名字错位使矛盾从「可解释」变成「真误导」。

## 问二 · 会不会误导——会，两枚实证+一枚活证

1. **本司自勘已踩过**（rhy-trirmc-retirement.md 勘定链 L2 原文）：10-01 晨勘「河源 TriRMC cron 面=disabled+0 job」**勘的是 8710（trirmc-mc）面，而 8712（trirmc）面实有 3 个 job**——勘误勘错面，直接损失一轮勘查信任。「两个相近名+职责交错分布」正是误导根因。
2. **职责分布反直觉**：退役前正身职责分散两 unit——8712 管 cron（域控制器本职），8710 管对外 MC 接收。运维者从 unit 名完全推不出这个分布；退役后唯一在役的 unit 又叫 trirmc-mc，与「河源域控制器=TriRMC」的产品口径对不上。
3. **活证=今日质询本身**：CEO 看 systemd 列表产生「为什么多出一个 trirmc-mc」的疑问——**第一认知歧义的终极实证：名字没有自解释，连 CEO 都要问**。「-mc」后缀还暗示「M 面 MC」语义，实际它跑在 R 面河源机上——面归属也会被名字带偏。

## 问三 · 产品口径方案（合并回单单元）

**总裁：河源 R 面域控制器=TriRMC 一个模块；MC 服务面是模块内的一个监听角色，不是独立模块。unit 归一，名字归一。**

| 项 | 口径 |
| --- | --- |
| 模块边界 | TriRMC 模块收编全部职责：R 面执行自治（cron 面）+MC 接收面（8710 长驻服务）=**一个模块两个角色**。类比：TriMLC 8713 也同时有 UI 面和 API 面，没人给它拆第二个 unit 名 |
| unit 正名 | 唯一 unit 正名 `trirmc.service`（在役 8710 职责整体迁入，**端口/通道/token/值面零变化**——LG-030 纪律只换名不改值）；「trirmc-mc」名退役留档 |
| 一模块一 unit 铁律 | **部署物名=产品概念名**：unit 名只准编码模块名，不准用后缀编码职责/拓扑——后缀想表达的「这是 MC 面」属于卡面「部署实例行」的信息，不属于名字。与讲解件方案一「卡名零机器位」同族：**名字只编码产品概念，工程拓扑进实例行** |
| 卡面呈现 | 四域面卡 TriRMC 卡不动（卡名=角色已正名）；卡头部署实例行列「unit：trirmc · 监听：8710（MC 接收）+cron 面」——unit 信息是实例事实 |
| 未来扩展 | 若 MC 接收面未来真长成独立模块（如 TriMC 河源实例），按「角色·实例」规则正式立项另立模块——**不以文件名后缀偷渡新模块** |
| 迁移序（产品侧） | ①本口径入正名稿（与方案一合并为「产品命名正名稿」）→②CTO 排窗做 unit 归一（systemd 单元重建+watchdog/监控/文档引用面同步，技术序归 CTO 卷）→③归一后 systemd 列表自解释：一行 trirmc=河源域控制器 |

**给今晚窗的裁点**：产品面立场=**归一成立、该做**；执行时点与 unit 重建的技术风险面（watchdog 引用/restart 链/监控面板引用）归 CTO 卷，本席不代答。若 CTO 面评估归一成本显著，最低限度产品红线=**「trirmc-mc」这个误导性名字必须消失**（改DisplayName/别名+文档正名锚定），unit 合并可候窗——名字纠偏零借口，架构合并可排窗。
