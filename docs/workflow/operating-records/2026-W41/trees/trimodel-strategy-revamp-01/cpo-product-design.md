## 摘要（大白话）

1. **cc-switch 查明白了**：它是给个人开发者的桌面小工具，管 8 个 AI 命令行/桌面工具的供应商配置，人点一下就切换。它证明「配置切换」是真需求，但停在「人做决定、它替你改文件」。
2. **TriModel 和它不是一个物种**：TriModel 是全公司四域的模型供给基础设施——规则自动决定用哪个模型、四域跨机自动拉取配置、故障自动降级兜底。三个自动化都是 cc-switch 没有的组织级能力。页面叙事照这个差距写，且不否认对手（它代理模式的 failover 是真自动化，只是层不同）。
3. **「模型策略」页按三概念重排**：模型（菜）/模型组合（套餐）/切换规则（点菜规矩），页顶加一行「当前生效」状态。改名文案全表已锚到实现行号；另附**禁改清单**——九处「无法连接配置服务」（04:12Z 勘正，初稿五处推定漏四处）是服务报错文案不是页面名，不能动。
4. **「兜底模型」页语义**=四域各钉一份保底直配，直落各域落地配置；TriModel 整个不在了各域也照常活——这是「只发配置不传话」设计的兑现。原连接配置表单五件原位并入，不推倒。

## 一、cc-switch 对表调研（令面任务①）

### 1.1 产品事实（对表来源：仓库 README 全文，raw.githubusercontent 取得）

- **定位一句话**：跨平台桌面端 All-in-One 管理器，管理 Claude Code、Claude Desktop、Codex、Gemini CLI、Grok Build、OpenCode、OpenClaw、Hermes Agent 八个 AI CLI/桌面工具的供应商配置。官网 ccswitch.io。
- **解决的痛点**：各家工具配置文件格式各异（JSON/TOML/.env），换一家供应商=找到对应文件手改对应字段，易错且要逐工具来。
- **核心功能面**：
  - 供应商管理：内置预设模板、一键导入（复制密钥即导）、一键切换、托盘快捷切换、拖拽排序、批量导入导出
  - 通用供应商：一份配置同时同步 Claude Code / Codex / Gemini CLI
  - 本地代理（进阶）：热切换、格式转换、自动故障转移、熔断、供应商健康监控、应用级接管
  - 统一 MCP 面板（双向同步）；Prompts 管理（CLAUDE.md / AGENTS.md / GEMINI.md 跨应用同步+回填保护）；Skills 一键安装（GitHub/ZIP）
  - 用量与成本面板（分模型计价）；会话管理器（历史浏览/搜索/恢复）
  - 云同步（Dropbox/OneDrive/iCloud/WebDAV）；深链导入（ccswitch://）
- **数据底座**：本机 SQLite 单一真源（~/.cc-switch/cc-switch.db）；切换=把选中供应商写入该工具活配置文件；双向同步（切换时写出、编辑活动供应商时从活文件回填）；原子写+自动备份（保留多份）。

### 1.2 产品形态边界（它做什么、不做什么）

**做什么**：把「换供应商」从手改配置文件变成一键操作；把散在八个工具里的配置收进一个本机面板；可选开本地代理做请求层故障转移。

**不做什么**（形态边界，即 TriModel 的机会面）：
1. **单机工具，无服务端**：管不到第二台机器——sg/河源跨机配置分发不在其射程。
2. **无组织维度**：没有域、席位、多消费者概念——它眼里只有「这台机器上的八个工具」。
3. **切换靠人点**：除代理 failover 外无规则引擎——没有「什么时段/什么情形自动用哪组模型」。
4. **只改配置文件，不服务配置**：它是写文件的工具，不是可供程序例行领取配置的服务。

## 二、TriModel vs cc-switch 定位对比（令面任务②-a，供页面叙事）

### 2.1 差异总表

| 轴 | cc-switch | TriModel |
| --- | --- | --- |
| 是什么 | 个人开发者的桌面配置切换器 | 多机多域组织的模型供给基础设施 |
| 管谁 | 单机上 8 个 AI 工具的配置文件 | 四域（M/R × 服务/本地）控制器的模型供给 |
| 怎么决定用哪个 | 人点（一键/托盘） | 规则引擎自动路由（时段/默认/额度三型） |
| 配置怎么到达 | 写入本机工具配置文件 | 常驻服务端，四域例行拉取 + 兜底直配 |
| 坏了怎么办 | 代理模式内 failover（可选开启） | 三层兜底梯：规则转入序列 → 兜底直配 → CLI 直配 |
| 规模弹性 | 一台机器 | 跨机（本机/sg/河源），一处管全司 |

### 2.2 「更灵活+更自动化」的准确表述（防夸大条款，页面叙事用）

CEO 对表点成立，但要精确到「差在哪一层」，否则经不起亲测（LG-058 级教训：表述不精确被亲测打回）：

1. **自动化的层不同**。cc-switch 的自动化在**请求层**：开本地代理后做热切换与故障转移——流量过它手。TriModel 的自动化在**决策层+分发层**：规则引擎自己决定什么情形用哪组模型（不碰流量），四域例行拉取自己拿配置（不需要人跑到每台机器上点）。一句话：cc-switch 是「你决定、它执行」，TriModel 是「规则决定、系统执行」。
2. **灵活的对象不同**。cc-switch 的灵活是**个人灵活**：单机上八工具多预设随手换。TriModel 的灵活是**组织灵活**：四域各配各的 + 共享模型菜单（模型策略=菜单、域卡=点菜、key 不进策略面）+ 规则自由组合。一个人用，cc-switch 够；一个跨三台机器跑常驻程序的公司用，需要的是 TriModel。
3. **不否认对手**（诚实条款）：cc-switch 的代理 failover 是真自动化，页面叙事禁写「cc-switch 没有自动化」；正确表述=「它的自动在请求转发层，我们的自动在配置决策与分发层」。

**页面叙事候选文案**（供 UI 一句话定位与讲解件对齐）：

> 「cc-switch 帮你切换模型；TriModel 让全公司四个域的模型供给自己跑——规则自动路由、配置自动下发、故障自动降级。」

## 四、「兜底模型」语义文案（令面任务②-c）

### 4.1 定位（三层故事，页面与讲解件共用）

1. **常态主通道=模型策略**：平时各域按规则自动路由——灵活。
2. **兜底第一层=兜底模型直配**：四域各钉一份兜底模型，改完经拉取下发**直接落到该域落地配置（settings.json）**——不参与规则博弈，是钉死的保底（CEO 语义：「兜底护栏/兜底直配」）。
3. **兜底第二层=CLI 直配**：TriModel 整体不可用时，各域凭**已落地**的配置照常运转（配置已在域内，程序不依赖 TriModel 在线）；各面域 CLI 也可直配。

第二层是「只发配置不传话」设计的兑现：TriModel 发完配置就退场，**域的存活不绑 TriModel 的存活**——兜底模型页卖的就是这个安心。

### 4.2 与「模型策略·默认规则」的辨析（防混淆，进副题与 tooltip）

- 默认规则=平时没命中时段窗时用哪个——**策略层**，活在规则引擎里；
- 兜底模型=域级钉死的保底通道——**配置层**，直落落地文件。
- 一个回答「平时怎么排」，一个回答「万一的时候拿什么保底」。落盘形态不同：兜底直配无论 TriModel 活不活都在。

### 4.3 页面文案提案

- **导航/页题**：兜底模型
- **副题**：四域各一份保底直配——改完经拉取下发，直接落到该域的落地配置。模型策略管平时怎么用得灵活，这里管万一的时候拿什么保底。
- **三态沿用**：已存未拉 / 已拉未落 / 已落生效（诚实三态现役语义不变）
- **卡结构**：四域签（M 面·服务域 / R 面·服务域 / 本机·本地域 ×2）各含：兜底模型选择（自模型策略菜单点选，或菜单外手填）+ r5 五件表单
- **空态提示（新增建议）**：未配置兜底=该域仅按模型策略规则供给，TriModel 不可用时无独立保底。
