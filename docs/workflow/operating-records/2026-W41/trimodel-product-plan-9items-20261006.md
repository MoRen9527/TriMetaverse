## 方案一 · 产品定义正名稿（打回 #2）

### 1.1 域面控制器定义（正名）

**域面控制器是一个软件模块**——一个域内「任务调度+治理+配置消费」的能力集合。模块是构件整体：可以是一个进程，也可以是多进程，**未来 k8s 部署形态下一个模块可以编排很多机器**。三不等于：**模块≠进程≠机器**。

旧表述「替一个工作地点管事的常驻小程序」错在把形态说小了（小程序=单进程轻量物），且隐含「一机一控制器」的部署绑定——正是被 k8s 未来形态击穿的假设。

### 1.2 卡名去机器位化方案（k8s 形态兼容）

**现状**：卡名写死机器位——「TriMLC·本机 / TriRLC·本机 / TriMMC·sg / TriRMC·河源」。

**问题两笔**：①与「卡如其名=角色」的自身规矩矛盾——机器位是**实例态**（会变的事实），不是**身份**（不变的定义）；②k8s 形态下机器位天然漂移、一控制器多实例，「·本机」从第一天就注定失真。

**正名方案：「角色（卡名）+ 部署实例（卡头一行）」二级结构**：

| 层 | 内容 | 变化频率 | 举例 |
| --- | --- | --- | --- |
| **卡名=角色** | TriMLC / TriRLC / TriMMC / TriRMC | 不变（改角色=改产品定义，走治理） | 「TriMLC」 |
| **卡头·部署实例行** | 现役部署位 / 实例数 / 健康 / 过渡注记 | 随部署变（动态读取） | 「现役：本机（寄居过渡）」→ 未来 →「现役：k8s 集群 X ·3 副本」 |

- **规则一句话**：卡名答「这是谁」，实例行答「它现在在哪」——机器位只准出现在实例行。
- **迁移**：现役四卡 UI 文案层改名一步到位（去·后缀，后缀内容并入实例行）；「寄居过渡」「同机过渡位」等注记归实例行保留。
- **护栏**：任何新卡入页，卡名过「角色判据」（服务哪条面/哪个域），机器位检查（卡名含机位词=打回）。

### 1.3 落点

- 讲解件已按白皮书口径改毕（v2）；本节为产品文档正名正身。
- cpo-product-plan v3 §2.3「角色·机位」实例化规则升格为「**角色+实例分离**」（机器位从身份降为实例事实）；M/R 面表述统一引白皮书 L191 原文。

## 方案二 · 域卡×策略卡联席链路设计（打回 #8）

### 2.1 CEO 定性与现状断点

CEO 定性：未见各域如何与策略卡的模型与规则建立配置选择上的联席，**产品易用性不足，体验差**。

现状断点（一缺一盲）：
- **缺**：策略卡定义了模型清单/模型集/规则，但域卡的现役配置条目（模型+key）是**手填孤岛**——策略卡说了「有什么可用」，域卡不知道；两边各写各的，改一边另一边不知情。
- **盲**：策略卡改了模型集，看不到「哪些域在用」；域卡配置改了，看不出模型是自创的还是菜单里有的。

### 2.2 心智模型：菜单与点菜

**策略卡=菜单**（全公司有什么可用：模型清单/模型集/规则），**域卡=点菜**（本域实际用哪份）。规矩一条：**点菜必须从菜单点，不许自带菜谱**——域卡上任何模型选择都出自策略卡清单。

### 2.3 联席机制三件（产品层）

1. **域卡条目引用化**：域卡现役配置条目的「模型」字段从手填改为**从策略卡模型清单下拉选**；新增条目可「引用策略卡模型集」一键带出整组。手填入口保留但降为「高级」，且手填值若与菜单重名则提示改用引用。
2. **规则适用勾选**：策略卡规则（什么任务走哪组模型）在域卡加一行「本域适用规则」——从策略卡规则清单勾选，勾选后该域消费配置按规则路由。零勾选=本域不套规则（如实显示）。
3. **反向引用可见**：域卡条目引用模型集时带来源标注（「来自策略卡·模型集 X」）；策略卡编辑/删除模型集时列出「被哪些域引用」——**改菜单前先知道谁点了这道菜**。

### 2.4 边界与验收锚

- **边界**：联席只做「选择引用」层；key 仍归各域域内管理（策略卡不搬钥匙——密钥分发走既有 S2 加密链，不进策略面）。
- **验收锚三条**：①域卡模型选择零手填孤儿（全部可溯源到菜单）；②删除被引用菜单项有引用拦截提示；③两边变更互相可见（域卡看得到来源、策略卡看得到引用方）。

## 方案三 · 连接配置四域化设计（打回 #9）

### 3.1 CEO 定性（原话锚）

「简单直接的讲，这个卡就是给四个域留一份直接修改本地配置的配置，拉取下发下去直接影响 setting.json。」

现役只有本机+sg 两项=产品设计不清、理解不到位（CEO 定性）——本方案按 CEO 定性重构。

### 3.2 重新定性

连接配置卡 ≠「本机开发工具指路便签」（旧口径作废），=**四个域各自的本地配置直改面**：每域一份「直接改本地配置」的入口，改完经拉取下发**直接落到该域的 settings.json**（域控制器的本地落地配置文件）。

### 3.3 卡内结构（四域同构）

卡内分四个域签，与四域面卡同序同构：**M 服务域 / M 本地域 / R 服务域 / R 本地域**。每域签=该域的本地配置表单（域内落地形态项：如本地端口、本地路径、直改项），表单旁三行状态：**配置版本 / 上次下发时刻 / 落盘结果**。

### 3.4 数据流（五步，产品层）

1. **改**：管理员在连接配置卡·某域签改本地配置项，保存。
2. **存**：写 TriModel 服务端该域的本地配置直改面（按域分账，服务端留版本）。
3. **拉**：该域域面控制器下次例行拉取时，连同拉到本地（拉取链现役已有先例——key-cache 同路）。
4. **落**：域控制器把拉到的本地配置**落盘写入本域 settings.json**——这一步是「直接修改本地配置」的兑现点，不落盘=没生效。
5. **效**：settings.json 变更生效，域内消费者按新配置跑。

### 3.5 与方案二的关系（两层正交）

- 联席（方案二）=**从菜单点菜**——管「选哪个模型集/规则」；
- 连接配置（本方案）=**改厨房本地设备**——管「本域落地形态」。
- 一句话：策略卡联席决定「用什么做饭」，连接配置决定「厨房本地怎么摆」——两层互不掺和，各答各的问题。

### 3.6 诚实语义与验收锚

- **下发没落盘不许显示成功**（诚实三态同族）：每域签三行状态如实报「已存未拉 / 已拉未落 / 已落生效」——最后一格不绿就不算完。
- **拉取链断**：该域 settings.json 保持最后已知好值（降级梯同源），卡上如实显示断链态。
- **验收锚三条**：①四域签齐（零缺席域）；②改→存→拉→落→效五步可在卡上逐环看状态；③落盘结果读数与目标 settings.json 实际内容一致（值面验证，非只看绿点）。
