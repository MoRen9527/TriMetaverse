## §一 · 问 1：代收代发链四件（格式/责任/SLA/兜底）

**信件格式（复用 letter·加三字段）**：`{letter_id, from:"bod", target_seat, kind(转达|请示|回报), body, in_reply_to?, relay:{via:"cos", forwarded_at, ack_by_target?}, sla_due?}`——**`in_reply_to` 与 `relay` 是新增**：前者使回信可挂回原信（防串线），后者使代发动作可追责（谁何时转给了谁）。**`body` 须自足**（收信席不读 bod 会话也能办——这是代发链与直发的本质差）。

**流转责任席（一段一主）**：
| 段 | 责任席 | 义务 |
|---|---|---|
| bod→信箱 | **bod** | 写信+提醒 COS 读（两步缺一=未送达） |
| 信箱→目标席 | **COS** | 代发（逐字转·不改判·加 relay 溯源）；**不得代裁**（BOD 集散面原则延伸到 COS 代发段=只转不判） |
| 目标席回信 | **目标席** | 回 COS（现形不变） |
| COS→bod | **COS** | 汇总回信（见 §二 回信通道） |

**SLA（两档·建议值候 CEO/COS 定）**：转达件=**COS 30min 内代发**（与现 D-88「派工后 30min 无回执催办」同口径）；请示件=**COS 读信 15min 内**（候批类不得积压）。**SLA 计时起点=信落箱时刻**（非 bod 写信提醒时刻）。

**丢失兜底（三层）**：①letter `delivered` 字段=送达真值（未 delivered 超时→bod 侧可查·**bod 须有读信箱能力否则兜底失效·见 §二**）②超时自动催办=复用 D-88 30min 催办机制扩一档「relay 超时」③**断链最坏情形**=COS 会话失活→bod 全盲——**须有非 COS 的旁路**（如 bod 可直接写树文件=落卷即达，不依赖信箱）。

## §二 · 问 2：COS→bod 回信通道

**关键依赖（产品面判断·技术可行性归 CTO 卷）**：回信能否到 bod，取决于 **bod 在 Copilot 宿主下有无「被动收信」机制**。
- **若有等价注入**（Copilot 侧 hook/定时注入）→ 走信箱·`target_seat="bod"`·与现 notify-inject 同形；
- **若无**（本席判断为更可能·候 CTO 实测定）→ **bod 只能「主动拉」**：三形择一——
  1. **bod 每拍自读信箱**（bod 本有 30min tick·tick 时读 `target_seat=bod` 未读件·**零新机制**·推荐）；
  2. **COS 把回信落成树文件**（如 `bod-inbox-<date>.md`）·bod tick 读文件——**落卷即达**·与「硬门签认必落卷直达」同精神；
  3. CEO 人工转述（不可取·CEO 不该做传声筒）。
- **建议=1+2 并用**：信箱为主（结构化·可回执）、树文件为兜底（bod 信箱读不到时仍有可达面）——**双通道=断链兜底的实体**（§一 第③层）。

## §三 · 问 3：方案 vs 现状取舍（产品/流程判断）

**值不值=有条件值**——不是简单的「省 token」对「多一跳」：

**收益面**：bod 跨会话 SendMessage token 归零（BOD 称最大 token 项之一——**读数候 CFO 面核**，本席不转述为定论）；且 bod 信件落信箱=**结构化留痕**（现 SendMessage 是会话态·不可事后机读），对台账/审计是增益。

**代价面**：①**时效**：每封信多 COS 一跳（+15~30min/封）·紧急件受损最大；②**错传/失真**：COS 代发=人手转述=有改写风险（须「逐字转·不改判」纪律约束·仍非机械保证）；③**单点**：COS 成 bod 唯一出口——COS 失活=bod 全盲（现 SendMessage 是点对点·无此单点）；④**能力面收窄**：bod 现可 ListAgents 对名址·直发任意席·换后全失。

**产品判断**：**这条链把 bod 从「通信节点」降成「写信人」**——适合 **bod 的低频/非紧急/集散型** 通信（呈报/转达/汇总），**不适合高频催办与紧急协调**。

**前提条件四条（任一不满足=不建议切）**：
1. **回信通道先实证**（CTO 卷：Copilot 有无注入·无则 tick 自读信箱实测通）——**回信不通=单向链=不可用**；
2. **旁路兜底在位**（bod 可落树文件直达·不依赖 COS 存活）；
3. **信量先测**（统计近一周 bod SendMessage 的量/类型/紧急度分布——若催办类占比高则代价大于收益）；
4. **灰度**：先并行跑 N 天（Copilot bod + 保留 CC 侧通道作回退）·量 relay 超时率/错传率后再定全切。

**结论一句**：**省 token 的收益是真的，但「COS 单点+时效+失真」三项代价也是真的——建议灰度验证回信通道与信量分布后再全切，不建议直接切。**
