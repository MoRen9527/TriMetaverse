- 视角: 产品语义+PRD 边界（技术面归 CTO 卷）

## §一 · PRD 边界（一条分界公式）

**PRD 回答「用户会感受到什么不同」；任务书回答「我们怎么把它做出来」。**

- **属 PRD**：用户是谁/场景、可感知行为变化、验收可感知判据、定价与价值交换影响、兼容与迁移对用户的承诺。
- **留任务书**：范围 items、落点/target、依赖、owner、verify、rollback、时序。
- **互不越界**：PRD 不写技术架构与实现（归技术方案）；任务书不重定义产品承诺（只引 `prd_ref` 锚）。
- 与 D-85 衔接：PRD=需求评审后成件（R6 产物），任务书=已批执行件——PRD 不复制池行原文，只提炼「承诺」。

## §二 · 「复杂到要另出 PRD」判据（三问任一=要 PRD）

1. **用户可感知变化？**（行为/界面/输出形变化——对内工具链用户也算）
2. **新能力或新场景？**（新功能/新用户群/新集成面）
3. **价值交换变化？**（定价/打包/额度/合同承诺）

- 三问全否（纯技术重构/内部可靠性/性能/机制改造·用户行为等价）→ **不要 PRD**（任务书内「产品声明」一行替代·见 §四）。
- **判不出=按要 PRD 保守处置**（防漏·与 D-85 保守优先同族）；**PRD 出=须有消费面**（决策/验收引用·不得成摆设件——同「产出-消费比」精神）。

## §三 · 任务书产品面字段（两型共用·最小集）

| 字段 | 形 | 说明 |
|---|---|---|
| `product_intent` | 一句 | 目标用户/场景（谁在什么场合用） |
| `observable_acceptance` | 1-3 条 | 用户可感知的验收判据（行为/输出/界面） |
| `prd_ref` | 路径+版本 \| `none` | 复杂型必填指针；简单型填 none 并配 §四 |
| `product_change` | `none` \| `minor` \| `major` | 简单型核心字段：none 须附一句理由 |
| `pricing_impact` | `none` \| 摘要 | 涉定价/额度时必填 |

## §四 · 简单任务书如何表达「不做产品变更」

- 一行：`product_change: none` + **理由一句**（例：「内部可靠性机制·用户行为不变」）。
- **反形警示**：**不写=默认有产品变更**（保守判·防「悄悄改了用户面却标简单」）。
- 若有**间接可感知面**（如日志格式/输出文案变化）须写明——「无直接用户面」≠「无任何可感知面」。
- 验收判据用**行为等价形**：原行为保持（可回归对表）+ 回滚可还原。
