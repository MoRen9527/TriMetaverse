## 〇、需求→现状映射

**现状 v1**：直连兜底=单套——手填三值（地址/密钥/模型）直写**「服务端所宿机」**的 `~/.claude/settings.json`（9 键模型档位全族 verbatim 同值）；旧边界明文「不碰 sg」。

**需求 v2**：按机位分两套——**TriMMC 套（sg 机）+ TriMLC 套（本机）**。语义=兜底通道与四卡形态对齐：每个面的会话各自有救自己的兜底配置。

## 一、产品语义（为什么两套）

1. **两面可达性不同**：本机可达的 provider 地址与 sg 可达的不同（sg 走代理段）——通用一套值必然对一面不可用。
2. **会话归属不同**：本机会话坏配置→本机兜底救；sg 13 席会话坏配置→sg 兜底救。
3. **故障域独立**：两台机器的 settings.json 是两个独立故障域——兜底=「谁坏了救谁」，配置必须分家。

## 二、两套定义

| 维度 | TriMLC 套（本机） | TriMMC 套（sg） |
| --- | --- | --- |
| 目标文件 | 本机 `~/.claude/settings.json` | sg 机 `~/.claude/settings.json` |
| 三值 | 地址/密钥/模型（各自独立填写） | 地址/密钥/模型（各自独立填写） |
| 现状展示 | 读本机现势（现有 GET 逻辑） | 读 sg 现势（经通道） |
| 应用通道 | 现有直写（实现零改动） | **待 CTO 定**（技术待定项 §五） |
| 状态文案 | 各自人话态（成功/失败/已是该值） | 同左 |

- 实现继承：9 键全族 verbatim 同值、写前备份、坏 JSON 拒写、幂等「已是该值」、密钥不回显——两套同等适用（v1 全部安全语义直接继承）。

## 三、UI 形态裁决

- **独立区两栏**（现「直连兜底」区内分栏）：TriMLC（本机）在前、TriMMC（sg）在后——就近原则（本机故障更频发、验证更快）；命名与四卡口径一致。
- 每栏：现状行（地址/模型/密钥尾 4）+ 三值表单 + 「还原兜底」按钮 + 行内人话状态。
- **不并入各卡**：兜底语义=「TriModel 配置面不好用时」的应急——必须独立于卡片禁用链（v1 边界明文「不参与卡片禁用链」），且 TriMLC 卡尚未建。并入卡内=卡数据坏时兜底也渲染不出，自毁前提。
- 词汇零黑话照旧（无 env 名/HTTP 码）。

## 四、边界与原则

1. **互不串写**（验收核心）：操作 TriMLC 栏→只写本机；操作 TriMMC 栏→只写 sg。零交叉。
2. **应急独立性**：两栏均不参与卡片禁用链；TriModel 卡数据坏时两栏必须仍可用。
3. **凭据不跨机**（继承河源模式原则）：sg 的写入执行发生在 sg 侧（本机 UI 传意图、sg 本地写 sg 文件）；sg 密钥不在本机落盘、不回显（尾 4 位展示归 CTO 定通道后裁）。
4. **旧边界修订声明**：v1「不碰 sg」被本需求修订为「sg 经专用通道写 sg」——修订的是通道，不修订的是凭据不跨机原则。

## 五、技术待定项（CTO 域，需技术方案）

1. sg 侧通道形态：三方候选——a) 本机 UI 直调 sg TriModel 的 claude-fallback 端点（sg 同代码已有该端点）；b) 经分发链（四卡同族）；c) 其他。选型+凭据（sg ADMIN_TOKEN 交付方式）归 CTO。
2. sg 侧读取路径（现状展示的数据来源）同通道定。
3. sg 侧写面安全姿态复用 v1 fail-closed 族。

## 六、验收锚

1. 两栏各自写各自目标机（本机操作零改动本机外部；sg 操作只动 sg）——互不串写断言。
2. 两栏在 TriModel 卡数据损坏场景下仍可操作（应急独立性断言）。
3. 继承断言族两套同跑（幂等/备份/坏 JSON 拒写/不回显）。
4. sg 侧写入的真实落盘由 sg 侧验证（跨机走查归 BOD/技术线）。
