## 〇、总纲：定位差异先于对表

上游演化方向=**开源产品成熟路径**（单体→模块族、核心→生态、工具→平台：apps/evals/website）。本司治理体系=**内部自用体系**（13 席高效运转+方法论沉淀）。
**吸收原则**：吸收「使体系更可靠/更省成本的机制」，不吸收「对外发布形态」。据此逐项对表——该不吸收的明确不吸收，防对标扩范围。

## 一、逐项对表

### ① apps/ 桌面化 → 印证另线，治理体系不吸收
- 治理体系不吸收（内部体系无需安装器/桌面壳）。
- 单列转记：上游 desktop 形态对 **TriCade**（PC 端捆绑产品线）有对标价值——那是产品线另一条线，候令另件。
- 唯一可借思路：bootstrap-installer=「接入门槛产品化」——映射本司=新员工 onboarding 一键化（归 CHO/CGR 域，产品侧仅提示）。

### ② skills/plugins/toolsets 三层分发 → **吸收（本件最强对表点）**
上游三层=核心/可选/目录。与我管道件「分区注入」同构且补上了我缺的第三层：
- **核心层**（全员必会）→ org/shared 核心层全量注入（已有）；
- **可选层**（按岗位/按需）→ 岗位装载层（已有「扩展层」雏形）；
- **目录层**（可发现未装载）→ **我件缺的**：想学但不在必读的知识放哪？上游答案=目录（可发现、不装载、零注入成本）。
产品定谳：**知识分发升三层**——核心（注入）/ 可选（岗位装载）/ 目录（可发现）。目录层=token 预算纪律的正解（不进注入面=不花全席成本），承载建议=CGR 目录索引面。机制对表：toolsets 的分发声明↔我们的 knowledge spec（page-specs 扩分发层字段候 CTO）。

### ③ evals/ 一等公民 → **吸收（收敛为两件）**
上游把评估作一等目录（非测试附属）。本司对应物已多（STE gate/走查三遍/联审/验收锚六条），但**知识管道自身无评估面**。收敛吸收：
1. 验收锚集合化为一等面（散件→汇集，随设计正身）；
2. **管道质量基线**三指标：消化归并正确率（抽检）、注入页可用性（抽 3 页去链可读——已有锚）、reject/escalate 判定复现性（同一素材二次消化锚扩展）。
不做：完整 evals 框架/回归工具链（内部体系不需要上游规模，够用即止）。

### ④ SOUL 顶层+default_soul.py → 部分吸收（身份连续性确认）
- **印证**：上游把 SOUL 放顶层并做成可编程种子=身份连续性是一等产品价值（不只是记忆连续）。对表我四问件「谁看=未来会话的自己」：soul=身份连续，wiki=知识连续——**两条连续性互补**，本司两者都已有载体（soul 覆盖层+注入页），上游印证方向正确。
- 可吸收：**soul 一等位原则**（身份种子顶置，非附属）；**default_soul 模式**（新员工身份种子可模板化生成）——映射 CHO onboarding，跨域转记（CHO/CGR 域裁）。
- 不吸收：可编程灵魂的工程实现（本司四层身份契约已够用）。

### ⑤ 多语言化+docs 迁 website → 主项不吸收，借一条结构原则
- 内部体系无对外面：多语言/website 均不吸收（防扩范围）。
- 唯一可借：**对外/内文档面分离**结构原则——上游 docs（内部）vs website（对外）分立。本司对应已有雏形（内部治理文档 vs 白皮书对外叙事），可随治理二期正身强化边界声明一句。

## 四、验收锚（增量）

2. 管道质量基线三指标可测（归并正确率抽检/注入页去链可读/reject·escalate 复现）。
3. 转记两条（③④）在 CHO/CGR 侧有落点记录（非本件直接管辖，验证转记未丢）。
