## 1. 文档定位

本文用于承接 TriMetaverse 项目级的架构说明、模块说明，以及 `reference` 层与开源吸收链的统一口径。

这里记录的是项目整体架构与模块边界层面的说明，不是某个具体代码仓、运行时模块或实现细节的开发规则。

当前该部分内容先由总助协助收口到项目文档层；待 `CTO` 正式上岗后，再交由 `CTO` 作为技术真源 owner 持续维护。

## 2. TriMetaverse reference说明

- 任何开源代码吸收，必须先从 TriMetaverse 整体架构、模块职责和长期边界判断开始；先确定它服务哪个模块、解决哪一层问题，再决定是否进入吸收链。
- 上游源码必须先统一放到 `TriMetaverse/reference/`，作为 reference 层；reference 只用于阅读、对照、拆解、留档和版本锚定，不得直接当作本地运行时真源。
- 一旦确认某个开源项目需要被 TriMetaverse 长期融合为独立模块，必须创建与其他主模块同级的模块目录；不得把 `reference/` 目录直接冒充模块本体。
- 该模块内必须建立 `vendor/` 目录，作为上游代码的冻结基线和渐进式吸收层；vendor 默认优先保持上游原貌，用于从最小版跑通到后续完整复刻之间的持续参考。
- 开源吸收链统一写为：`TriMetaverse/reference -> 模块/vendor -> 模块真实实现`；不得跳过 reference 直接散改上游代码，也不得把 vendor 误写成自研主干。
- 当前阶段必须先跑通最小版闭环，再决定是否继续扩展到更完整的复刻；能通过 wrapper、adapter、配置覆盖和最小 patch 复用上游的，不先重写平替。
- 吸收上游代码时，优先复用其成熟、稳定、已被验证的优势能力；对与现有体系重复、弱于现有实现、或不服务当前阶段目标的功能，明确列为排除项，不必复刻。
- 不得为了“看起来完整”而复制上游全部能力；凡是不属于当前模块职责、不符合当前阶段最小闭环、或会造成重复功能的部分，直接砍掉或后置，避免双份实现和边界混乱。
- 项目级目标不是机械复刻上游，而是形成符合 TriMetaverse 总体架构的最优解：弱势功能砍掉，优势功能吸收，重复能力合并，模块边界保持清晰。
- 如开源吸收动作会引入新的长期主模块或改变既有模块边界，必须先咨询 `BusinessStrategy`；在中央真源口径更新前，不得把边界变化写成既成事实。
- 架构表中的模块一旦被写成正式模块面，默认应补齐独立 git 仓、`README.md`、`docs/` 六件套、根级 `.gitignore` 与本地 `CodeGraph`；占位模块也应先补齐这套骨架，再继续标注为待初始化。
- 任务命中既有正式模块时，`Discovery` 阶段应先形成 `ModuleTargetingReport`，并由 `TriDev` 完成 `ModuleReadinessInit`（标配审计与缺口 init）后再进入后续开发。
- 新增正式模块时，`Discovery` 阶段应先由 TriCompany 输出 `NewModuleBaselineRelease`（含 `vendor-extraction-profile`），经签核后由 `TriDev init` 执行模块骨架初始化；未达到 `approved` 前不得写成既成模块。

## 3. 当前阶段运行与宿主边界

- “赛博公司”是当前所有人格 Agent 与非人格 Agent 的经营和交互核心载体，不再把经营自治单独命名为第三个基础设施主控；赛博公司实施侧规则先由 `TriCompany` source 侧维护，再按发布规则同步到中央摘要层。
- `TriMC` 是公司云端实体，承载整个公司运行面——共享公司知识体系、运营公司业务、发放公司奖励、审计相关活动，并执行托管无人值守工作流（周度平移、IPD CMO 商机发现等已成熟的自动化编排）。`TriLC` 作为分布式员工工位承担本地人机协作主入口（编码/办公/视频制作等）；`TriMC` 同时作为 `TriLC` 本地崩溃时的故障 fallback。
- `TriMC` 架构（2026-07-10 CPO/CTO 联审 + CEO 中央收口裁决）：
  - **infra 层**：以 `TriMC/vendor/claude-code/` 中的 Claude Code 2.1.88 作为主力 agent runtime，吸收其 daemon / cron（ScheduleCronTool 三件套）/ task 管理 / self-hosted-runner / tools 工具箱（40+ tools）；
  - **员工编排层**（TriMC 自建，高于 Claude Code infra）：Soul Loader + Memory Injector + Tool Gater + Context Builder，OpenClaw assistant 模式作为设计参考；
  - **OpenClaw 吸收裁剪**：社交通道 → `TriGateway`，消息队列管理 → `TriMC`；`vendor/openclaw/` 裁为薄参考层，用于心跳补丁（如 daemon placeholder 不足时）；
  - **模型接入**：通过 `TriStaciss` Anthropic-compatible 端点（`POST /v1/messages`）接入 DeepSeek 等模型，`TriModel` 负责配置路由（provider: "TriMetaverse" → TriStaciss）；TriStaciss Anthropic 端点为 TriMC 上线前置依赖。
- 当前阶段（copilot-host 练兵场）：shadow 与本地手动版直接运行在 `copilot` 宿主上；从 Copilot-host 本地手动版切换到 TriMC 服务器正式版，通过 TriMC 自身部署实现，而不是把 `TriCode` 写成服务器版 runtime。
- `TriModel` 负责 Provider 与 Model 的统一配置，为 `TriMC`（公司级 agentic orchestration）、`TriLC`（本地人机协作主入口）与 `TriCode`（本地编码 agentic orchestration）提供统一的模型接入点；支持多 provider 适配、模型路由与 fallback 链。Phase 1 已作为配置平面 API 服务上线（2026-07-22），提供 `/v1/models`、`/v1/config/keys` 端点；library 模式保留作为本地 dev 和 fallback。
- `TriPilot`、`TriCode`、CLI（如 `opencode`、`claude code`、`codex`）与 `vscodium` 共同组成 PC 端软件层；其中 `TriCode` 是 `TriPilot` 插件与本地工具链的 glue 适配层，提供 ACP 协议适配；`TriPilot` 默认直连 `TriLC`（本地主入口），仅在 `TriLC` 不可用时自动切换 `TriMC` 云端通道。不再承担服务器端 runtime 语义。
- PC 端软件层一方面配合 `TriLC` 完成本地化任务、本地工具调用与部分服务域下发任务，另一方面也保留给用户直接使用的桌面自动化、PC 软件自动化与 `vibe coding` 入口语义。
- `TriSkill` 是统一 skill 提供模块；2026-07-11 起进入吸收初始化阶段（vendor 基线：mattpocock/skills，39 个 SKILL.md），已产出吸收分析报告、三层 registry 与 Wave 0 三个自有 skill（tri-ask / tri-handoff / tri-grill-me）；Wave 1-3 待产出。

## 5. 命名与别名治理

- 中央 registry、计划文档、教程文档统一使用 `TriGateway` 作为规范化模块名称。
- 物理目录已修正为 `TriGateway/`；为保证已有 workspace、脚本和外部引用平滑迁移，历史 typo 路径 `TriGatway/` 暂作为兼容别名保留。
- 后续自动扫描、批处理 prompt、报告聚合和教程生成都必须维护 `TriGateway <-> TriGatway` 的 alias 映射，避免把两个名字误判成两个模块。
- 产品 canonical name 统一采用 `TriPilot`、`TriStaciss`、`TriAvatar`；`TriDeployment` 与 `Tride` 为历史名，已分别更名为 `TriAuto` 与 `TriCode`，仅保留为历史兼容路径名。
- `TriMC` 已更名为 `TriMMC`（Meta Main Controller，元虚拟主控）、`TriLC` 已更名为 `TriRLC`（Reality Local Controller，元现实本地控制器）（2026-08-21 三元宇宙重定义）：历史名 `TriMC` / `TriLC` 保留为兼容路径名，复用 `TriDeployment -> TriAuto` 先例与 `install-tricade.ps1` 的 `-MigrateLegacy` 机制；后续自动扫描、批处理 prompt、报告聚合和教程生成必须维护 `TriMMC <-> TriMC`、`TriRLC <-> TriLC` 的 alias 映射，避免把新旧名误判成两个模块。
- 上述 alias 为双名过渡期安排，终点为触发式而非时间式：改名兼容批次落地且存量装机迁移完成即收，终点条件登记在案以防双名无限延长（新名立不住）。
- 消歧条目：`TriMLC`（Meta Local Controller，元虚拟本地控制器，系统模块）≠ `TriModel`（Provider/Model 统一配置层，npm 包名 `trimodel`）。语域口径：TriModel＝组件层（模型配置），TriMLC＝系统层（元虚拟本地腿）。口语读法约定：TriModel 读 "Tri-Model"（2 音节），TriMLC 拼读 "Tri-M-L-C"（4 音节）。
- 叙事合流：元虚拟/元现实双系统对与 `docs/execution/two-phase-architecture-roadmap.md`（v2 系统论）的训练系统/生产系统两套永续系统是同一划分的两种词汇（元虚拟/元现实 对 训练/生产），引用时两套词汇互解释义，不作为两条顶层叙事线分别引用。
