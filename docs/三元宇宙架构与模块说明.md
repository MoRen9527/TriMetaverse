# 三元宇宙架构与模块说明

版本：V0.2
日期：2026-04-23
状态：当前阶段说明

## 1. 文档定位

本文用于承接 TriMetaverse 项目级的架构说明、模块说明，以及 `reference` 层与开源吸收链的统一口径。

这里记录的是项目整体架构与模块边界层面的说明，不是某个具体代码仓、运行时模块或实现细节的开发规则。

当前该部分内容先由总助协助收口到项目文档层；待 `CTO` 正式上岗后，再交由 `CTO` 作为技术真源 owner 持续维护。

## 2. TriMetaverse reference说明

- 任何开源代码吸收，必须先从 TriMetaverse 整体架构、模块职责和长期边界判断开始；先确定它服务哪个模块、解决哪一层问题，再决定是否进入吸收链。
- 上游源码必须先统一放到 `TriMetaverse/reference/`，作为 reference 层；reference 只用于阅读、对照、拆解、留档和版本锚定，不得直接当作本地运行时真源。
- 一旦确认某个开源项目需要被 TriMetaverse 长期融合为独立模块，必须创建与其他主模块同级的模块目录；不得把 `reference/` 目录直接冒充模块本体。
- 该模块内必须建立 `vendor/` 目录，作为上游代码的冻结基线和渐进式吸收层；vendor 默认优先保持上游原貌，用于从最小版跑通到后续完整复刻之间的持续参考。
- 开源吸收链统一写为：`TriMetaverse/reference -> 模块/vendor -> 模块真实实现`；不得跳过 reference 直接散改上游代码，也不得把 vendor 误写成自研主干。
- 当前阶段必须先跑通最小版闭环，再决定是否继续扩展到更完整的复刻；能通过 wrapper、adapter、配置覆盖和最小 patch 复用上游的，不先重写平替。
- 吸收上游代码时，优先复用其成熟、稳定、已被验证的优势能力；对与现有体系重复、弱于现有实现、或不服务当前阶段目标的功能，明确列为排除项，不必复刻。
- 不得为了“看起来完整”而复制上游全部能力；凡是不属于当前模块职责、不符合当前阶段最小闭环、或会造成重复功能的部分，直接砍掉或后置，避免双份实现和边界混乱。
- 项目级目标不是机械复刻上游，而是形成符合 TriMetaverse 总体架构的最优解：弱势功能砍掉，优势功能吸收，重复能力合并，模块边界保持清晰。
- 如开源吸收动作会引入新的长期主模块或改变既有模块边界，必须先咨询 `BusinessStrategy`；在中央真源口径更新前，不得把边界变化写成既成事实。

## 3. 当前阶段运行与宿主边界

- “虚拟公司”是当前所有人格 Agent 与非人格 Agent 的经营和交互核心载体，不再把经营自治单独命名为第三个基础设施主控。
- `TriMC` 是当前统一的 agent runtime 与 interaction core，负责运行时、planner、context 整理、tools 接入、模型调用以及相关交互切片。
- `TriMC` 当前以 `TriMC/vendor/openclaw/` 中的 OpenClaw 核心作为 shadow 基线；后续再按真实集成进度吸收 Hermes 的优势能力。
- shadow 与正式接管当前都直接运行在 `copilot` 宿主上；正式切换通过 `TriHost` 配置实现，而不是把 `Tride` 写成正式宿主。
- `TriHost` 负责宿主适配、多 host 配置与正式切换承载；在真实实现落地前，应明确标注为待初始化或待接入。
- `Tripilot`、`Tride`、CLI（如 `opencode`、`claude code`、`codex`）与 `vscodium` 共同组成 PC 端软件层；其中 `Tride` 是本机 runtime / CLI orchestration 底座，不再承担正式宿主语义。
- PC 端软件层一方面配合 `TriLC` 完成本地化任务、本地工具调用与部分服务域下发任务，另一方面也保留给用户直接使用的桌面自动化、PC 软件自动化与 `vibe coding` 入口语义。
- `TriSkill` 是未来的统一 skill 提供模块；在真实代码、README 或结构文档落地前，只能标注为待初始化，不能写成现役能力。

## 4. 模块主旨与期望能力基线

本节是“模块摸底 / registry 收口 / 小白教程化梳理”的中央主旨真源。后续任何模块级扫描，都必须先把真实代码、真实文档与本节的“功能主旨 / 期望能力 / 当前状态提醒”做对照，再写 gap、风险和后续计划。

如某模块真实职责准备发生长期变化，必须先更新中央 `BusinessStrategy` 口径，再改模块级 registry；不得先在模块里把边界变化写成既成事实。

| 模块 | 功能主旨 | 期望能力 / 关键职责 | 当前状态与边界提醒 |
| --- | --- | --- | --- |
| `TriMetaverse` | 中央战略仓与项目级真源 | 维护总商业模式、阶段门禁、workflow、中央 registry、reference 吸收链规则 | 不直接承担各模块业务实现 |
| `TriCompany` | 虚拟公司研发仓与经营编排孵化仓 | 沉淀产品/工程/registry 文档、总助草案、Hermes 融合草案与当前阶段 Copilot 宿主资产 | 试运行宿主资产承载中，不等于已成为正式主控宿主 |
| `TriMC` | 统一 agent runtime 与 interaction core | 负责 runtime、planner、context 整理、tools 编排、模型调用、服务域执行与研发工作流运行切片 | 当前 shadow 基线在 `TriMC/vendor/openclaw/`，后续再吸收 Hermes 优势能力 |
| `TriLC` | 本地域控制器 | 负责 detached local runtime、本地节点升级、planner、tool bus、本地执行生命周期 | 面向本地域执行，不替代服务域主控 |
| `Tripilot` | VS Code 扩展与 webview 用户入口 | 负责桌面交互入口、本地域工具入口与用户侧可直接使用的交互前台 | 只维护模块事实，不重写总体战略 |
| `Tride` | PC 端开发工具链与 orchestration 底座 | 接入 `opencode`、`claude code`、`codex` 等开发能力，承接 runtime/CLI/SDK 与 agentic orchestration | 不再承担正式宿主语义 |
| `vscodium` | IDE 宿主基础设施 | 承接 Tripilot 配套宿主、上游同步、桌面开发工作台与本地自动化环境 | 必须区分上游能力与本地定制 |
| `TriHost` | 宿主适配与正式切换承载层 | 负责多 host 配置、正式切换、宿主差异封装 | 当前待初始化 / 待接入 |
| `TriSkill` | 统一 skill 提供模块 | 负责未来统一 skill 封装、分发与跨宿主供给 | 当前待初始化，不能写成现役能力 |
| `Tristaciss` | 模型 SDK 接口转换与 API 平台 | 负责多提供商适配、云端/本地模型路由、接口转换、前后端统一调用面 | 当前产品真源优先看 `CLAUDE.md` 与 `AGENTS.md` |
| `Triavatar` | Web 入口与未来虚拟形象入口 | 负责 Web 端入口、未来虚拟形象体验与规划中的游戏化入口 | 必须区分已实现内容与未来 3D / 4D / 游戏规划 |
| `Trideployment` | 自动部署与交付完备性模块 | 负责镜像族、Kubernetes 发布面、GitOps 模板、交付完备性审计 | 不能把尚未生成的部署资产写成现役交付件 |
| `TriTest` | 测试与质量门禁模块 | 负责自动测试、覆盖率、测试脚手架、CI 回归和测试完备性审计 | 只有真实报告或脚手架存在时才能写成已具备能力 |
| `TriDev` | 自动化开发流程模块 | 负责“源码开发 -> shadow test -> 本地正式接管 -> 持续迭代”的流程沉淀、版本号签发、产物归档、阶段 gate | 当前待开发；不要把“本地正式接管”和“TriMetaverse MVP 正式上线”混写 |
| `TriGateway` | 网关模块的规范化中央名称 | 先用于统一命名、后续网关真源落位与未来 registry 建立 | 规范目录已修正为 `TriGateway/`；为平滑迁移，历史路径 `TriGatway/` 暂作为兼容别名保留；在 README / AGENTS / 实现出现前，具体职责仍待中央补定 |
| `TriMobile` | 本地域移动端入口 | 负责移动端触达、本地域移动体验与未来和 `Triavatar` 协作的入口形态 | 当前占位，能力均应标为待初始化 |
| `TriMem` | 用户系统模块 | 负责用户体系、身份绑定、区块链身份关联与数据库设计 | 当前占位，禁止虚构 schema 或身份流程 |
| `TriWeb4` | Web3 / Web4 模块 | 负责钱包、合约交互与 Web3 / Web4 能力 | 当前占位，禁止虚构协议栈与进度 |
| `TriChain` | 公链模块 | 负责链上执行、公链能力与链上集成 | 当前占位，禁止虚构链型、合约部署状态或进度 |

当前阶段涉及 `TriCompany` 源仓、`TriCompany-copilot-host-assets` 支撑包、`TriMetaverse/.github` live 宿主入口与 `TriMetaverse/docs` 中央摘要层之间的治理关系，统一参见 `docs/workflow/tricompany-copilot-host-assets-governance.md`。
若只是定位当前阶段的模块事实、published-copy 规则或 host operator 动作，默认先回 `TriCompany/` 真源、`TriCompany/.github/manifests/tricompany-published-copy-manifest.json` 与治理页；只有在确实需要当前宿主专用 runbook、phase 证据或 support-object-set 时，才补看 `TriCompany-copilot-host-assets/**`。

## 5. 命名与别名治理

- 中央 registry、计划文档、教程文档统一使用 `TriGateway` 作为规范化模块名称。
- 物理目录已修正为 `TriGateway/`；为保证已有 workspace、脚本和外部引用平滑迁移，历史 typo 路径 `TriGatway/` 暂作为兼容别名保留。
- 后续自动扫描、批处理 prompt、报告聚合和教程生成都必须维护 `TriGateway <-> TriGatway` 的 alias 映射，避免把两个名字误判成两个模块。
- 模块摸底与教程化实施计划见 `docs/workflow/module-registry-baseline-rollout-plan.md`。
